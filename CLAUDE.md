# OPERATING CONTRACT

If this conflicts with anything under REFERENCE, this wins.

## Response style — with one exception

Terse, action-first, no trailing summaries, don't re-explain what the code already shows. **Exception: plan/spec verification output is not "over-explaining."** When verifying (see The Gate), state what you checked, the exact command you ran, and what you found — explicitly, out loud. Terseness never suppresses verification reporting. These two rules do not compete; this carve-out is the tiebreak.

## Memory — one rule, no ambiguity

`MEMORY.md` / auto-memory exists so you don't re-ask the user things already settled (preferences, prior decisions). It is **never a citation.** Any claim sourced from memory, CLAUDE.md, or a code comment that touches a write path, money math, routing, or schema must be re-confirmed against code (`grep`/`Read`) before it enters a plan or spec. Memory orients; code decides. Do not resolve this toward "trust memory" because re-checking is friction — re-checking is the job.

**Same rule for agent/doc output — scoped to merge/done/release-state claims.** Any "PR merged", commit SHA, "QA passed", or deploy/release-gate claim — whatever its source — gets one mechanical check before you repeat or act on it: `git cat-file -t <sha>` / `gh pr view <n> --json state,mergeCommitOid`. Agents fabricate completed work that passes plausibility (hallucinated merge SHAs that were never git objects; an invented QA run written into a release-gate doc) — the project's signature failure mode. Scope the check to merge/done/release-state — **not** every agent-added identifier; the one-sentence-diff path stays exempt.

**Destructive batch sweeps get an adversarial refute, not a spot-check.** When a fan-out/triage verdict drives an *irreversible* action across many items — closing issues, deleting branches, dropping stashes — run every `already-done`/`drop`/`safe-to-delete` verdict through a **fresh skeptic prompted to refute it** (find the unmerged commit / the unmet acceptance box) before acting; only verdicts that survive get executed (a spot-check let a half-done #223 reach a `close`). `.claude/workflows/verified-sweep.js` encodes this (investigate → refute → act); reach for it on any multi-item close/delete sweep.

## The Gate — fresh-context review before implementation

A plan/spec authored in-session ships its author's blind spots into the implementation. The in-session checklist below does not catch this on its own: every worked example in `docs/SPEC-VERIFICATION.md` is a logged case where the embedded check missed it and an independent fresh-context reviewer caught it. The checklist is the reviewer's rubric, not a substitute for the reviewer.

**Mandatory before writing code — NOT only for hand-offs — when the change touches ANY of:**

- `BalanceCalculator` / money math / `MoneySerializer`
- `security/firestore.rules` or Cloud Functions auth/validation
- routing (`app_router.dart`, route tree, deep links, back guards)
- a data-shape / schema / field-name change with both a read-path and a write-path

→ Run **fresh-context Opus review** (zero session history) against the spec **before implementation** — `/run-the-gate` drives it: each round spawns **TWO parallel fresh reviewers** (rubric + orthogonal-axis adversary — single-reviewer rounds missed the #857 caption regression twice; the adversary hunts off-map regressions and derived surfaces); never reuse this session's context, and neither reviewer sees the other's verdict. Apply the union of [P1]s, re-run with a *new* pair each round, stop when BOTH verdicts are P1-clean in the same round (~2 rounds typical; 3 = over-scoped spec). Unconditional for the categories above — "it's not being handed off" is **not** an exemption; the disasters happen in-session too, and convergence pressure (sycophancy, momentum, prior approval) is exactly what this interrupts.

Outside those categories (describable as a one-sentence diff, no money/route/schema/rules surface): skip the gate, just do it.

## Verification principles

Run while writing the spec; report results out loud. Full reasoning + worked examples: `docs/SPEC-VERIFICATION.md`.

1. **Classify every callsite on a shared read/write path** — INBOUND (display only) / OUTBOUND (feeds a write) / BOTH (treat as OUTBOUND). Skipping this is how display-formatted strings get persisted unchanged.
2. **Verify every concrete claim against code, not docs.** Paths, route constants, field names, scripts. Re-run the grep in the moment; an upstream agent's citation is not proof.
3. **Trace one read-path per write-path.** "Who reads this after it changes?" must have a named answer.
4. **Enumerate fields from the type, not memory.** Open the model file; list exhaustively.
5. **Spell out data contracts, don't gesture at them.** Exact map keys, exact callback signatures, exact prop names. "Two different shapes" is an intention, not a spec.
6. **Verify arithmetic decomposition.** `aggregate = sum(slices)` asserts the field decomposes across the slicing — read the field-construction lines, not the algorithm flow. (`netBalance` folds settlements; `totalPaid` does not.)
7. **Adversarial pass on an orthogonal axis.** If the fix is on axis A, the worked example must exercise axis B (settlements / money-flow / scope / time / identity). Same-axis examples only re-prove what you already believed. Distrust your own earlier in-session claims; treat each iteration round as v1.

## Workflow

- Plan before multi-file work; author the spec with **`superpowers:writing-plans`** → `docs/plans/<date>-<topic>.md`, then run the 7 verification principles + the Gate on it. Capture the plan before touching code.
- Bug fix = failing regression test first (RED) → fix (GREEN) → re-run failing test → full suite. No fix ships without a test that would have caught it.
- `flutter analyze` clean before you call anything done; run the relevant tests after.
- Commits: conventional (`feat(scope):` …); match `git log --oneline -20`.
- PRs: review the whole branch diff (`git diff main...HEAD`), not the last commit.
- In doubt about scope: smaller change + follow-up, don't bundle.
- **Merge hygiene kills ghost-debt at the source.** Every PR body carries `Closes #N` (partial → `Refs #N` + name the unmet boxes, issue stays open re-scoped); the repo auto-deletes head branches on merge. `.github/pull_request_template.md` carries the ritual. **For a partial delivery, `Refs #N` must be in the COMMIT MESSAGE too, not just the PR body** — squash-merge auto-closes from the squashed *commit message* (which inherits your branch commits' bodies), NOT the PR description (#447's body said `Refs #428`, its commit body said `Closes #428`, #428 wrongly auto-closed). Amend the commit — editing only the PR body is not enough.
- **Surface the fan-out plan before launching a large workflow.** A multi-agent / high-token workflow states its clusters in one line *before* spending, so scope can be redirected before the cost — not narrated after it.
- **No Schrödinger's fix.** A fix is in exactly one state: an open PR, merged, or explicitly deferred to a named milestone. Never the resting state of a `git stash` or an unpushed local branch — that's invisible debt that reads as "almost done" forever.
- **Backend deploy state is a git tag, not a memory note (#327).** Before deploying Functions/rules, run `tool/pending_deploy.sh` (or the **`deploy-ceremony`** skill); the moving **`backend-deployed`** tag is the machine source of truth for what's in prod (advanced ONLY by `tool/deploy_firebase_backend.sh` on a successful deploy + prod-state verify); `docs/DEPLOY-LEDGER.md` is the human history (never parsed). Don't reconstruct "what's deployed" from scattered `⚠️ NOT deployed` flags.
- **No real users yet → server changes deploy freely.** No client-compat gating, no deploy-first-vs-client-first ordering — overrides every `⚠️ old clients PERMISSION_DENIED until client ships` note (#290/#318/#294). Revisit only once a shipped client has users.
- **Triage/PICK rigor:** revalidate stale open issues with `.claude/workflows/triage-sweep.js` (Workflow) — it verifies each issue against live code (still repros? severity right? secretly fixed?) and refutes every close verdict before acting (the #223 half-done-close guard, applied to triage). Caller supplies the issue list; only act on `closeCleared`.

## Project Overview

Rihla ("Journey") — Splitwise-style group expense splitter: persistent groups → events → ledger. Package `safar`, Android `com.safar.safar`, version per `pubspec.yaml`. Backend **Firebase only**: Firestore, Auth, Cloud Functions (Node 22/TS), FCM. No Firebase Storage SDK — protected media via Functions. Firestore offline persistence handles offline reads and queued-write replay (the hand-rolled SQLite read-cache was removed in #50). Anon auth on first launch + optional email-link recovery. Supabase migration is **complete — do not add Supabase keys**.

## Financial Calculations — landmines

`decimal` package, never `double`. Default OMR (3dp); also USD/EUR/GBP/SAR/AED/QAR. `BalanceCalculator` lives in `lib/features/ledger/providers/expense_provider.dart` (**not** a separate `balance_calculator.dart` — people hunt for one that doesn't exist). Scopes: global/subGroup(legacy)/personal/custom. Splits: equally/shares/exact/percent. **Rounding remainder → alphabetically-last recipient** so `sum(shares)==amount` — don't move without updating `balance_calculations_test.dart`. **Quantize every per-head/per-slice share via `_toCurrencyPrecision` (→ `MoneySerializer` subunit round-trip), NEVER `Decimal.toDecimal(scaleOnInfinitePrecision:)` alone** — that only rounds NON-terminating divisions, so a terminating sub-subunit quotient (e.g. OMR 2.900/8 = 0.3625) slips through as a half-subunit share, breaking the client↔server oracle parity below and leaving `netBalance` non-whole-subunit (settle-up cap then rejects the full balance). All allocators (`_allocateEqual`/`_allocateWeighted`) now quantize; mirror it in any new one (#596). Settlement opt: greedy min-transactions. `MoneySerializer` converts `Decimal`↔integer subunits **only at the Firestore boundary**; inside the app stay in `Decimal`. Scale: OMR/KWD/BHD=1000, USD/EUR/GBP/SAR/AED/QAR=100, **JPY=1** (easy to forget). Every allocator **must never emit a negative owed** — `firestore.rules` only checks `splitDistribution is map`, not signs/sum, so a forged write can persist negatives or tolerance-drift over-allocation; the calculator defends (negative entry → equal-split fallback FIRST, before tolerance/drift checks since a negative can still be in-tolerance; in-tolerance residual closes onto the alphabetically-last recipient that can absorb it without going negative). **`calculateBalances` is a cross-implementation ORACLE** mirrored byte-for-byte by the TS server oracle `recomputeNet` (`functions/src/callables/groupNetBalance.ts`; the SHARED allocators are reused by `deleteGroup`/`leaveGroup`/`removeMember` — no second copy to drift): same per-event universe (`participantIds ∪ (payers+settlement parties \ live)`, NOT split recipients), same "drop owed for any key outside the universe," same in-tolerance exact residual close-out, same negative→equal-split guard. So a key referenced by a split but absent from `participants` is **dropped on purpose** (parity contract, not a bug to "fix") — the conservation gap (a departed explicit-split recipient, #249) is fixed at the **caller's universe construction on BOTH client and server**, never by changing drop semantics; the per-event drill-down (`_buildPerEventBreakdown`) is intentionally `participantIds`-only. New negatives stay rules-blocked (`firestore.rules` `splitValuesNonNegative`, ~L528), so the guard only fires on legacy/Admin docs. Parity pinned by `delete_group_balance_parity_test.dart` (1b residual; 1c/1d/1e negative fallback) + `group_balance_provider_test.dart`.

**Itemized split (#203/#605) = `SplitMode.exact` + opaque `splitExplanation` — NOT a new `SplitMode`.** `BalanceCalculator.allocateItemizedDistribution` reduces items (+ #605 service/tax/tip/discount adjustments) to a whole-subunit exact `splitDistribution` CLIENT-SIDE; discount re-allocates the *remaining* bill proportional to pre-discount owed (provably keeps every owed ≥ 0). `splitExplanation` (`split_explanation.dart`) is INBOUND/display-only — it reconstructs the editor on reopen and is NEVER read by `recomputeNet`/any Function; `firestore.rules` guards it as `is map && size()<=64` (opaque). So balance truth stays in `splitDistribution` and the client↔server oracle parity holds with NO server/rules change — **never wire the server to read `splitExplanation`, and never add a `SplitMode.itemized`.**

**Settlement creates are CALLABLE-ONLY (#1129).** The `recordSettlement` Cloud Function (`functions/src/callables/recordSettlement.ts`) is the SINGLE create path for BOTH scopes — `firestore.rules` denies client settlement creates everywhere, and the client activity type allow-list dropped `event_settlement`/`group_settlement` (phantom-history forge closed; those rows are server-authored, actorName derived from the recorder's member doc matched by `userId` FIELD). Inside ONE `db.runTransaction` (the correctSettlement idiom, NOT the #1144 3-phase lock) the server recomputes the pair's outstanding on the settle's SCOPE basis via the shared oracle, **REJECTS `amountFils > outstanding`** (`failed-precondition {kind:'over-outstanding', outstandingFils}` — closes the #1093-residual over-settle/forged-amount hole; reject, never clamp), derives the #1093 `sd1` dedup id from the client's `observedPairEpoch` (TS ports in `functions/src/callables/shared/settlementIds.ts`, golden-vectored byte-parity with the retired Dart helpers — a retry/racer of the same observation returns `alreadyRecorded:true`, probe runs BEFORE the cap), and writes doc(s) + the ONE #1140 activity row atomically with ISO-STRING timestamps only (a Firestore `Timestamp` type-buckets apart in `orderBy` and epoch-0s `Settlement.fromFirestore`). Consequences, don't fight them: settlement recording is **ONLINE-ONLY** (HTTPS callables have no offline queue — screens pre-flight `connectivity == ConnectivityStatus.offline` and `syncing` PROCEEDS); the home bump is server-gated (`shouldBumpLedgerRevision`); the #773/#719/#1106 client revalidations stay as ADVISORY UX (server is authoritative); cap bases are per-scope BY DESIGN (event = that event's #249-universe snapshot mirroring `_freshOutstandingForPair` — deliberately per-event, not pair-global; group/gsu total = full-group aggregate `.net`; gsu legs = participantIds-only `perEventNet` drill-down matching the client decompose) — widening any basis breaks client↔server parity and false-blocks legit settles. #1140 residue: the co-batched CLIENT activity rows now cover only event created/deleted; `member_joined` stays best-effort; settlement rows are the server's.

**Group settle-up DECOMPOSES into per-event legs (#752) — since #1129 as ONE `recordSettlement` mode `'groupSettleUp'` transaction, retiring the client `WriteBatch` AND `kMaxDecomposeLegsAtomic` (the 20-access-call rules budget no longer applies; the server bound is `MAX_FAN_IN_EVENTS` = 400 legs, so the old >8-leg single-write carve-out is GONE — big settle-ups decompose fully).** The client still runs the pure `BalanceCalculator.decomposeGroupSettlement` (capped integer-subunit allocator: `Σ(perEvent)+residual==toSubunits(A)` exactly, residual ≥ 0 never negative) and sends legs in the displayed `eventOrder` (the WYSIWYG contract); the server re-verifies conservation, caps every leg at its event's drill-down overlap (`{kind:'stale-decomposition'}` on mismatch), enforces #1144 membership itself (#720 defer-to-server — the client `bothLiveMembers` pre-gate is deleted), and derives the shared `groupSettleUpId` (= the gsu `sd1` id; the client no longer mints a UUID). The ONE remaining client routing fallback: `decomposition.perEvent.isEmpty` (pure cross-event pair) → mode `'group'` single aggregate settlement. **The oracle/`recomputeNet` is UNTOUCHED** — it folds event settlements per-event and group settlements globally by collection PATH; `groupSettleUpId` stays a display/correction link, **oracle-invisible (never wire the server's balance math to read it)** — same contract as `splitExplanation`. The one-tap **correct button stays HIDDEN** on `groupSettleUpId`-tagged settlements — logical corrections route through `correctLogicalSettleUp`.

Settlement doc ids are deterministic dedup keys (`sd1…`, #1093) derived from (scope, directed pair, currency, subunits, pair-epoch) — since #1129 derived SERVER-side in `recordSettlement` (the client sends `observedPairEpoch` via the retained `SettlementService.directedPairEpoch`); never revert to random uuids on a create path, and never add id inputs that differ across devices (names, timestamps, notes).

**Group settle-up RECORD refuses a converging basis (#1106).** `groupBalancesProvider` deliberately proceeds-on-partial while per-event streams deliver their FIRST snapshot (#244 display decision — keep it), so a cold-`push()` entry can render an understated balance with a live Record CTA; `_showRecordPaymentSheet` therefore gates BOTH its entry and the #719 confirm-time re-read on `groupConvergingEventIdsProvider` (the loading-skip mirror of `groupFailedEventIdsProvider`). Don't wire the converging set into the balance provider or the #244 error banner (display stays warn-not-block), and don't remove the gate to "simplify" — the #719 re-read alone cannot catch the window (it re-reads the same still-converging provider).

Functions: `functions/src/` (TS, Node 22), Jest under Java 21 + emulator.
