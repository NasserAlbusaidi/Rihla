## Verdict

This is a "splitter that pretends to be multi-currency". `MoneySerializer` is the only correct multi-currency component; everywhere else, `OMR` is hardcoded at the boundary, and the rest of the system silently coerces foreign currencies into the OMR scale on every settlement write, every edit-amount round-trip, every Add-Expense submission, every SQLite cache decode. The "boundary discipline" the CLAUDE.md crows about exists in `MoneySerializer.toSubunits/fromSubunits`, but nowhere upstream — there is no single source of truth for "what currency is this event in?", and the call sites have responded by sprinkling `'OMR'` literals (≥ 6 distinct sites in the ledger feature alone, more in the cache). On top of that: `BalanceCalculator` does not enforce `isDeleted`, the settlement adjustment math silently mis-reports `totalPaid`, the settlement cache writes amounts with no currency column at all, and the optimal-settlement payload smuggles `Decimal` through a `Map<String, dynamic>` that downstream tiles `as`-cast non-null. Fix-and-ship is not on the table for v1.0 if you ever add a second currency. For OMR-only launch, the CRITICALs are still real — soft-delete leakage and the settlement cache write being lossy will hurt you regardless of currency. Rethink before you take a non-OMR group live.

## CRITICAL (5)

### 1. Settlements write `currency: 'OMR'` to Firestore unconditionally — drops the caller-supplied currency on the floor
- **Location**: `lib/features/ledger/models/settlement_model.dart:130-137`
- **Principle**: Partial write across stores / leaky abstraction. The model claims it serializes a settlement; in fact it rewrites currency.
- **What it says**:
  ```dart
  Map<String, dynamic> toFirestore() {
    const currency = 'OMR';
    return {
      ...
      'amountFils': MoneySerializer.toSubunits(amount, currency),
      'currency': currency,
      ...
    };
  }
  ```
- **Why it bites**: `Settlement` has no `currency` field on the in-memory model, so this isn't even using the value the caller passed in to `SettlementService.addSettlement(currency: 'USD', ...)`. The service builds its own data map (which does honour `currency`, line 84-85), but anyone who calls `settlement.toFirestore()` directly — including future code paths, migrations, batch repair scripts, or anyone who tries to re-persist a Settlement read off a stream — will silently relabel USD/EUR/GBP as OMR while keeping the integer subunit count. A 100-USD settlement (10 000 subunits at scale 100) re-persisted via `toFirestore` becomes "10.000 OMR" the next time someone reads it back through `MoneySerializer.fromSubunits(10000, 'OMR') == 10.000`. Currency-corruption is undetectable in the UI because the user already typed OMR.
- **Related issues**: #2 (no `currency` field on `Settlement`), #3 (`AddSettlement` writes hardcoded OMR upstream too), #6 (settle_up_screen hardcodes `'OMR'`).

### 2. `Settlement` model has no `currency` field — round-trip from Firestore drops it
- **Location**: `lib/features/ledger/models/settlement_model.dart:5-46` (no `currency` field), `:94-124` (`fromFirestore` reads `data['currency']` into a local, ignores it)
- **Principle**: Broken invariant. The persisted shape carries currency; the in-memory shape doesn't. Read-path drops a load-bearing field.
- **What it says**:
  ```dart
  factory Settlement.fromFirestore(Map<String, dynamic> data) {
    final currency = data['currency'] as String? ?? 'OMR';
    final amountFils = data['amountFils'] as int? ?? 0;
    ...
    return Settlement(
      ...
      amount: MoneySerializer.fromSubunits(amountFils, currency),
      // currency: currency,   // ← does not exist on the model
    );
  }
  ```
- **Why it bites**: The amount is decoded with the right currency once, then the currency identity is thrown away. Downstream, every settlement is rendered with whatever currency the UI screen hardcodes (`'OMR'`). The moment a USD settlement is committed (which is possible — `SettlementService.addSettlement` exposes `currency: 'USD'`), it's displayed and re-formatted as OMR everywhere. The amount magnitude is right (decoded correctly once) but the identity is wrong. Worst case: the user records a 100 USD settlement, sees "100.000 OMR" in the history, settles up "again" against an OMR ledger, double-counts the payment. This is the exact class of bug B3 (append-only settlements) was supposed to prevent.
- **Related issues**: #1, #3.

### 3. `BalanceCalculator.calculateBalances` does not filter `isDeleted` — relies entirely on the service-level query filter
- **Location**: `lib/features/ledger/providers/expense_provider.dart:175-315`
- **Principle**: Trust boundary violation. A pure money function trusts its caller to have pre-filtered deleted rows. Any path that bypasses the Firestore stream — SQLite cache, tests, direct queries, an exported audit log, a future debugging tool — will fold deleted rows back into the math.
- **What it says**:
  ```dart
  for (final expense in expenses) {
    final payerId = expense.payerParticipantId;
    if (paidMap.containsKey(payerId)) {
      paidMap[payerId] = paidMap[payerId]! + expense.amount;
    }
    // No isDeleted check anywhere in calculateBalances.
  ```
- **Why it bites**: `ExpenseCacheRepository.getExpenses` *does* filter `is_deleted = 0`, but it's a per-callsite contract, not an invariant of the calculator. If anyone ever reads from a path that doesn't filter — including the SQLite cache after schema-drift, or an `eventExpensesProvider` that fails its side-write and falls back to a raw read — a soft-deleted expense gets summed into `totalPaid` and `owedMap`, and the balance is silently wrong. The whole point of soft-delete is recoverability with a guaranteed exclusion from math; the calculator is the wrong layer to omit that check. Bonus: `Expense.fromFirestore` reads `isDeleted` into the model and the field is right there on `expense.isDeleted`. The fix is one line; the *absence* of that line means every future caller has to remember.
- **Related issues**: #4 (totalPaid is already wrong about settlements; a deleted expense is just another way it lies).

### 4. `UserBalance.totalPaid` does NOT include settlement payments — it lies in its own field name
- **Location**: `lib/features/ledger/providers/expense_provider.dart:278-305`
- **Principle**: Naming that misleads + broken invariant. `totalPaid` is what callers will reach for to answer "how much has this person paid?" The field decomposition `netBalance = (totalPaid + settlementAdj) - totalOwed` shows that settlements are folded into `netBalance` but kept out of `totalPaid`.
- **What it says**:
  ```dart
  for (final s in settlements) {
    if (s.payerParticipantId != null && settlementAdjustmentMap.containsKey(...)) {
      settlementAdjustmentMap[s.payerParticipantId!] += s.amount;
    }
    ...
  }
  ...
  final totalPaid = paidMap[p.id] ?? Decimal.zero;
  final totalOwed = owedMap[p.id] ?? Decimal.zero;
  final settlementAdj = settlementAdjustmentMap[p.id] ?? Decimal.zero;
  final netBalance = (totalPaid + settlementAdj) - totalOwed;
  ```
- **Why it bites**: `SettlementSummaryCard` (and any future export, dashboard tile, or "amount paid by you" UI) reads `myBalance.totalPaid` and shows it as the user's lifetime paid amount. After two people record settlements, the "Total paid by you" tile undercounts those payments by the settlement amount — silently — while the net balance is correct. The aggregate-equals-sum-of-slices invariant from CLAUDE.md ("Verify arithmetic decomposition. `aggregate = sum(slices)` asserts the field decomposes across the slicing — read the field-construction lines, not the algorithm flow. (`netBalance` folds settlements; `totalPaid` does not.)") is *literally documented as a bear trap* in the project's own contract, and the contract correctly predicts the production behaviour you have here. Either rename `totalPaid` to `totalExpensePaid` (and add a `totalSettlementsPaid` if anyone needs it) or fold it in. Don't ship a field whose name lies.
- **Related issues**: #11 (SettlementSummaryCard reads this field directly and surfaces it).

### 5. `ExpenseCacheRepository._decodeSplitValue` hardcodes `'OMR'` when reading `SplitMode.exact` from SQLite — silently destroys non-OMR exact splits
- **Location**: `lib/core/services/cache/expense_cache_repository.dart:152-162`
- **Principle**: Partial write across stores. The cache is supposed to be transparent; here it loses information.
- **What it says**:
  ```dart

    final persistedValue = _persistedInt(value);
    return switch (mode) {
      SplitMode.exact => MoneySerializer.fromSubunits(persistedValue, 'OMR'),
      ...
    };
  }
  ```
- **Why it bites**: An exact USD split persisted as `199` (1.99 USD at scale 100) is decoded as `0.199` OMR. Same row, written by the cache repository, read by `BalanceCalculator` (via the cache fallback path) — every USD/EUR/GBP/SAR/AED/QAR exact split silently divides by 10 the moment the app reads from SQLite instead of Firestore (offline mode, cold start, the asyncMap side-write race). The SQLite row has no `currency` column at all (see `cacheExpenses` columns at `:48-63`) and `Expense.fromCache` returns rows with no `currency` (line 80-109), so the model is constructed at default 'OMR' and the split decode also uses 'OMR'. Two compounding bugs in one path. JPY (scale 1) is worse: `199` decodes as `0.199` instead of `199`.
- **Related issues**: #12 (cache writes no currency column), #1 (settlement Firestore write same shape of bug).

### 10. `_persistedInt(Decimal/num) -> .toBigInt().toInt()` truncates silently for fractional values, no guard
- **Location**: `lib/features/ledger/models/expense_model.dart:357-362`, `lib/core/services/cache/expense_cache_repository.dart:164-168`
- **Principle**: Trust boundary violation + fail-silent. The function is named `_persistedInt` and takes `Object?` but is called on values that, for exact splits, are subunit integers and for percent splits are scaled-by-1000 integers, but for shares can be `Decimal.fromInt(...)`. Mix the wrong mode at the wrong time and you get truncation with no signal.
- **What it says**:
  ```dart
  static int _persistedInt(Object? value) {
    if (value is int) return value;
    if (value is num) return value.toInt();         // truncates 9.99 to 9 silently
    if (value is Decimal) return value.toBigInt().toInt();  // same
    return Decimal.parse(value.toString()).toBigInt().toInt();
  }
  ```
- **Why it bites**: If a future migration or an offline-cached Firestore doc roundtrips an exact-mode distribution as a string like `"9.99"` (cents not encoded as integer) or as `num` (Firestore happily returns `9.99` as `double` if it ever was stored as one), this function returns `9`. Silently. Splits become 9 fils where they should be 9990. The function is also one of two `_persistedInt` implementations (model and cache); both have the same shape, which means a future migration could plausibly touch one and not the other. Either validate that the input is an integer (throw or log if not) or rename to `_truncateToInt` and own the lie.
- **Related issues**: #5, #12.

### 11. `_allocateExact` falls back to **equal** split when sum-of-exact doesn't match amount within 0.001 — only signal is a `debugPrint`
- **Location**: `lib/features/ledger/providers/expense_provider.dart:336-353`

- **Why it bites**: A user records a 100 USD lunch with an exact split that sums to 100.02 (typo). The dollars don't disappear, but the *intent* does. For money math, the rule is: surface the mismatch to the user, do not silently rewrite their distribution. Either reject the split before persistence (the editor already validates this via `_canApply` in `custom_split_sheet.dart:204-216`, so the fallback only fires if persisted state diverged from validator) or emit a real signal — Sentry breadcrumb, an `invalid_distribution` flag on the expense — not a debugPrint that lands on the floor.

### 14. `_splitTolerance = 0.001` is currency-blind; for OMR it's 1 fils, for USD it's 0.1 cents (correct enough by luck), for JPY it's 0.001 yen (nonsense)
- **Location**: `lib/features/ledger/providers/expense_provider.dart:164`, `lib/features/ledger/widgets/custom_split_sheet.dart:96`

### 15. `calculateOptimalSettlements`: comparator chained via `Decimal.compareTo` is fine, but sort stability across re-renders is not — debtor/creditor order can flip if two have equal balance, producing different optimal settlements between rebuilds
- **Location**: `lib/features/ledger/providers/expense_provider.dart:437-438`
- **Principle**: Non-determinism / referential transparency. Same input, different output, no reason given.
- **What it says**:
  ```dart
  debtors.sort((a, b) => a.netBalance.compareTo(b.netBalance));
  creditors.sort((a, b) => b.netBalance.compareTo(a.netBalance));
  ```
- **Why it bites**: `List.sort` in Dart is *not stable*. Two debtors with the same `netBalance` can appear in either order between rebuilds. ### 16. `_allocateExact` accepts the user's distribution **as-is** when it validates, but never normalizes precision — the persisted shares can carry trailing fractional fils that the balance calculator sums into nonsense subunit math
- **Location**: `lib/features/ledger/providers/expense_provider.dart:336-353`
- **Principle**: Broken invariant. Every other split path runs through `_toOmaniPrecision` (`expense_provider.dart:400-405`); exact does not.
- **What it says**:
  ```dart
  return Map<String, Decimal>.from(distribution);    // raw, un-normalized
  ```
  vs.
  ```dart
  // _allocateWeighted normalizes:
  final allocation = isLast
      ? amount - allocated
      : _toOmaniPrecision(((amount * weights[recipientId]!) / denominator)...);
  ```
- **Why it bites**: A user enters "10.0005" for one participant in an exact-mode USD expense whose total is 10.001 (because the per-tile input formatter accepts `decimalDigits: AppFormatters.currencyConfig[currency]?.decimals ?? 3`). The tolerance check `(total - amount).abs() <= 0.001` passes. The distribution is persisted with sub-cent precision. `MoneySerializer.toSubunits(10.0005, 'USD') = (10.0005 * 100).toBigInt() = 1000` — `.toBigInt()` truncates the 0.05 cent. Now sum-of-persisted-shares != amount, even though the in-memory Decimal sum did. The invariant the project's CLAUDE.md spends 200 words on ("Rounding remainder → alphabetically-last recipient so sum(shares)==amount") doesn't hold for exact mode because exact mode bypasses the precision normalization.
- **Related issues**: #14 (tolerance), #10 (truncation).

### 17. `_allocateWeighted` allocates `amount - allocated` to the alphabetically-last recipient — but for `_allocatePercent`, if the sum-of-percents is within tolerance of 100 but *not exactly 100*, the last recipient absorbs the slack on top of their declared percent
- **Location**: `lib/features/ledger/providers/expense_provider.dart:374-398`
- **Principle**: Broken invariant. The user wrote percentages; the calculator overrides one of them.
- **What it says**:
  ```dart
  final allocation = isLast
      ? amount - allocated
      : _toOmaniPrecision(((amount * weights[recipientId]!) / denominator)...);
  ```
- **Why it bites**: User splits 100 USD as Alice 33%, Bob 33%, Charlie 34.001%. Sum = 100.001%, within tolerance of 100, so the validator passes. Allocations: Alice = 33.00 USD, Bob = 33.00 USD, Charlie = (100 - 66.00) = 34.00 USD — *not* the 34.001% Charlie wrote (which would have been 34.001 USD). The discrepancy is invisible and 0.01 USD here, but for round-number tolerance edge cases and for currencies with different precision the slack absorption can be larger and is *guaranteed* to land on Charlie (alphabetically last) every time, which means the same person always absorbs everyone else's rounding error. That's deliberate (per CLAUDE.md) for equal splits but unwanted for *percent splits where the user typed each percentage explicitly*. Either reject percent distributions that don't sum to exactly 100, or distribute the slack proportionally, but don't silently rewrite Charlie's percent.
- **Related issues**: #11, #14.

### M4. `Settlement.toFirestore` writes `recipientName`/`payerName` it reads at deserialization but the model has no `currency` to write — asymmetric
- **Location**: `lib/features/ledger/models/settlement_model.dart:129-146`
- **Principle**: Asymmetric serialization. `toFirestore` does not mirror `fromFirestore`.
- **Why it bites**: A model written via `toFirestore` then re-read via `fromFirestore` does not round-trip the currency; the model is structurally wrong.

### M5. `_addExpenseCreatedActivity` uses `amount.toString()` for `logText` and `'amount'` metadata, alongside `amountFils` — two sources of truth in the activity log
- **Location**: `lib/features/ledger/services/expense_service.dart:203, 215-218`
- **Principle**: Two source of truths for amount. If anyone ever fixes a bug in amount math, the activity log says one thing and the expense doc says another.
- **Why it bites**: Future "edit this expense" flow that updates `amountFils` will leave a stale `amount` and `logText` in the activity log forever (append-only logs).

### M6. `BalanceCalculator.calculateBalances` allocates new maps and a new sortedRecipients list inside the for-each-expense loop
- **Location**: `lib/features/ledger/providers/expense_provider.dart:191-276`
- **Principle**: Quadratic-ish allocation in a hot path (used per scroll-frame in the ledger screen). 30 expenses × 5 participants per expense × 1 sort per expense, recomputed every Riverpod rebuild.
- **Why it bites**: For small data this is fine. For groups that grow past ~200 expenses (which is realistic over a year), this is a measurable jank. The function should be memoized at the provider boundary or take a builder pattern that reuses the maps.

### M7. `eventBalancesProvider` and `eventUnifiedLedgerProvider` both rebuild from scratch on every settlement snapshot — no incremental update
- **Location**: `lib/features/ledger/providers/expense_provider.dart:118-156`, `lib/features/ledger/providers/ledger_provider.dart:9-44`
- **Principle**: Untestable design. The provider's job is to combine three streams, but the combination logic is duplicated across providers with subtly different loading/error semantics (see `expensesAsync.hasError` short-circuits but `settlementsAsync.hasError` doesn't, in `eventBalancesProvider:131-133`).
- **Why it bites**: A settlement read failure does not show an error UI — the calculator runs with an empty settlement list, producing an inflated "you owe" balance. Same data layer, two different error policies.

### M8. `ExpenseService.updateExpense`: `if (description != null) updates['description'] = description;` — there is no way to clear the description back to null
- **Location**: `lib/features/ledger/services/expense_service.dart:258`
- **Principle**: Naming that misleads. The argument's nullability is overloaded as "is changed".
- **Why it bites**: The Edit screen does `description: payload.description ?? ''` to work around it (`edit_expense_screen.dart:104`), which writes an empty string instead of deleting the field. Persisted empty strings vs missing fields mean two different "no description" representations live in production. Use a sentinel or a `clearDescription: true` flag like `clearSplit`.

### M9. `_distributionEquals` in EditExpenseScreen takes `Map<String, dynamic>` and compares `.toString()` — a `Decimal('1.500')` and a `Decimal('1.5')` don't compare equal as strings
- **Location**: `lib/features/ledger/screens/edit_expense_screen.dart:131-140`
- **Principle**: Wrong abstraction. Stringification of Decimal is non-canonical (trailing zeros preserved).
- **Why it bites**: A user re-opens an edit screen on an expense whose stored shares are `1.500` and the editor displays them as `1.5` (custom_split_sheet trims trailing zeros in `_formatPlainDecimal`). On Save with no UI changes, `_distributionEquals` returns false because `"1.5" != "1.500"`, and the code persists the "changed" distribution. Lots of no-op writes; harmless but indicates the equality check is structurally wrong.

### M10. `ExpenseCard` swallows the project's actual category icon source — its own switch on `_categoryIcon` ignores the `expense.categoryIcon` field
- **Location**: `lib/features/ledger/widgets/expense_card.dart:33-42`, alongside `_categoryIcon` field at expense_model.dart:49
- **Principle**: Naming that misleads / dead branches. The model carries `categoryIcon`; the card ignores it.
- **Why it bites**: Stylistic but distortive: changes to category icons in `ExpenseCategory.iconData` (which the rest of the app uses) don't reach this card. Two card widgets in the same file (`expense_card.dart` and `recent_expenses_section.dart` line 87 which actually does use `expense.categoryIcon`) have different icon sources.

### M11. `_AmountHero` in `expense_editor_body.dart` builds two stacked widgets — a visible Text and a fully-transparent TextField — so the cursor and selection are invisible to the user
- **Location**: `lib/features/ledger/widgets/expense_editor_body.dart:706-735`
- **Principle**: Naming that misleads. The widget is called `_AmountHero` and it both *displays* the amount and *captures* input; the only signal of the input being a real TextField is the underline at line 696.
- **Why it bites**: Long-press paste, cursor positioning, RTL caret — all broken because the actual input cursor is `Colors.transparent`. Users who paste a number can't see what they pasted into. Money entry UX should not be a magic trick.

### M12. `BalanceCalculator.calculateTotalExpenses` exists, is exposed, but is never used outside of `calculateBalances`'s peer functions
- **Location**: `lib/features/ledger/providers/expense_provider.dart:478-480`
- **Principle**: Dead code / premature abstraction.
- **Why it bites**: Three other callers in this file inline `expenses.fold<Decimal>(Decimal.zero, (sum, e) => sum + e.amount)` instead of using this method. Two ways to compute the same thing, neither documented as canonical.

## NOT RAISED (good calls)

- `lib/core/services/money_serializer.dart` — The serializer is the one clean thing here. Throws on unknown currency rather than defaulting, uses `BigInt` arithmetic on the Decimal multiplication, scales documented inline. If the call sites used it as documented, most of CRITICAL #1, #5, HIGH #6–#9 would be gone.
- `lib/features/ledger/providers/expense_provider.dart:260-275` — The remainder-on-alphabetically-last rule for equal splits is correctly implemented and the sort makes it deterministic. CLAUDE.md mentions it as load-bearing; the code matches the doc.

## Suggested next move

Stop. Before any v1.0 release that touches non-OMR expenses, you need a real currency story: one source of truth per event (the event doc, presumably), every screen and service reading from it, and `MoneySerializer` calls scoped by event-currency, not by literal at the call site. Walking the codebase for `'OMR'` literals is a five-minute job and produces the work list. Then: revisit `Settlement` to add a `currency` field (CRITICAL #2), normalize the cache repos' columns to include currency, and add a regression test that round-trips a USD settlement through Add → Read → Edit → Read → SQLite cache → Read and asserts the currency identity is preserved at each step. After that, separately, fix the `BalanceCalculator` invariants: filter `isDeleted` in the calculator (CRITICAL #3), rename or fix `totalPaid` to actually mean "total paid" (CRITICAL #4), and replace the silent fallback in `_allocateExact` with a surfaced error (HIGH #11). The structural items (`Map<String, dynamic>` for optimal settlements, the `_persistedInt` truncation, the duplicated split helpers) belong in a follow-up `/grill-my-plan` session — they're not fires, but they're the design choices that *let* the CRITICALs exist in the first place.
