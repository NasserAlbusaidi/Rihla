## Verdict

This is "fix and ship" for `joinGroupByInviteCode`, but it's "rethink before scale" for `deleteAccount` and `cleanupAnonUidArtifacts`. The dominant failure mode is *unbounded fan-out without resumability*: both cleanup paths iterate every event-and-subcollection serially in one callable invocation, with no checkpointing, no retry idempotency at the auth-delete-then-Firestore-write boundary, and `Promise.all` patterns that will OOM the function before they time out. The trust boundary on `cleanupAnonUidArtifacts` is also weaker than it looks — secret compared with `!==`, no rate limit, no per-oldUid attempt counter — and `joinGroupByInviteCode` has a transaction that will explode the moment a group has too many events because every read counts against the 500-write ceiling. The code is competently written at the line level; it's the *callable-as-job* design that's load-bearing and fragile.

## CRITICAL (3)

### 1. `joinGroupByInviteCode` transaction will fail under realistic group sizes

- **Location**: `functions/src/callables/joinGroupByInviteCode.ts:212-298`
- **Principle**: Unbounded resource use — Firestore transaction limits
- **What it says**:
  ```ts
  groupId = await db.runTransaction(async (tx) => {
    // ...
    const [groupSnap, memberSnap, eventsSnap] = await Promise.all([
      tx.get(groupRef),
      tx.get(memberRef),
      tx.get(eventsQuery),               // pulls every event in the group
    ]);
    // ...
    if (eventsSnap.size > 400) {
      throw new HttpsError('failed-precondition',
        'Group has too many events to join safely.');
    }
    // ...
    for (const eventUpdate of eventFanoutUpdates) {
      tx.update(eventUpdate.ref, updateData);
    }
  ```
- **Why it bites**: Firestore transactions cap at 500 writes (the 400 guard acknowledges this implicitly), but more importantly the *reads* in a transaction contend with every concurrent reader/writer of those same documents. A user joins a 300-event group, the transaction reads 300 event docs, fans out 300 updates plus the group + member writes, and on contention the SDK retries the entire transaction — re-reading all 300 docs each time. Under any concurrency (two users joining via shared link), the contention rate spikes, you eat the 60s default callable timeout, and the join silently fails with `deadline-exceeded` on the client. The 400-event guard is a tombstone — it papers over a design that should not be a single transaction at all. The fan-out belongs in a non-transactional follow-up using batched writes once membership is established. (Related: issue 2.)

### 2. Auth user deleted before Firestore cascade is durable, leaving the cleanup unrecoverable

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:530-587`
- **Principle**: Partial write across stores — ordering of irreversible operations
- **What it says**:
  ```ts
  for (const groupSnap of groupSnaps.docs) {
    try {
      const actions = await processGroup(...);
      groupsProcessed += 1;
    } catch (error) {
      groupsFailed.push(groupSnap.id);            // swallowed, retried never
    }
  }

  let authUserDeleted = false;
  try {
    await getAuth().deleteUser(oldUid);            // IRREVERSIBLE
    authUserDeleted = true;
  } ...

  if (groupsFailed.length === 0) {
    await cleanupIntentRef.delete();
  }
  ```
- **Why it bites**: A group cascade can fail (rules drift, malformed `participantNames`, contention) and be recorded in `groupsFailed`. The next thing the function does is **delete the anonymous auth user**. The auth identity is now gone. The cleanup intent is *retained* because of the `groupsFailed.length === 0` guard — but no caller can ever re-invoke this callable with `oldUid` again, because the rule check `assertRecoveredUser(newUid)` requires the *new* uid to be the signed-in caller, and the intent doc is keyed on the *old* uid. The retry path is theoretically possible (the new uid can call again with the same `oldUid` + secret) — but in `auth_recovery_service.dart` the client wrapper [discards `groupsFailed`](functions/test/callables/cleanupAnonUidArtifacts.test.ts:558) and reports success to the user. So in practice: stale `oldUid` strings remain pinned across every "failed" group's expenses, settlements, member docs, and activity logs — *forever*. Order should be: cascade to completion → delete intent → delete auth user. Auth deletion is the last irreversible action, not the middle one.

### 3. `cleanupAnonUidArtifacts` secret comparison is not constant-time

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:331`
- **Principle**: Trust boundary violation — timing-side-channel on bearer secret
- **What it says**:
  ```ts
  if (data.secret !== cleanupSecret) {
    throw cleanupIntentError();
  }
  ```
- **Why it bites**: The cleanup intent secret is a 32-byte bearer token that authorizes the callable to *rewrite every UID reference of `oldUid` to the caller's uid* — essentially "claim another anon account's data." Comparing it with `!==` is a string-equality short-circuit; in v8/Node, equal-prefix comparisons take longer than mismatched-prefix comparisons. A remote attacker who knows an `oldUid` (these are not secret — they leak through expense `createdBy` and activity logs that other group members can read) can repeatedly call the callable from their own auth context and statistically narrow the secret. There is no rate limit on `cleanupAnonUidArtifacts` either (unlike `joinGroupByInviteCode` which has the `joinAttempts/<uid>` lock), so an attacker gets unbounded attempts. Either use `crypto.timingSafeEqual` *and* add a per-(newUid, oldUid) attempt limiter, or store a SHA-256 hash of the secret in the intent doc and compare hashes (hash comparison is constant-time-ish because both inputs are fixed length and the attacker controls neither).

## HIGH (6)

### 1. `deleteAccount` loads every event-and-subcollection serially; will time out on real groups

- **Location**: `functions/src/callables/deleteAccount.ts:382-459`
- **Principle**: Unbounded resource use / timeout cascade
- **What it says**:
  ```ts
  const eventsSnap = await groupRef.collection('events').get();
  for (const eventDoc of eventsSnap.docs) {
    // ...
    const expensesSnap = await eventDoc.ref.collection('expenses').get();
    for (const expenseDoc of expensesSnap.docs) { ... }
    settlementsScrubbed += await processSettlementsCollection(...);
    const eventActivitySnap = await eventDoc.ref.collection('activity_logs').get();
    for (const activityDoc of eventActivitySnap.docs) { ... }
  }
  ```
- **Why it bites**: Per group, this is a serial walk: `events.get()` → for each event `expenses.get()` then `settlements.get()` then `activity_logs.get()`. A user in 5 groups with 20 events each = 5 × (1 events get + 20 × 3 subcollection gets) = 305 sequential Firestore reads before the first write commits. With Firestore admin SDK p99 read latency around 80–120ms when not warmed up, that's 25–35 seconds just for reads — and the v2 callable default timeout is 60s. There is no `timeoutSeconds` option set in `setGlobalOptions`. The comment at the top of the file already acknowledges this ("Future upload flows should add receipt Storage object deletion or a resumable cleanup job here") — but the cleanup job is needed *now*, not for future uploads. This is a `deadline-exceeded` waiting for the first user with a healthy group history.

### 2. `cleanupAnonUidArtifacts` parallel snapshot fetch will OOM the function on large groups

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:369-392`
- **Principle**: Unbounded resource use — `Promise.all` over collection reads with no concurrency limit
- **What it says**:
  ```ts
  const eventCascades = await Promise.all(eventsSnap.docs.map(async (eventSnap) => {
    // ...
    const [expensesSnap, settlementsSnap, activityLogsSnap] = await Promise.all([
      eventSnap.ref.collection('expenses').get(),
      eventSnap.ref.collection('settlements').get(),
      eventSnap.ref.collection('activity_logs').get(),
    ]);
    return { eventSnap, eventData, participantIds, participantNames,
             expensesSnap, settlementsSnap, activityLogsSnap };
  }));
  ```
- **Why it bites**: This is one `Promise.all` of N events, each spawning a `Promise.all` of 3 subcollection `get()`s. For a group with 50 events × ~30 expenses + 5 settlements + 20 activity logs, you're holding 50 × 55 ≈ 2,750 DocumentSnapshot objects in JS heap *simultaneously* before any cascade writes start, on a 256MB v2 function default. There's no batching, no streaming, no `.stream()` usage. The test `large groups migrate without a single transaction write ceiling` (line 467) presumably exercises the batch writer with synthetic data — it doesn't measure heap. First production cleanup of an active user kicks off and OOMs the function; the cleanup intent stays, the next retry OOMs again. The function fails to converge.

### 3. `deleteAccount` Auth deletion failure leaves user in a poisoned state

- **Location**: `functions/src/callables/deleteAccount.ts:529-547`
- **Principle**: Partial write across stores — error swallowing combined with irreversibility
- **What it says**:
  ```ts
  try {
    await getAuth().deleteUser(uid);
    output.authUserDeleted = true;
  } catch (error) {
    if ((error as { code?: unknown }).code === 'auth/user-not-found') {
      output.authUserDeleted = false;
    } else {
      logger.error('deleteAccount auth delete failed after cascade', { ... });
      throw new HttpsError('internal',
        'Account data was scrubbed, but the Auth user could not be deleted.',
        output);
    }
  }
  ```
- **Why it bites**: At this point in execution, the Firestore cascade has already happened — every group's `memberIds` has the user's uid replaced with a tombstone, every expense has `createdBy = 'deleted-user'`, etc. If `deleteUser` then fails (rare, but: GCP outage, IAM hiccup, rate limit), the user's auth identity is still valid. They can sign in. They can call `deleteAccount` again, but on the second call `groupsSnap` returns *zero groups* (their uid is no longer in any `memberIds`), so the cascade is a no-op — `processGroup`'s membership check would not fire because the user isn't in any group. The user now sees an authenticated-but-data-less account they cannot delete via the normal flow. The cascade should *first* delete the auth user, *then* do Firestore work — or, better, mark the auth user disabled at the start as a kill-switch, then cascade, then delete-auth as the final step.

### 4. `cleanupAnonUidArtifacts` is not idempotent across the auth-delete boundary

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:553-587`
- **Principle**: Idempotency / at-least-once
- **What it says**:
  ```ts
  let authUserDeleted = false;
  try {
    await getAuth().deleteUser(oldUid);
    authUserDeleted = true;
  } catch (error) {
    if ((error as { code?: unknown }).code !== 'auth/user-not-found') {
      throw error;                                  // re-thrown, no retry handling
    }
  }
  ```
- **Why it bites**: Cloud Functions callables are at-least-once on certain network failure paths (especially with App Check token retries). If `processGroup` succeeded for all groups, `deleteUser` succeeded, the FCM/joinAttempts deletes succeeded, the intent deleted — but the *response* never reached the client (network drop), the client will see a failure and the next call from the new uid will retry. On the retry, `assertRecoveredUser(newUid)` still passes, `assertCleanupIntent` *fails* because the intent doc was deleted, and the callable returns `permission-denied` "Invalid cleanup intent." The client sees an error on a successful cleanup, prompts the user to retry, and the retry never works. Either persist a `completedAt` tombstone for completed intents and return success on re-presentation of a valid (completed) one, or surface this in the client wrapper. Right now, the client wrapper [intentionally discards the response](functions/test/callables/cleanupAnonUidArtifacts.test.ts) and treats failure as success — which masks the bug but leaves the user without confirmation.

### 5. `cleanupAnonUidArtifacts` has no rate limit; bearer-secret bruteforce gets unbounded attempts

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:502-520`
- **Principle**: Trust boundary violation — rate limit asymmetry
- **What it says**:
  ```ts
  export const cleanupAnonUidArtifacts = onCall<...>(
    { enforceAppCheck: true },
    async (request: CallableRequest<...>) => {
      // ... no joinAttempts-style lock
      await assertRecoveredUser(newUid);
      const cleanupIntentRef = await assertCleanupIntent(oldUid, cleanupSecret);
  ```
- **Why it bites**: `joinGroupByInviteCode` correctly throttles to 5 attempts/hour via `joinAttempts/{uid}`. `cleanupAnonUidArtifacts` has no equivalent — App Check rate-limits per app instance but not per caller-target tuple. An attacker who knows an `oldUid` (these are readable to any group member via `createdBy`, `actorId`, etc.) can call this callable as their own authenticated email user, with any guess at `cleanupSecret`, repeatedly. Combined with issue CRITICAL-3 (non-constant-time compare), this is the full timing-attack setup. Even ignoring timing: 15 minutes × no rate limit × App Check tokens minted per device = many thousands of guesses. The secret is 32 bytes so a blind brute-force is infeasible, but the side-channel makes it dramatically more feasible than the keyspace would imply. Add `cleanupAttempts/{newUid}` mirroring `joinAttempts/{uid}`.

### 6. `deleteAccount` orphan-group decision is made before subcollection cascade runs

- **Location**: `functions/src/callables/deleteAccount.ts:350-376`
- **Principle**: Broken invariant — `groupOrphanedAndSoftDeleted` reflects pre-cascade state
- **What it says**:
  ```ts
  const remainingRealCreator = oldestRealMemberUid(members, uid);
  const hasRealSurvivor = remainingRealCreator != null;
  // ...
  if (!hasRealSurvivor) {
    groupUpdate.createdBy = deletedUserSentinel;
    groupUpdate.isDeleted = true;
    groupUpdate.deletedAt = FieldValue.serverTimestamp();
  }
  ```
- **Why it bites**: `oldestRealMemberUid` filters out the deleted user, tombstones, and `isDeleted == true` members — fine. But the soft-delete decision happens before any expenses or settlements are looked at. A group with one human member (the one deleting) and three shadow members carrying real settlements is now marked `isDeleted: true` even though it carries ledger facts other parties might query (e.g., audit). More importantly, the rule on `groups/{groupId}` permits reads only to members of `memberIds`; once the deleting user is tombstoned and the group is `isDeleted`, *no human* can read or restore that group's ledger. If the deletion later partially fails (issue HIGH-3) and the user re-authenticates, they can't get back into the group because they're not in `memberIds` anymore. Soft-deletion of group records should be a separate, observable step gated on "are there any real un-tombstoned members" *after* the membership rewrite, not before.

## MEDIUM (8 shown of 8)

### 1. `BatchWriter` is duplicated verbatim across two callables

- **Location**: `functions/src/callables/deleteAccount.ts:44-80` and `functions/src/callables/cleanupAnonUidArtifacts.ts:33-69`
- **Principle**: Coupling vs cohesion — copy-paste of a load-bearing utility
- **Why it bites**: Two identical 35-line `BatchWriter` classes with the same `batchLimit = 450`. When the limit needs to change (e.g., to 400 because of indexed-write inflation), or the batch needs to learn to retry on `aborted`, one of these will be updated and the other won't. Pull this into `functions/src/util/batch-writer.ts` and import from both.

### 2. `processSettlementsCollection` exists only in `deleteAccount`; cleanup callable inlines the same pattern

- **Location**: `functions/src/callables/deleteAccount.ts:304-320` vs `cleanupAnonUidArtifacts.ts:482-488`
- **Principle**: Wrong abstraction — same loop, two shapes
- **Why it bites**: `deleteAccount` wraps the settlement scrub into a helper that returns a count; `cleanupAnonUidArtifacts` inlines it inside `processGroup` with an `actions: string[]` log. The two diverge in the future when one gets a fix (e.g., handling the new `splitDistribution` field on settlements) and the other doesn't. Pick one shape.

### 3. `assertCleanupIntent` reads-then-deletes outside a transaction — TOCTOU window

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:319-342` (read) and `:586` (delete)
- **Principle**: Race condition / TOCTOU
- **Why it bites**: The intent is read at the start of the callable, the entire group cascade runs (potentially tens of seconds), and the intent is deleted at the end if `groupsFailed.length === 0`. If two concurrent invocations of the callable happen with the same `oldUid` + `cleanupSecret` (legal: same client retries, or attacker replay), both pass `assertCleanupIntent`, both run the cascade, both delete the intent (second is a no-op). Wasteful and possibly write-conflicts. Reads/deletes of one-time tokens belong in a transaction: read + verify + mark-consumed atomically.

### 4. `replaceUid` silently dedupes — possibly desired but it changes semantics on collision

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:114-123` and `deleteAccount.ts:114-126`
- **Principle**: Hidden mutation / principle of least astonishment
- **Why it bites**: When `newUid` is already in `memberIds` (e.g., a recovery where the user joined the group from both anon and email accounts), `replaceUid([oldUid, newUid], oldUid, newUid)` returns `[newUid]` — fine. But the same helper is used for `participantIds` on events, `customSplitParticipants` on expenses, etc. Silently changing array length on `customSplitParticipants` can shift split-distribution semantics if downstream code assumes `customSplitParticipants.length === Object.keys(splitDistribution).length`. The dedupe is correct in spirit but the helper name doesn't telegraph it. Either rename to `replaceUidUnique` or split into `replaceUid` (positional) and `dedupe` (separate step).

### 5. `generateTombstoneId` uses `Math.random` instead of `crypto.randomUUID`

- **Location**: `functions/src/callables/deleteAccount.ts:90-95`
- **Principle**: Naming that misleads / weak entropy in identity-bearing field
- **Why it bites**: 36⁸ ≈ 2.8e12 keyspace, but `Math.random` collisions are not actually uniform across that space — V8's xorshift128+ has known bias patterns, and the `while (memberIds.includes(tombstoneId))` loop guards only against the *current* group's existing tombstones, not against other groups or future tombstones. This is identity for a row that will persist forever. Use `crypto.randomUUID()` or `crypto.randomBytes(6).toString('hex')` — same cost, real entropy, and you can drop the in-loop collision check.

### 6. `rewriteString(value, originalName)` does `value.split(originalName).join(deletedMemberName)` — no boundary check

- **Location**: `functions/src/callables/deleteAccount.ts:128-133`
- **Principle**: Trust boundary violation — naive substring replacement on user content
- **Why it bites**: If `originalName = "Al"`, every activity log description containing the substring "Al" anywhere — "Alex paid for tea", "Halal restaurant" — gets mutilated into "Deleted member" mid-token. Single-character or short display names will scramble logs across the group. At minimum guard against `originalName.length < 3` or wrap the replacement in word boundaries. The PII concern is "remove the name from logs"; the substring nuke is over-eager and silently corrupts data adjacent users will still read.

### 7. `groupsFailed` is reported but the client wrapper discards it

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:20-26` (the field) and `lib/core/services/firebase_functions_service.dart:68` (the wrapper)
- **Principle**: Observability — partial-failure signal exists at the wire but is dropped on the client
- **Why it bites**: The Cloud Function does the right thing — collects per-group failures, returns them, keeps the intent doc alive. The Dart wrapper [doesn't surface `groupsFailed`](functions/test/callables/cleanupAnonUidArtifacts.test.ts:558) to the caller. The user sees success even when 3 of 8 groups failed. This is a server-side observability win the client wrapper cancels out. Either drop the field from the response (and own that fact in the rules/recovery design) or expose it.

### 8. `assertRecoveredUser` swallows the underlying auth error

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:295-313`
- **Principle**: Error context stripped before bubbling
- **Why it bites**:
  ```ts
  } catch (error) {
    if (error instanceof HttpsError) throw error;
    throw new HttpsError('failed-precondition',
      'Recovered user must exist before cleanup.');
  }
  ```
  Any non-`HttpsError` from `getAuth().getUser()` (network timeout to Identity Platform, IAM perms, transient 5xx) is rewritten as `failed-precondition` "Recovered user must exist." On-call sees "user doesn't exist" in logs when the real cause is a GCP Auth outage; they spend an hour checking the user account that's perfectly fine. Log the original error before rewriting the message.

## NITPICK (4)

### 1. `Timestamp.now().toMillis() - createdAt.toMillis() > cleanupIntentMaxAgeMs` — clock-skew dependency

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:335-338`
- **Principle**: Hidden coupling to time
- **Why it bites**: `createdAt` is a server timestamp written by the *client's* nearest Firestore frontend; the `Timestamp.now()` in the callable is the *function's* clock. In normal operation these are within milliseconds, but the comparison treats them as the same source. A 1s skew won't matter on a 15-minute window, but the dependency is undocumented.

### 2. `assertNoInput` accepts `null`, `undefined`, AND `{}` — three names for the same intent

- **Location**: `functions/src/callables/deleteAccount.ts:82-88`
- **Principle**: Principle of least astonishment
- **Why it bites**: The callable client SDK may send `{}` or omit data entirely depending on platform; the function accommodates all three. Fine, but a one-line comment explaining why three branches exist would save the next reader 60 seconds.

### 3. `actions: string[]` log accumulator is high-cardinality at info level

- **Location**: `functions/src/callables/cleanupAnonUidArtifacts.ts:535-541`
- **Principle**: Silent log levels / log cardinality
- **Why it bites**: For each cascaded group, the log includes `actions` like `expenses.<eventId>.<expenseId>`, one per touched doc. A user with a long history floods Cloud Logging with thousands of unique-string entries per cleanup. Either move the per-doc actions to DEBUG and keep a summary count at INFO, or roll them up into a small JSON object before logging.

### 4. `firebase-admin: ^13.8.0` and `firebase-functions: ^7.2.5` use caret ranges

- **Location**: `functions/package.json:18-19`
- **Principle**: Unpinned / floating dep
- **Why it bites**: Both are load-bearing SDKs with active minor releases that have shipped breaking changes within majors historically. With `^`, a re-`npm install` six months from now may pull a 13.20.x that subtly changes batch-commit semantics. Either pin exactly (no caret) or commit a frozen lockfile and run CI with `npm ci`. The repo has a `package-lock.json` (implied by `overrides`) but no visible CI policy enforcing `--frozen-lockfile`.

## NOT RAISED (good calls)

- `functions/src/callables/joinGroupByInviteCode.ts:147-189` — `recordFailedJoinAttempt` correctly resets the counter outside the window and locks at the threshold inside a single transaction; the rate-limit semantics survive concurrent failures cleanly. This is the right shape for a per-uid limiter, and it's a useful model for the issue I raised under HIGH-5.
- `functions/src/callables/joinGroupByInviteCode.ts:113-119` — `isLookupFailure(error)` distinguishes "user mistyped the code" from "the function itself crashed" so only the former increments the lockout. Quietly correct.
- `functions/src/callables/cleanupAnonUidArtifacts.ts:295-313` — requiring the recovered user to have an `emailLink`/`password` provider before letting them claim another uid's data is the right second factor on top of the cleanup secret.

## Suggested next move

Triage in this order. First, fix CRITICAL-3 (constant-time secret compare + per-(newUid, oldUid) rate limit — pattern already exists in `joinGroupByInviteCode`) because it's an active credential exposure. Then fix CRITICAL-2 by re-ordering the cleanup pipeline: cascade → mark intent consumed (don't delete; flip a flag) → auth-delete as the *last* step. Both of those are line-level fixes that close attack surface without re-architecting.

Then stop and re-plan CRITICAL-1, HIGH-1, and HIGH-2 together — they share the same root cause, which is *"the callable IS the job."* The callable should kick off a job and return job-id; a separate scheduler (or a callable that resumes on re-invocation by checkpoint) does the actual cascade. Until that exists, every additional event/group/expense added to the live data set narrows the window before these functions start timing out and OOM-ing in production. The team comment at `deleteAccount.ts:15-17` already names this — promote it from "future" to "now."

The MEDIUMs are mostly de-duplication and observability; do them while reading the relevant callable, not as a sweep.
