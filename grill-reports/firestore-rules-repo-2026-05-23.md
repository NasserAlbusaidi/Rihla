## Verdict

The rules file is doing a lot of work — strict key whitelists, schema validation, immutable `createdBy`, append-only settlements — and most of it lands. The failure mode is on the **boundary between the rules and the Dart write paths**: the service layer assumes the rules will save it, the rules assume the service layer will respect contracts, and the two are out of sync in ways that will manifest as opaque `permission-denied` errors on a paid user's device, not as test failures. The dominant pattern is **trust-boundary drift** — the client validator, the rule validator, and the data the service actually sends are three different specifications of the same field. Fix the CRITICALs before launch; the rest is "fix and ship" territory.

## CRITICAL (2)

### 1. Soft-deleted-participant lockout: events become permanently uneditable once any participant leaves the group

- **Location**: `security/firestore.rules:281-300` (`validEventBase`), invoked from `validEventUpdateCommon` at `:328-334`, ultimately gating `:381` `allow update`.
- **Principle**: Broken invariant / trust boundary violation.
- **What it says**:
  ```javascript
  function validEventBase(data) {
    return isValidDisplayName(data.name)
      && ...
      && data.participantIds.hasOnly(groupMembers())   // <-- reads CURRENT group memberIds via get()
      && ...
  }
  function validEventUpdateCommon() {
    return ...
      && validEventBase(request.resource.data);        // <-- re-checks on EVERY update
  }
  ```
- **Why it bites**: `groupMembers()` reads `groupData(groupId).memberIds` at the moment of the update request, not at the moment of event creation. The instant anyone leaves the group (`validSelfLeave` at `:218`) or is removed (`validCreatorRemoveMember` at `:224`), any event that still lists them as a participant fails `participantIds.hasOnly(groupMembers())` on the next update — for everyone, forever. The user sees: rename the event, get `permission-denied`. No log, no signal, no path forward. They cannot even soft-delete the event (admin path runs through the same gate). The data is fine; the rules have constructed a state machine where membership churn turns events into read-only relics.
- **Related issues**: compounds with #2 below — the service's `FieldValue.serverTimestamp()` write masks this as "maybe the timestamp is the problem", making it harder to debug from the client.

### 2. `EventService.updateEvent` / `deleteEvent` / `addParticipant` rely on `FieldValue.serverTimestamp()` for `updatedAt`, which Firestore evaluates inconsistently inside rules and *will* surprise you

- **Location**: `lib/features/events/services/event_service.dart:101-104` (`deleteEvent`), `:125,131,133,175,205` (`updateEvent`, `addParticipant`, `removeParticipant`). Rule expects `data.updatedAt is timestamp` (`security/firestore.rules:298`) and `(data.deletedAt == null || data.deletedAt is timestamp)` (`:295`).
- **Principle**: Hidden coupling to time/env (rules evaluate `serverTimestamp()` differently than ordinary timestamp writes) + fail-silent (when this breaks, the client gets `permission-denied` with no schema diff).
- **What it says**:
  ```dart
  await db.collection('groups').doc(groupId).collection('events').doc(eventId)
      .update({
        'isDeleted': true,
        'deletedAt': FieldValue.serverTimestamp(),
        'updatedAt': FieldValue.serverTimestamp(),
      });
  ```
- **Why it bites**: There are two compounding issues. First: `validEventAdminUpdate` (`security/firestore.rules:372-377`) requires that `affectedKeys()` on a soft-delete is exactly `['isDeleted','deletedAt','updatedAt']`. If the document's existing `updatedAt` already equals what `serverTimestamp()` resolves to (millisecond-grained collision is unlikely but possible inside the same second on emulator/tests), `updatedAt` is *not* in `affectedKeys()` and the rule shape mismatches. Second and more important: the rest of the codebase writes `updatedAt`/`createdAt`/`settledAt`/`createdAt` as **ISO-8601 strings** (`expense_service.dart:137`, `settlement_service.dart:89`, `event_model.dart:178`). The `event_service.dart` is the **only** place that uses `serverTimestamp` for these fields, and `validEventBase` accepts `(data.createdAt is string || data.createdAt is timestamp)` — but `(data.updatedAt is timestamp)` is required (no string fallback). Drift between service files of the same project is a footgun; the rules cement it. The day someone copies the expense_service pattern into event_service, every event update breaks at the rule, not at the type system.
- **Related issues**: #1 (the lockout failure mode looks identical from the client — `permission-denied`).

## HIGH (5)

### 3. `isValidDisplayName` drift between Dart and Firestore rules — 33+ raw chars pass client validation, fail at the server

- **Location**: `lib/core/utils/name_validators.dart:36-52` (`displayNameValidationError`) vs `security/firestore.rules:24-31` (`isValidDisplayName`).
- **Principle**: Trust boundary violation; the comment at `name_validators.dart:3` *promises* the two are in sync. Comments that lie.
- **What it says**:
  ```dart
  // Dart side
  if (trimmed.length > kDisplayNameMaxLength) {                // checks TRIMMED length
    return DisplayNameValidationError.tooLong;
  }
  ```
  ```javascript
  // Rule side
  s.size() >= 1 && s.size() <= 32                              // checks RAW length
    && s.trim().size() >= 1
  ```
- **Why it bites**: A user types `"Alice"` then accidentally pads with 30 trailing spaces (mobile keyboard space-bar repeat, copy-paste from another app, an autocomplete suggestion that appends whitespace). Trimmed length = 5; raw length = 35. Dart `validateDisplayName` returns `null` (valid). The write hits Firestore. The rule rejects (`s.size() <= 32` fails). The user sees `permission-denied` on group creation / member rename / event creation. Three places this lights up: `group_provider.dart:107-108` (`createGroup`), `:283-291` (`updateMemberDisplayName`), and any caller of `event_service.dart:46-66` that takes user-typed text. The Dart layer also has `normalizeDisplayName` at `name_validators.dart:73-75` that trims+collapses whitespace, but it's not called by `validateDisplayName` and not enforced anywhere in the write path I could find. The comment "Mirrors the server-side rules check" is a lie.
- **Related issues**: #4 (same drift class, different field).

### 4. `displayNameMapValuesAreValid` does not enforce the `(former member)` reserved-wording check on map entries

- **Location**: `security/firestore.rules:39-46`.
- **Principle**: Broken invariant — the single-string form (`isValidDisplayName`, `:24-31`) rejects `.* \(former member\)$`, but the map-values form does not apply the same check to each value identically.
- **What it says**:
  ```javascript
  function displayNameMapValuesAreValid(names) {
    return names is map && names.size() > 0
      && names.values().join('').matches('^[^\\x00-\\x1f\\x7f]+$')
      && names.values().join('\n').matches('^[^\\n]{1,32}(\\n[^\\n]{1,32})*$')
      && names.values().join('\n').matches('^[^\\n]*[^\\n ][^\\n]*(\\n[^\\n]*[^\\n ][^\\n]*)*$')
      && !names.values().join('\n').matches('(^|.*\\n)[^\\n]* \\(former member\\)(\\n.*|$)');
  }
  ```
- **Why it bites**: The reserved-suffix block *is* present (last clause), but the regex relies on `\n`-separated joining to delimit entries. If a value itself contains a *real* newline, that would be filtered earlier by the control-char check (`\x00-\x1f` includes `\n` at `\x0a`), so the delimiter is safe — BUT the rule on `participantNames` accepts up to 32 chars per value, and the reserved-wording check is applied as a post-hoc regex against the joined string. The match is per-entry only because each entry is bounded by `\n`. This works *as long as* no participant name ends in exactly ` (former member)`. The deeper bite: the `isValidDisplayName` for individual fields *also* checks the same suffix at `:30`. Why is this check duplicated, by hand, in two slightly different regex dialects? It's drift waiting to happen. The next time someone updates the reserved-wording list (add ` (banned)`, ` (suspended)`), they'll update one and not the other. Pull this into a shared helper or accept that it'll desync. Also: an empty-string map value (`""`) — does the second regex `[^\\n]{1,32}` reject it? `{1,32}` requires ≥1 non-newline char per entry, so `""` joined as `"foo\n\nbar"` → `[^\\n]{1,32}` doesn't match the empty middle segment → rejected. OK. But this is fragile reasoning to ship to prod.
- **Related issues**: #3 (display-name validation drift).

### 5. Currency dropped from settlement cache and partially decoded with hardcoded `'OMR'` in expense cache — a write-path correctness failure for non-OMR groups

- **Location**: `lib/core/services/cache/settlement_cache_repository.dart:42-58` (no currency column written); `lib/core/services/cache/expense_cache_repository.dart:152-162` (`_decodeSplitValue` hardcodes `'OMR'`).
- **Principle**: Naming that misleads — `cacheSettlements` claims to cache the settlement, but loses a field that affects how the amount is interpreted. Wrong abstraction — the cache stores `Decimal` text and a split distribution, but split decoding requires the currency, which the cache no longer carries.
- **What it says**:
  ```dart
  // settlement_cache_repository.dart — no currency column
  batch.insert('settlements', {
    'id': s.id, 'trip_id': s.tripId,
    'payer_participant_id': ..., 'recipient_participant_id': ...,
    'amount': s.amount.toString(),
    'note': s.note, 'created_at': ..., ...
  }, ...);
  ```
  ```dart
  // expense_cache_repository.dart
  Decimal _decodeSplitValue(Object? value, SplitMode mode) {
    final persistedValue = _persistedInt(value);
    return switch (mode) {
      SplitMode.exact => MoneySerializer.fromSubunits(persistedValue, 'OMR'),    // <-- hardcoded
      ...
    };
  }
  ```
- **Why it bites**: A user in a JPY group (no subunits — `MoneySerializer` scale is 1) creates an exact-split expense. The Firestore write is correct (currency='JPY', amountFils stored at scale 1). The cache write succeeds. The cache *read* path runs `_decodeSplitValue` with hardcoded `'OMR'`, which has scale 1000 — every exact-split amount comes out 1000× too small. The user sees their balance briefly correct (Firestore snapshot), then wrong (cache replays), then correct again (next snapshot). Memory observation 14667 already flagged this for settlements. The CLAUDE.md says "JPY=1 (easy to forget)" — it is, and you forgot it here. The cache is supposed to be a transparent read-cache, not a money mangler.
- **Related issues**: none directly, but compounds with the cache layer's delete-all-then-batch-insert pattern (#6) — every snapshot replays this through the lossy decoder.

### 6. `actorName` non-null contract violated by `logGroupEvent` callers — fire-and-forget write swallows the rule rejection

- **Location**: `lib/features/groups/services/group_activity_service.dart:103-127` (`logGroupEvent` requires non-null `String actorName`); rule at `security/firestore.rules:643-666` requires `isValidDisplayName(request.resource.data.actorName)` — non-null AND 1–32 chars. Caller pattern at `lib/features/groups/screens/group_settle_up_screen.dart:325-332` resolves to `actorName` from `settingsProvider.deviceName`, falling back to `fromName`, neither of which is validated.
- **Principle**: Fail-silent (the `.catchError` at `group_activity_service.dart:125` swallows the rejection); trust boundary violation (no client-side validation of the same name the rule will reject).
- **What it says**:
  ```dart
  unawaited(
    _activityRef(groupId).doc(id).set({
      ...
      'actorName': actorName,
      ...
    }).catchError((Object e) {
      if (kDebugMode) debugPrint('[GroupActivity] log failed: $e');
    }),
  );
  ```
- **Why it bites**: A user with `deviceName == ''` (never set — `settingsProvider.deviceName` is empty by default until onboarding writes it) hits the settle-up flow. The `actorName` resolved fallback is `fromName`, which can also be empty (e.g., a member that exists in the group with no display name). The fire-and-forget write goes out with `actorName: ""`. The rule rejects (size < 1). `catchError` eats the error in release builds (`kDebugMode` is `false`). Result: settle-up succeeds, group activity log silently misses the settlement entry. The user thinks the activity feed is broken; the team can't even grep for the error because it never reached Sentry. This is the activity log's whole job, and it's quietly broken on a class of users.
- **Related issues**: #3 (the same name validation drift makes this manifest more often).

## MEDIUM (4)

### 8. `validCurrency` accepts any 3-char string — a group in OMR can have a JPY expense written by any peer

- **Location**: `security/firestore.rules:48-50`.
- **Principle**: Trust boundary violation (validation is a shape check, not a domain check) + premature trust (CLAUDE.md enumerates a fixed currency list — OMR/USD/EUR/GBP/SAR/AED/QAR/KWD/BHD/JPY — the rules don't enforce it).
- **Why it bites**: A peer creates an expense with `currency: 'XYZ'` or `currency: 'JPY'` in a group whose `currency` is `'OMR'`. The expense passes `validExpenseBase`. The balance calculator now must either reject the expense at calculation time (which it does via `MoneySerializer.toSubunits` not knowing how to scale 'XYZ' → exception during balance calc) or compute mixed-currency balances (which CLAUDE.md says it doesn't do — there's no multi-currency conversion). Result: one corrupt expense from any group member can crash the balance calc for the entire group. Bounded blast radius (one group at a time), but trivial to trigger and trivial to prevent (`data.currency in ['OMR','USD',...]` in the rule).

### 9. `validEventLightUpdate` lets a participant add a `participantId` without adding the matching `participantNames` entry

- **Location**: `security/firestore.rules:336-354`.
- **Principle**: Broken invariant — `participantIds` and `participantNames` must be referentially complete, and the rule doesn't enforce that on light updates.
- **Why it bites**: The light-path additive update lets you push a new ID into `participantIds` without requiring a matching entry in `participantNames`. The UI then renders a participant with a blank/placeholder name across every screen that reads from `event.participantNames`. Not a security issue, but a UX cliff — and it sneaks past the test suite because every test probably calls `addParticipant` which sends both. The rule should require that `request.resource.data.participantNames.keys().hasAll(request.resource.data.participantIds)` (or the equivalent — every new participantId must have a name in the new map). Right now it only checks that you didn't *remove* or *change* existing entries.

### 10. `recoveryCleanupIntents.allow update` enables silent secret rotation by the retiring UID

- **Location**: `security/firestore.rules:152-165`.
- **Principle**: Idempotency / principle of least astonishment.
- **Why it bites**: The intent is a one-time bearer secret per spec, but the rule allows `create, update` from the same UID. If the auth recovery flow re-runs (user taps email link twice, hits the back button, race between two devices), `_cleanupIntentFactory` will overwrite the existing intent with a new secret. The first cleanup callable that ran with the old secret will now fail to consume it (or worse — the new secret leaks via whatever exposes intents to the callable). The spec calls these "one-time bearer secrets"; the rule says "rewritable as often as the same UID wants". Pick one. If rotation is desired, document it explicitly (and confirm the callable handles secret churn idempotently — observation 18363 already flagged async-unawaited cleanup with premature success signaling, so this isn't theoretical).

### 11. `expense_cache_repository.dart` and `settlement_cache_repository.dart` delete-all-then-batch-insert without a transaction — concurrent snapshot writes race

- **Location**: `lib/core/services/cache/expense_cache_repository.dart:37-68`, `lib/core/services/cache/settlement_cache_repository.dart:31-60`.
- **Principle**: Race condition (TOCTOU) — `db.delete` then `db.batch.commit` is two separate sqflite calls.
- **Why it bites**: Two Firestore snapshots arrive back-to-back (network catch-up after going online). `asyncMap` on the stream fires `cacheExpenses` twice. Snapshot A: `delete WHERE trip_id=e1`, then begins batch insert (rows A1, A2, A3). Snapshot B (interleaved on the same sqflite isolate, but `db.batch().commit()` is async — the Flutter event loop will interleave): `delete WHERE trip_id=e1` runs *between* A's delete and A's batch commit. Result: A's batch inserts rows that B's delete has already erased — except A's insert hasn't run yet, so B sees an empty set, deletes nothing, then B's batch inserts. Now A's batch runs and inserts duplicates (or, with `ConflictAlgorithm.replace`, overwrites with A's potentially-stale data). The dominant failure mode is "cache briefly shows old expenses A's snapshot already invalidated". Wrap the delete + batch in `db.transaction` and the race is gone. `noResult: true` doesn't help here — that's just a return-value optimization.

## NITPICK (4)

### 12. `requesterIsRecordCreator()` is named like a query, returns a bool, but reads from `resource.data` — works only on update/delete, silently false on `create`

- **Location**: `security/firestore.rules:101-103`.
- **Principle**: Principle of least astonishment. A function called `requesterIsRecordCreator` reads `resource.data.createdBy` — but `resource` is `null` on create, so this always returns false on create. The function is only meaningful on update/delete. Add a comment or rename `requesterIsExistingRecordCreator`.

### 13. `db.collection('groups').doc(groupId).collection('events').doc(eventId)` chain is duplicated across `EventService` despite the base class providing `eventSubcollection`

- **Location**: `lib/features/events/services/event_service.dart:70-75, 95-100, 141-146, 167-172, 197-202`.
- **Principle**: Leaky abstraction — `FirestoreRepository.eventSubcollection` exists to encapsulate this path, but `EventService` writes to the event *document* (not subcollections) and so reaches around the helper. The helper is incomplete: it returns subcollections but not the event doc itself. Either add `eventDoc(groupId, eventId)` to the base class or accept the duplication; either way, decide.

### 14. `_settlementsRef` / `_activityRef` are private helpers in `GroupSettlementService` / `GroupActivityService`, but `eventSubcollection` is the canonical name in the base class

- **Location**: `lib/features/groups/services/group_settlement_service.dart:28-29`, `lib/features/groups/services/group_activity_service.dart:33-34`.
- **Principle**: Inconsistent naming across the same architectural layer. If the base class is going to own subcollection access, it should own all subcollection accessors, not just event subcollections. Right now `groups/{gid}/settlements` and `groups/{gid}/activity` get bespoke helpers; `groups/{gid}/events/{eid}/expenses` gets the base class helper. Same problem, two patterns.

### 15. `eventId: groupId` sentinel in `addGroupSettlement` is exactly the kind of overload the rule has to know about — and does, brittlely

- **Location**: `lib/features/groups/services/group_settlement_service.dart:79` and `security/firestore.rules:689` (`data.eventId == groupId`).
- **Principle**: Magic numbers / strings (a sentinel value used as semantic carrier). The rule explicitly checks `data.eventId == groupId` for the group-settlement variant. This is fine but only because there is exactly one writer. The day someone adds a second group-scoped settlement-shaped collection, this sentinel breaks silently. Either give group settlements a typed `eventId: null` (and update the rule to `data.eventId == null || data.eventId == groupId`) or document the sentinel right next to the rule.

## Suggested next move

Triage #1 first — the participant-lockout bug is the kind of thing that surfaces a month after launch when a user finally leaves a group, and your only signal is a support ticket from someone else in the group. Fix the rule to read participantIds against the group's state *at event creation*, not at every update (or — better — relax `validEventBase` on updates so existing participants don't need to revalidate against current group memberIds). #2 is the next priority; rationalize all the timestamp writes to one format (ISO strings everywhere, or `Timestamp.fromDate` everywhere — your choice — but stop mixing). #3 and #6 are a single cleanup: make `displayNameValidationError` apply the rule's checks faithfully (raw length, not trimmed) and add the same validation at every `logGroupEvent` callsite. After that, the cache currency drift (#5) is the kind of footgun that the existing 80% coverage isn't catching — write a JPY/exact-split regression test and the rest follows. The dead-code function (#7) is a five-minute fix and a comment. Don't bundle.
