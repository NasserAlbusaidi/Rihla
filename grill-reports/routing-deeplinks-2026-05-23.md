## Verdict

The router itself is tidy — no `goNamed`, no `state.extra`, direct-entry guards consistently present. The rot is at the edges: two independent `app_links` subscriptions racing on cold start, an onboarding gate that exists in CLAUDE.md but not in the route tree, prefs poisoning on send-failure, and an orphaned-Firestore-doc path on recovery failure. This is "fix and ship" — not a rewrite — but the deep-link cold-start path is the highest-risk surface and has the least test coverage. Treat HIGH 1, 2, 4, 5, 6 as a single coupled story: the deep-link plumbing needs a single owner, not two parallel listeners with one dedupe set between them.

## HIGH (12)

### 1. Two independent `app_links` subscriptions process every inbound URI

- **Location**: `lib/core/services/deep_link_service.dart:25` and `lib/features/auth/providers/auth_email_link_bootstrap_provider.dart:232`
- **Principle**: Hidden coupling — two services subscribed to the same global stream with no shared dedupe, no priority order, no ownership.
- **What it says**:
  ```dart
  // deep_link_service.dart
  _subscription = _appLinks.uriLinkStream.listen(
    (uri) => _openJoinLink(router, uri), ...);

  // auth_email_link_bootstrap_provider.dart
  final subscription = appLinks.uriLinkStream.listen(
    (uri) => unawaited(handleUri(uri)), ...);
  ```
- **Why it bites**: Every emitted URI is dispatched twice — once to the join-link parser, once to the email-link parser. Each is filtered by its own predicate, so today most URIs only "match" in one place — but the moment a URL legitimately contains *both* a `code=` query and a Firebase `oobCode` query (or any future ambiguity), both handlers fire concurrently. `_openJoinLink` calls `router.go(...)` synchronously; `handleUri` shows a snackbar and mutates `pendingEmailLinkProvider`. The order is non-deterministic. Worse, there is no single source of truth for "what kind of link is this" — the email-link path is gated on `FirebaseConfig.auth.isSignInWithEmailLink(link)` which is a network-influenced predicate. If it returns true after `_openJoinLink` already moved the router, the user lands on `/join/...` and *then* gets a recovery snackbar from a totally different deep link.
- **Related issues**: HIGH 3 (no dedupe in DeepLinkService), HIGH 11 (https accepted with no host check)

### 2. Join-link cold start fires after the splash + home flash

- **Location**: `lib/main.dart:168-172`
- **Principle**: Race condition / TOCTOU — deep-link dispatch is gated on `_AuthGate` resolving and `SafarApp` mounting and a post-frame callback firing.
- **What it says**:
  ```dart
  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addPostFrameCallback((_) {
      if (!mounted) return;
      unawaited(DeepLinkService.instance.init(ref.read(routerProvider)));
    });
  }
  ```
- **Why it bites**: The OS launches the app via a `rihla.app/join/ABC123` intent. `_AuthGate` runs anon sign-in (multi-second on a cold-network device). `SafarApp` finally mounts. `addPostFrameCallback` queues. The first frame paints — user sees `/home`. Then the callback fires, `getInitialLink()` resolves, `router.go('/join/ABC123')` runs, screen jumps. On a flaky network where `ensureAnonymousSession` fails, `SafarApp` *never* mounts (retry screen is shown), `DeepLinkService.init` never runs, and the join link is silently lost — the OS only buffers `getInitialLink` once.
- **Related issues**: HIGH 8 (retry path loses the initial link permanently)

### 3. `DeepLinkService` has no per-URI dedupe; `authEmailLinkBootstrap` does

- **Location**: `lib/core/services/deep_link_service.dart:22-40` vs `lib/features/auth/providers/auth_email_link_bootstrap_provider.dart:108, 119`
- **Principle**: Principle of least astonishment — twin pipelines with twin behaviors.
- **What it says**:
  ```dart
  // deep_link_service.dart — no seenKeys
  _subscription = _appLinks.uriLinkStream.listen(
    (uri) => _openJoinLink(router, uri), ...);
  final initialLink = await _appLinks.getInitialLink();
  if (initialLink != null) {
    _openJoinLink(router, initialLink); // could fire same URI again
  }
  ```
- **Why it bites**: `app_links` is documented to emit the same URI through both `getInitialLink()` and `uriLinkStream` on the same cold start under some Android lifecycle paths — the email-link bootstrap has a `seenKeys` set with a comment naming this exact case. The join-link service does not. Symptom: a user opens a join link, lands on `/join/ABC123`, taps "Back to home", and the second emission of the same URI shoves them back to `/join/ABC123`. Looks like a bug in JoinGroupScreen; the bug is here.

### 4. The onboarding gate documented in CLAUDE.md does not exist in the router

- **Location**: `lib/core/router/app_router.dart:67-73`, `lib/main.dart` (no onboarding redirect), `OnboardingScreen` (no route entry in `app_router.dart`)
- **Principle**: Broken invariant — CLAUDE.md asserts "router hard-redirects all non-onboarding routes until complete", and that assertion is false.
- **What it says**:
  ```dart
  @visibleForTesting
  String? appRouteRedirect(String matchedLocation) {
    if (matchedLocation == AppRoutes.splash) {
      return AppRoutes.home;
    }
    return null;
  }
  ```
- **Why it bites**: `onboardingComplete` exists in `AppSettings`, `SettingsService` reads/writes it, `OnboardingScreen` exists at `lib/features/onboarding/screens/onboarding_screen.dart` — but no route declares it, no `redirect` callback consumes it. A first-launch user opening a `rihla.app/join/ABC123` link bypasses onboarding entirely. Either the doc is stale and onboarding has been demoted to home-screen empty state (in which case the contract is a lie and the next dev will trust it), or this is a regression. Either way, the load-bearing claim that "deep links cannot be blocked on first launch" coexists with the load-bearing claim that "router hard-redirects all non-onboarding routes" and *both cannot be true*.
- **Related issues**: doc/code drift; surface to CLAUDE.md hygiene section.

### 5. `linkEmailToCurrentUser` poisons prefs before the send call

- **Location**: `lib/features/auth/services/auth_recovery_service.dart:163-171`
- **Principle**: Partial write — prefs and Firebase Auth are independent stores; one is updated before the other, with no rollback.
- **What it says**:
  ```dart
  Future<void> linkEmailToCurrentUser(String email) async {
    await setPendingEmail(email);
    await _setInFlightOp(opLink);
    await _auth.sendSignInLinkToEmail(...); // may throw
    FirebaseConfig.log('Recovery: link email send queued (email redacted)');
  }
  ```
- **Why it bites**: User taps "Link my email" on poor connectivity. `setPendingEmail` succeeds. `_setInFlightOp` succeeds. `sendSignInLinkToEmail` throws `network-request-failed`. The screen surfaces "no connection" — fair. But prefs now hold a pending email + `inFlightOp=link` for an email that no link was ever sent for. The user closes the app, opens it later, and clicks a *legitimate* recovery link from a previous session — the bootstrap reads `inFlightOp=link` and runs `linkWithCredential` against the new email instead of `signInWithEmailLink`. Behavior diverges from intent. The fix is to clear-on-throw, or persist only after send succeeds. `sendRecoveryLink` has the same shape.
- **Related issues**: HIGH 6 (similar pattern with the cleanupIntents doc).

### 6. `completeRecovery` writes a `recoveryCleanupIntents` doc unconditionally; no rollback on failure

- **Location**: `lib/features/auth/services/auth_recovery_service.dart:242-308`
- **Principle**: Partial write across stores — Firestore intent doc is created before recovery; if recovery fails, the doc is orphaned with a usable secret.
- **What it says**:
  ```dart
  if (oldUid != null && oldUid.isNotEmpty) {
    try {
      cleanupSecret = await _cleanupIntentFactory(oldUid);
    } catch (...) { ... }
  }
  ...
  await _auth.signOut();
  final result = await _auth.signInWithEmailLink(...); // may throw
  ```
- **Why it bites**: The flow writes a doc with `{secret, createdAt}` to `recoveryCleanupIntents/{oldUid}` *before* signing out and attempting `signInWithEmailLink`. If the email-link sign-in fails (expired oobCode, network drop after signOut), the cleanup intent doc sits in Firestore against the *still-active* old UID. The user is now signed out (anon session minted by `_AuthGate` on next launch produces a *new* UID), but the intent doc points at the previous anon UID with a secret valid for triggering a destructive `cleanupAnonUidArtifacts` callable. No TTL on the doc is visible in this file. Whoever can read that doc (security rules permitting) can replay the cleanup against an account that the user did not, ultimately, recover. Also: between `signOut()` and the new sign-in, `authUserChangesProvider` fires with `null` then with a new UID — `uidChangeListenerProvider` may wipe the cache for an aborted recovery.

### 7. `uidChangeListener` captures `cacheWipeFn` at provider-creation time via `ref.read`

- **Location**: `lib/features/auth/services/uid_change_listener.dart:33`
- **Principle**: Hidden coupling to time / boot order — the listener locks in whatever `cacheWipeFnProvider` produced at first read.
- **What it says**:
  ```dart
  final uidChangeListenerProvider = Provider<void>((ref) {
    String? lastUid;
    var seenInitial = false;
    final wipe = ref.read(cacheWipeFnProvider);
    ref.listen<AsyncValue<firebase_auth.User?>>(...);
  });
  ```
- **Why it bites**: If a test overrides `cacheWipeFnProvider` *after* `appBootstrapProvider` has already been watched (which transitively reads `uidChangeListenerProvider`), the override is ignored — the listener still calls `LocalDatabase.wipeAndReinitialize`. This is brittle to provider override order and exactly the class of failure that produces test-flake reports two months from now. Use `ref.read(cacheWipeFnProvider)` *inside* the `ref.listen` callback, or `ref.watch` the provider at the top — either preserves the override.

### 8. The retry path in `_AuthGate` silently drops the cold-start deep link

- **Location**: `lib/main.dart:113-153`, in combination with `lib/main.dart:168-172`
- **Principle**: Fail-silent — the failure is observable in logs but produces a user-visible "where did my join link go?" with no recovery path.
- **What it says**:
  ```dart
  void _retry() {
    setState(() {
      _authFuture = FirebaseConfig.ensureAnonymousSession();
    });
  }
  ```
- **Why it bites**: Anon sign-in fails (e.g. App Check token rejected on first launch). User taps Retry. Sign-in succeeds. `SafarApp` mounts. `DeepLinkService.init` finally runs. `_appLinks.getInitialLink()` returns null because the OS only buffers the initial intent once — that initial value was *consumed by the OS* before init had a chance. The user opened the app via an invite link, sees `/home`, and has no idea why the link didn't work. Two telemetry levels (Sentry exception capture + the lost deep link) but no user-recoverable signal. Either init the deep-link service *before* `_AuthGate` (and queue the dispatch until auth resolves) or capture the initial URI in `main()` before `runApp`.
- **Related issues**: HIGH 2 (post-frame-callback timing).

### 9. `DeepLinkService` is a process-lifetime singleton with no test seam

- **Location**: `lib/core/services/deep_link_service.dart:7-18`
- **Principle**: Untestable design — `static final DeepLinkService instance = DeepLinkService._(AppLinks())` cannot be swapped.
- **What it says**:
  ```dart
  class DeepLinkService {
    DeepLinkService._(this._appLinks);
    static final DeepLinkService instance = DeepLinkService._(AppLinks());
  ```
- **Why it bites**: Widget tests cannot fake `AppLinks` — the singleton is instantiated at class load with the real package. The dedupe + lifecycle behavior of `DeepLinkService` is invisible to the test suite. Any regression in `parseJoinLink` (the only thing this file actually tests in unit form) will hit production without a coverage signal for the listener wiring. Inject `AppLinks` via a provider or constructor, or expose `DeepLinkService.forTesting(appLinks)`.

### 10. `pendingEmailLinkProvider` is set by the bootstrap but readable only from one screen

- **Location**: `lib/features/auth/providers/auth_email_link_bootstrap_provider.dart:21, 139` and `lib/features/auth/screens/recover_pending_screen.dart:132`
- **Principle**: Wrong abstraction — the producer is global, the consumer is local; the contract advertised in the comment is not honored anywhere most users will encounter it.
- **What it says**:
  ```dart
  /// UI in later phases reads this to surface a "Confirm your email" prompt.
  final pendingEmailLinkProvider = StateProvider<String?>((ref) => null);
  ```
- **Why it bites**: A "different-device" recovery case (user receives email link on a phone that never primed `pendingEmail`) sets this state from `handleUri` and surfaces a snackbar. The snackbar disappears in 4 seconds. The only consumer of `pendingEmailLinkProvider` is `RecoverPendingScreen` — which the user is *not on* because they never initiated recovery on this device. Net effect: the "later phases" prompt promised in the comment doesn't exist; the link is captured in provider state and never reaches a user-actionable surface. Either route to a global "confirm email" screen from the bootstrap, or delete the provider and stop pretending.

### 11. `_emailLinkFromUri` accepts any `https://` URI without host filtering

- **Location**: `lib/features/auth/providers/auth_email_link_bootstrap_provider.dart:32-46`
- **Principle**: Trust boundary violation — every inbound https deep link reaches Firebase SDK calls and provider-state mutation before any host/path check.
- **What it says**:
  ```dart
  if (scheme == 'https') {
    return uri.toString();
  }
  ```
- **Why it bites**: Not a credential-theft hole — Firebase verifies the `oobCode` server-side, and `EmailAuthProvider.credentialWithLink` requires a matching `pendingEmail`. But every https URI received via `app_links` (which is any registered domain — `rihla.app`, `rihla-safar.web.app`, plus anything else `AndroidManifest.xml` declares) is normalized, dedupe-keyed, logged with `redactForLogging`, and gated on a network-influenced `isSignInWithEmailLink` call. A third-party app firing a non-Firebase https link at the registered domain triggers a remote check and a log line per emission. The check should be: scheme=https AND host in `{...firebaseapp.com|web.app|<your-auth-domain>}` AND looks-like-email-auth-link, before anything else.

### 12. `completeRecovery` fires cleanup via `unawaited(...)` after returning the result

- **Location**: `lib/features/auth/services/auth_recovery_service.dart:277-307`
- **Principle**: Error swallowing / fail-silent — the cleanup is best-effort by design, but the Future's error handling is decorative.
- **What it says**:
  ```dart
  unawaited(
    _cleanupAnonUidArtifacts(oldUid: oldUid, cleanupSecret: cleanupSecret)
        .then((cleanupResult) { ... })
        .catchError((Object error, StackTrace stackTrace) { ... }),
  );
  ```
- **Why it bites**: The `Future` returned from `_cleanupAnonUidArtifacts` is detached. If the callable wrapper throws *synchronously* before returning a Future (cloud-functions misconfig, region mismatch, codegen drift), the throw escapes the `.catchError` chain — `.then` and `.catchError` are only invoked on Futures, not on synchronous throws inside the wrapper. The crash bubbles out of `unawaited` as an uncaught zone error. More routine case: a network failure logs a Sentry breadcrumb but `cleanupResult.hasGroupFailures` triggers a *warning* breadcrumb that no dashboard alarms on — the old anon UID's group docs linger in Firestore with no observable signal. Cleanup is fire-and-forget but the failure mode is silent enough to never get noticed.

### 2. `appRouteRedirect` is `@visibleForTesting` for a one-line redirect

- **Location**: `lib/core/router/app_router.dart:66-73`
- **Principle**: Premature abstraction — the helper exists to satisfy a test, not because it carries logic worth isolating.
- **Why it bites**: `appRouteRedirect` only maps `'/'` → `'/home'`. The function will either grow to hold the missing onboarding redirect (HIGH 4) or stay trivial forever. The `@visibleForTesting` annotation is a tell that someone wanted to write a unit test for `routerProvider` and couldn't, so the redirect callback was hoisted to be reachable. Test the router via `GoRouter.match` or `routerDelegate` directly.

### 3. Resend cooldown logic duplicated across two screens

- **Location**: `lib/features/auth/screens/link_email_sent_screen.dart:31-66` and `lib/features/auth/screens/recover_pending_screen.dart:30-69`
- **Principle**: Coupling vs cohesion — same 35-line Timer + `_remainingSeconds` + `_startCooldown` block in two places.
- **Why it bites**: Tomorrow someone changes the cooldown from 60s to 90s and updates one screen. The deliverability constraint cited in the comment applies to both — same Firebase quota — so the two values must agree. Extract to `_ResendCooldownController` or a `ChangeNotifier` reused by both.

### 4. `_back` duplication across auth screens

- **Location**: `lib/features/auth/screens/recover_screen.dart:107-122`, `lib/features/auth/screens/link_email_screen.dart:97-112`
- **Principle**: Principle of least astonishment — the canonical pattern from CLAUDE.md is `if (!context.canPop()) go('/home')`; these screens have their own bespoke variant with a `Navigator.maybeOf` fallback no other screen uses.
- **Why it bites**: Each direct-entry screen now has a slightly different recovery path. The `Navigator.maybeOf` fallback fires only if `GoRouter.maybeOf(context)` returned null — which means the screen is mounted outside a `MaterialApp.router`. In production that's never true. In tests, it varies. Either centralize as a shared helper or pick one pattern.

### 5. 16 copies of `pageBuilder: (context, state) => CustomTransitionPage(...)` boilerplate

- **Location**: `lib/core/router/app_router.dart:147-461`
- **Principle**: Coupling vs cohesion — every route declaration repeats 8 lines of `CustomTransitionPage` scaffolding.
- **Why it bites**: A future change to the transition (curve, duration, accessibility tweak) requires editing 16 sites. Extract a `_page(child, transition)` helper. Two routes already use special transitions (home fade, modal slide-up) — keep those bespoke; the other 14 default to `_sharedAxisTransition`.

### 6. `errorBuilder` leaks the matched location to the user

- **Location**: `lib/core/router/app_router.dart:464-468`
- **Principle**: Error context exposure — `errorPageNotFound(state.matchedLocation)` shows the raw path.
- **Why it bites**: User receives `Page not found: /group/abc/event/xyz/legacy-module` because someone shared a stale deep link. The path is debugging information; the user gets no recovery action. Show a "Take me home" button; log the actual path through Sentry.

### 7. `DeepLinkService._reportError` does not capture to Sentry

- **Location**: `lib/core/services/deep_link_service.dart:106-114`
- **Principle**: Metrics that won't fire on the actual failure mode — `FlutterError.reportError` surfaces red-screen in debug and an `onError` callback in release, but no Sentry breadcrumb or exception.
- **Why it bites**: Compare to `authEmailLinkBootstrap` which uses `FirebaseConfig.log(..., error: e, stackTrace: s)` and lands in Sentry. Deep-link stream errors are exactly the on-call signal you need at 3am when someone reports "join links stopped working" — make sure they show up.

### 8. `RecoverPendingScreen._initialUid` captures `null` if uid is still resolving

- **Location**: `lib/features/auth/screens/recover_pending_screen.dart:45, 117-126`
- **Principle**: Race condition — `_initialUid = ref.read(uidProvider)` runs in `initState`; `uidProvider` is `null` until `authUserChangesProvider` produces a value.
- **Why it bites**: If the user lands on this screen during the anon-session bootstrap (rare, but possible if a recovery link arrives during a cold start before the anon session resolved), `_initialUid` is captured as `null`. The first emission from `authUserChangesProvider` produces the new anon UID, the listener sees `next != _initialUid` (null vs new UID), declares recovery complete, snackbars "welcome back", and `go(home)` — without recovery actually happening. The dispatch is contingent on `_completed` which only flips on the listener; nothing guards against the null-initial case.

### 9. Outbound invite host disagrees with comment in `app_links.dart`

- **Location**: `lib/core/config/app_links.dart:7-14`
- **Principle**: Comments that lie — the comment says "legal/help pages live on the Firebase Hosting default domain until `rihla.app` is wired"; `inviteLinkHost = 'rihla-safar.web.app'`, but `DeepLinkService._universalJoinHosts` *does* include `rihla.app`.
- **Why it bites**: Outbound shares (QR + share sheet) hand out `https://rihla-safar.web.app/join/ABC123`. Inbound accepts `rihla.app/join/ABC123` (per `_universalJoinHosts`). On the day someone flips `inviteLinkHost` to `rihla.app`, nothing in this file references the deep-link allow-list — the join host can drift out of sync. Tie them together (export from one constant).

### 10. `EventType.fromString(state.pathParameters['type'] ?? 'custom')` silently coerces

- **Location**: `lib/core/router/app_router.dart:296-298`
- **Principle**: Fail-silent — invalid path param resolves to `custom` instead of `errorBuilder`.
- **Why it bites**: A stale deep link with `/group/g1/create-event/picnic` (after `picnic` is removed from EventType) silently lands on the create-custom-event flow. The user expected one thing and got another. Either validate-and-404 or surface the resolution decision to the user.

- `lib/main.dart:31-34` — `_useFirebaseEmulator` is private to `main.dart` and read once at app boot; the file-level const carries no value over a `final` inside `main()`. *Principle: scope creep.*

## NOT RAISED (good calls)

- `lib/features/auth/providers/auth_email_link_bootstrap_provider.dart:108-126` — the `seenKeys` dedupe set with `oobCode`-preferring key is the right shape; the comment naming the exact failure mode (`getInitialLink` + `uriLinkStream` double-emission) is the rare comment that earns its tokens.

## Suggested next move

Triage the deep-link cold-start path as a single coupled story: HIGH 1, 2, 3, 8, 9, 11 are all "two listeners, no single owner, no test seam, lost on retry, no host filter". Pull them into one mini-design: who owns `app_links`, where is the initial URI captured (before `runApp`, ideally), and how does it survive the auth-gate retry. Then HIGH 4 — reconcile the onboarding gate with CLAUDE.md (either implement the redirect or strike the line). HIGH 5, 6, 7, 12 are the recovery-service correctness cluster — order-of-writes, rollback on failure, override-survivable wiring. Feed the structural ones (HIGH 1, 4, the recovery service constructor) into `/grill-my-plan` before refactoring.
