Audit all 9 service files for error handling completeness at system boundaries per D-02.

**What constitutes a system boundary (D-02):**
- Firestore reads/writes: `.get()`, `.set()`, `.update()`, `.delete()`, `.add()`, `.snapshots()` (stream setup)
- Firebase Storage: `.putFile()`, `.getDownloadURL()`, `.delete()`, `.ref().listAll()`
- Firebase Auth: `FirebaseAuth.instance.currentUser` access, `signInAnonymously()`
- WriteBatch operations: `batch.commit()`

**Rules per D-02:**
- Verify existing try/catch blocks handle errors well (meaningful error message, not swallowed silently)
- Add try/catch where missing at system boundaries
- Do NOT wrap internal code that can't fail (pure computations, model construction)
- Leave read-path errors to Riverpod's AsyncValue.error where appropriate (stream providers already handle this)
- Fire-and-forget writes (like activity logging) should catch and debugPrint, not rethrow

**Audit checklist per service:**

1. **ExpenseService** — Check `addExpense`, `updateExpense`, `deleteExpense` for try-catch around Firestore `.set()/.update()/.delete()`. Stream setup in `watchExpenses` is handled by StreamProvider (no additional wrapping needed).

2. **SettlementService** — Check `recordSettlement`, `deleteSettlement` for try-catch. WriteBatch.commit() calls must be wrapped.

3. **GearService** — Check `addGearItem`, `togglePacked`, `deleteGearItem` for try-catch around Firestore writes.

4. **SubGroupService** — Check `createSubGroup`, `addMember`, `removeMember`, `deleteSubGroup` for try-catch.

5. **DocumentService** — Check `uploadDocument`, `deleteDocument` for try-catch around BOTH Firestore and Storage operations. Storage operations are especially error-prone (network, permissions, quota).

6. **MemoryService** — Check `uploadMemory`, `deleteMemory` for try-catch around Storage + Firestore operations.

7. **GroupSettlementService** — Check `recordGroupSettlement` for try-catch around WriteBatch.commit().

8. **GroupActivityService** — This is fire-and-forget (`logGroupEvent`). Verify it catches errors and uses debugPrint (not rethrow). If it already does, leave it.

9. **EventService** — Check `createEvent`, `updateEvent`, `deleteEvent` for try-catch. Event creation is complex (writes to multiple subcollections) — must be wrapped.

**For each missing try-catch, add this pattern:**
```dart
try {
  // existing Firestore/Storage/Auth operation
} on FirebaseException catch (e) {
  debugPrint('ServiceName.methodName failed: ${e.code} ${e.message}');
  rethrow; // Let the UI layer handle via AsyncValue.error or catch
}
```

For fire-and-forget operations (activity logging):
```dart
try {
  // operation
} catch (e) {
  debugPrint('ServiceName.methodName failed: $e');
  // Do not rethrow — fire-and-forget
}
```

**Do NOT add try-catch to:**
- Stream return statements (`return firestore.collection(...).snapshots().map(...)`) — these are handled by StreamProvider
- Pure model construction (`Expense.fromFirestore(data)`)
- Internal utility methods that don't touch external systems
