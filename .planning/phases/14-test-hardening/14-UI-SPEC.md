# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Phase Nature: Infrastructure-Only

Phase 14 produces zero user-visible UI changes. Its output is:

- New Dart files: `lib/core/keys/shared_keys.dart` and `lib/features/*/keys/*_keys.dart`
- Modified widget files: `key:` parameters added to existing widgets inside `build()` methods
- Modified test files: `find.byKey()` replaces structural `find.text()` / `find.byType()` calls
- Modified CI file: `.github/workflows/release_android.yml` gains a `find.text()` regression warning step

No screens are added. No layouts change. No colors, fonts, or spacing values change. This UI-SPEC documents the contract for code-level design artifacts only — the Key class API and the structural patterns that downstream visual phases depend on.

## Key Class Design Contract

This section documents the structural output of Phase 14. It is the primary deliverable of this UI-SPEC.

### Key Naming Convention (from D-01, D-02, D-03, D-04 in CONTEXT.md)

| Rule | Specification |
|------|---------------|
| File location — feature keys | `lib/features/{feature}/keys/{feature}_keys.dart` |
| File location — shared keys | `lib/core/keys/shared_keys.dart` |
| String pattern | `feature_widget_role` — all lowercase, underscores (e.g., `'ledger_expense_list'`) |
| Class declaration | `abstract final class {Feature}Keys { ... }` |
| Static key fields | `static const screen = Key('feature_screen');` |
| Parameterized keys | `static Key itemCard(String id) => Key('feature_item_card_$id');` — non-const factory method |

### Mandatory `.screen` Keys (D-10 — unconditional)

Every screen widget gets a `.screen` key placed on its root Scaffold (or root widget) inside `build()`. This is unconditional — even screens with zero current test coverage receive this key.

Pattern:
```dart
// static field in key class:
static const screen = Key('event_command_center_screen');

// applied in widget build():
return Scaffold(key: EventKeys.screen, ...);
```

### Structural vs Content Classification Rule (from D-05, D-06, D-07)

| Category | Assertion Type | Action |
|----------|---------------|--------|
| Module card presence/absence | `find.text('Ledger')` checking card exists | Convert to `find.byKey()` |
| Screen navigation confirmation | `find.text('New Group')` after Navigator.push | Convert to `find.byKey()` |
| Section header presence | `find.text('Members & Balances')` | Convert to `find.byKey()` |
| Tap target | `tester.tap(find.text('Create Group'))` | Convert to `find.byKey()` |
| Navigation bottom sheet | `find.text('Create a Group')` checking sheet opened | Convert to `find.byKey()` |
| Empty state widget presence | `find.text('No groups yet')` | Convert to `find.byKey()` |
| Formatted amounts | `find.text('25.500 OMR')` | Keep `find.text()` |
| User-supplied fixture data | `find.text('Desert Crew')`, `find.text('Alice')` | Keep `find.text()` |
| Validation error messages | `find.text("Group name can't be empty.")` | Keep `find.text()` |
| Computed summary text | `find.textContaining('2 expenses')` | Keep `find.text()` |
| Financial state labels | `find.text('YOU OWE')`, `find.text('All settled!')` | Keep `find.text()` |

### Anti-Patterns (from RESEARCH.md)

| Anti-Pattern | Correct Pattern |
|--------------|----------------|
| `const Key('event_card_${event.id}')` — interpolation in const | `static Key eventCard(String id) => Key('event_card_$id')` |
| Key on inner private widget `_CardBody` | Key on outermost public widget `SmartModuleCard` |
| Reusing same Key constant for two sibling widgets | Distinct constant per widget (`ledgerCard`, `gearCard`, not `moduleCard` twice) |
| Speculative keys for untested widgets | Only key widgets that tests reference (D-09), except screens (D-10) |
| Modifying constructor `super.key` parameter | Key goes on root widget inside `build()`, not constructor signature |

## Migration Execution Contract

### Commit Strategy (from D-11, D-12)

Each unit of work is one atomic commit containing:
1. New or updated key class file (`lib/features/*/keys/*.dart`)
2. Widget files with `key:` parameters added
3. Updated test file with `find.byKey()` replacing structural `find.text()`/`find.byType()` calls
4. Green `flutter test {test_file}` run confirmed before commit

Files with 4 or fewer calls sharing the same feature area may be grouped into one commit.

### Rename Resilience Verification (D-13)

After full migration, execute verification protocol:
1. Temporarily rename `'Ledger'` to `'Treasury'` in `lib/features/events/widgets/event_module_list.dart`
2. Run full suite: `flutter test`
3. Confirm: only `find.text('Ledger')` content assertions fail — zero `find.byKey()` failures
4. Revert the rename immediately — do not commit the temporary change
5. Record result as proof of success criterion 3

### CI Addition (D-14)

Add after the existing test step in `.github/workflows/release_android.yml`:

```yaml
- name: find.text() regression warning
  run: |
    BASELINE=83
    CURRENT=$(grep -rn "find\.text(" test/ | wc -l | tr -d ' ')
    if [ "$CURRENT" -gt "$BASELINE" ]; then
      echo "::warning::find.text() calls increased from $BASELINE to $CURRENT. New structural assertions should use find.byKey() instead."
    fi
    echo "find.text() calls: $CURRENT (baseline: $BASELINE)"
```

Baseline of 83 = estimated remaining content-only `find.text()` calls after migration. This number must be confirmed at migration completion and updated in the CI step before the phase closes.
