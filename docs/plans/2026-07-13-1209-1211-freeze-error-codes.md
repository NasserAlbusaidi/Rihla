# Spec C — #1209 + #1211: transient-freeze error codes honor the #1144 contract

Issues: #1209 (P2) + #1211 (P3) — one concern: callables surface TRANSIENT freezes with error codes the
client maps to terminal outcomes (settle-up snackbar / silent leave-success). Branch:
`fix/1209-1211-freeze-error-codes`. Commit body: `Closes #1209` AND `Closes #1211` (both lines).
Spec ships in PR as `docs/plans/2026-07-13-1209-1211-freeze-error-codes.md`.

## Contract (departureLock.ts:24-28, verified)

Lock contention / transient freeze → `aborted` (client: retry copy, no Sentry). `failed-precondition` is
reserved for real preconditions (unsettled balance, R1 universe-only). `not-found` means the group is
GONE (missing, soft-deleted, or being deleted) — the client treats it as "nothing to do, go home".

Flag classification — **scoped to leaveGroup/removeMember/departureLock ONLY** (Gate round-1 P1: it does
NOT apply to deleteGroup, see the guard box below):
- **Terminal (→ not-found)**: `isDeleted`, `deletingInProgress` (deletion in flight ends in the group
  being gone; a leaver can treat it as done). `deletingInProgress`→not-found is admittedly optimistic —
  a delete can fail and the group survive — but that is the PRE-EXISTING semantic on these callables,
  deliberately preserved; reclassifying it is out of scope (note in PR body).
- **Transient (→ aborted)**: `claimingInProgress`, `accountDeletionInProgress`, `departureInProgress`
  (each is a bounded operation after which the group lives on and the caller is still a member).

**deleteGroup GUARD BOX — do not "align" these two branches:** in `acquireDeleteGroupLock`,
`isDeleted` → returns `{alreadyDeleted: true}` — a SUCCESS response (deleteGroup.ts:~130-140, pinned by
deleteGroup.test.ts test 16 ~:978), and `deletingInProgress` → the concurrent-observer branch that
proceeds to finalize idempotently (deleteGroup.ts:151-160, pinned ~:1156). That is the #519/#529
idempotency contract. The ONLY deleteGroup changes in this PR are the two `failed-precondition →
aborted` throws listed in Sites.

## Verified defects (main @2ce0891c)

1. `functions/src/callables/deleteGroup.ts:161-167` (`acquireDeleteGroupLock`): the three transient flags
   throw `failed-precondition` — client `_executeDelete`
   (`lib/features/groups/widgets/group_danger_section.dart:333-336`) maps EVERY failed-precondition to
   "settle up before deleting" on a possibly fully-settled group. Sibling `finalizeGroupDeletion`
   (deleteGroup.ts:275-281) already throws `aborted` for the identical flags.
2. `deleteGroup.ts:349-357` malformed-lock path: throws `failed-precondition` ("Malformed delete lock was
   cleared. Retry group deletion.") — a retry instruction on a code the client renders as settle-up.
3. `functions/src/callables/leaveGroup.ts:86-93` and the in-tx re-check `:174-181`: transient flags throw
   `not-found` — client `_executeLeave` (group_danger_section.dart:245-248) maps not-found to
   `router.go('/home')` with NO message: user believes they left while still a member.
4. `functions/src/callables/shared/departureLock.ts:49-56` (`acquireDepartureLock`, shared by leaveGroup
   AND removeMember): same four-flag `not-found`, same misread. (departureInProgress contention at :57-62
   is already correctly `aborted`.)

## Fix — server (functions/)

At every site above, split by the classification: keep `not-found` for `isDeleted || deletingInProgress`;
throw `new HttpsError('aborted', 'Another operation is in progress. Try again.')` for
`claimingInProgress || accountDeletionInProgress` (and `departureInProgress` where checked —
deleteGroup.ts:164). Sites:

- deleteGroup.ts `acquireDeleteGroupLock` :161-167 → aborted (all three flags there are transient).
- deleteGroup.ts malformed-lock throw :353-356 → aborted (message unchanged).
- leaveGroup.ts pre-check :86-93 → split.
- leaveGroup.ts in-tx re-check :174-181 → split.
- departureLock.ts `acquireDepartureLock` :49-56 → split.
- removeMember.ts pre-check :~108-115 → split (builder re-verifies exact lines).
- removeMember.ts in-tx re-check :~207-213 → split.
- **Sweep**: grep the three files for any OTHER
  `claimingInProgress|accountDeletionInProgress|departureInProgress` throw sites beyond the seven above
  and align them; list sweep results in the PR body. Do NOT touch non-departure callables
  (join/addShadow/claim/correct*/recordSettlement quiesce behavior is a separate contract — out of
  scope), and do NOT touch deleteGroup's alreadyDeleted/observer branches (guard box).
- Update the departureLock.ts:24-28 contract comment to name the not-found-vs-aborted split explicitly.

## Fix — client

`group_danger_section.dart` `_executeDelete` catch: add an `aborted` branch BEFORE the
failed-precondition branch, mirroring `_executeLeave`'s (:269-276): show
`context.l10n.groupMembershipChangeInProgress` snackbar, NO Sentry, return. (Deliberate key reuse for a
delete action — the semantics are "another operation is in progress, try again", which is what the copy
says; a delete-specific string is ARB churn for no user value. Note the reuse in the PR body.)
`_executeLeave` and `group_members_section.dart` already have aborted branches — verify, don't
duplicate. After the server split, the existing client `not-found → /home` mappings become
semantically correct (group really gone) — leave them.

## Non-goals

- No change to the genuine failed-precondition throws (unsettled balance, R1 universe-only, malformed
  input) or their client copy.
- No change to reaper, rate-limit codes, or the #1144 lock mechanics themselves.
- No retry loops / auto-retry client-side — copy invites manual retry, that's the #1149 pattern.
