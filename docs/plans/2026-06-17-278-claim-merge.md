# Shadow Members — Claim/Merge-on-Join (fast-follow slice of #278) Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
>
> **This spec is Gate-CATEGORY on all four axes** (new Cloud Function auth + money re-key + schema field-name re-key + a rules-adjacent member-doc rewrite). **It MUST clear `/run-the-gate` (a fresh-context Opus subagent, zero session history) BEFORE any PR6 code is written**, and PR7/PR8/PR9 each re-Gate before their own code. The money/parity tests below are non-negotiable.

**Goal:** When a real person joins a group that already holds a placeholder ("shadow") member with their name (the creator typed "Ali" via `addShadowMember`, PR1 of the add-by-name slice), let the joiner **claim** that shadow: the shadow's placeholder uuid identity is re-keyed to the joiner's real auth uid across every money doc, so the joiner inherits the shadow's balance instead of starting from zero. This is the **mirror image of `deleteAccount.ts`'s uid→tombstone re-key** — here it is uuid→uid. It is the last open slice of #278; **#278 CLOSES when PR9 ships.**

**Architecture:** A claim is a server-authoritative **uuid→uid re-key** performed by a NEW Admin-SDK callable `claimShadow`, modeled byte-for-byte on `deleteAccount.ts`'s two-phase cascade (Phase B = idempotent batched child-doc scrubs via `BatchWriter`, then Phase C = a transaction that retires the member identity with `group.memberIds` rewritten **LAST**). It cannot be a client rules carve-out: `memberIds` is fully server-authoritative (`firestore.rules:308` `validMemberIdsRefresh` requires `memberIds` unchanged), and #524 binds a client-written member doc's `id == userId == request.auth.uid` (`firestore.rules:783`) — a re-key that swaps a uuid for a uid in `memberIds` and touches other members' money docs can only be done by the Admin SDK. Because the balance oracle (`recomputeNet`, `groupNetBalance.ts`) is **identity-blind** (it keys on `userId`, never `isShadow`), the re-key is "just" a key rename across docs — but `splitDistribution` is a **map keyed by participant id**, and if the joiner already holds their own slice in the same group (D2), a naive overwrite-rename would **silently delete money**. So PR6 first **restores the SUM-on-collision map re-keyer `mergeUidMapKey`** (deleted in #441; see below), and PR7 asserts in-transaction that the post-re-key net per currency equals `priorShadowNet + priorClaimerNet` (B4 parity), aborting the whole claim if it doesn't. Authorization (PR8) is **creator-approval** (D1): the joiner *requests* a claim, the creator *approves*, and only an approved request lets `claimShadow` run. PR9 surfaces claimable shadows on the join screen (they arrive via a callable payload because the members list is read-gated `firestore.rules:815`) with a **hard, irreversible-by-design confirmation** (D3).

**Tech Stack:** Cloud Functions (Node 22 / TypeScript, `firebase-functions/v2`), Firestore Admin SDK, Jest + Firestore emulator (Java 21); Flutter / Riverpod / Dart client.

## PR8 — Claim authorization: creator-approval (BACKEND + minimal client, **GATE**)

**Goal:** Implement D1 — a joiner *requests* a claim; the creator *approves*; only an approved request lets `claimShadow` actually re-key. Reject self-claim without approval; reject anon (D6). This is the impersonation gate.

**Design (the request/approve state machine — spec the exact docs/fields):**
- A claim request is a server-written doc, e.g. `groups/{gid}/claimRequests/{requestId}` with `{requesterUid, requesterDisplayName, shadowMemberId, shadowDisplayName, status:'pending'|'approved'|'declined', createdAt, decidedBy, decidedAt}`. **It is server-authoritative** (written only by callables; rules `allow write: if false` for clients, readable by the creator + the requester). Spec the exact rules block + the `firestore.rules` read predicate (creator OR requester).
- `requestClaimShadow(groupId, shadowMemberId)` callable: caller must be a **durable** account (reject anon, D6) and **already a member** of the group (they joined via invite code, then saw the claim offer — PR9). Validates the shadow exists + `isShadow:true` + unclaimed. Writes a `pending` request. Idempotent (re-request returns the existing pending request). One pending request per (requester, shadow).
- `decideClaimRequest(groupId, requestId, approve:boolean)` callable: caller must be the **group creator** (`group.createdBy === uid`, mirroring `removeMember.ts:90`); reject anon. On `approve:true` → flip status to `approved`, then invoke the PR7 re-key inline (call the shared `claimShadow` engine function directly, NOT over HTTP) within the same authorization context, then mark the request `claimed`. On `approve:false` → status `declined` (the requester falls back to "join as new"). Reject deciding an already-decided request (idempotent).
- **Self-claim without approval is impossible by construction:** the requester cannot call `decideClaimRequest` (they are not the creator), and `claimShadow`'s re-key is only reachable via an approved `decideClaimRequest`. PR7's standalone `claimShadow` callable, if it remains exported, MUST be tightened here to require an approved request (or be de-exported and only the engine function kept) — **decide in the Gate**: the safest shape is to NOT export a directly-callable `claimShadow` at all, and route every re-key through `decideClaimRequest(approve:true)`. **Recommend de-exporting the raw `claimShadow` callable**; keep `claimShadowEngine` as an internal function PR8 invokes. Flag to the Gate.
- **The #279-guard inversion note:** a claim *request* is the inverse of the `joinGroupByInviteCode.ts:330-344` rejection — a name match that the join guard treats as "name taken" is what surfaces the claim offer (PR9). The join guard itself is UNCHANGED in PR8 (the join still rejects a colliding NEW name; the claim path is a SEPARATE post-join action). Do NOT weaken the join collision guard.

**Files:**
- Create: `functions/src/callables/requestClaimShadow.ts`, `functions/src/callables/decideClaimRequest.ts` (or one file with both — match the one-callable-per-file convention).
- Modify: `functions/src/callables/claimShadow.ts` → export `claimShadowEngine(db, groupRef, shadowMemberId, claimerUid)` for `decideClaimRequest` to call; de-export the raw `onCall` (per the Gate decision).

- Create: `functions/test/callables/claimRequest.test.ts`.
- Minimal client: a callable wrapper in the relevant provider (`group_provider.dart`) for `requestClaimShadow` / `decideClaimRequest` (the UI lands in PR9).

**Test table (TDD):**
```
1.  requestClaimShadow: anon → permission-denied (D6); non-member → permission-denied; valid member → pending request written
2.  requestClaimShadow on a non-shadow / already-claimed shadow → failed-precondition; no request
3.  requestClaimShadow idempotent: second request → same pending doc, no duplicate
4.  decideClaimRequest by NON-creator → permission-denied; request unchanged (impersonation gate — the core D1 test)
5.  decideClaimRequest approve by creator → status approved→claimed; the PR7 re-key ran (assert memberIds swap + B4 parity on a debtor shadow)

7.  decideClaimRequest on an already-decided request → failed-precondition (idempotent)
8.  decideClaimRequest anon → permission-denied
9.  end-to-end: request → approve → the claimer's balance == shadow's prior balance (full D1+D2 happy path)
```

## PR9 — Claim picker on join (CLIENT + payload, **GATE**)

**Goal:** Surface claimable shadows to a real joiner with a "is this you? claim / I'm new" choice and a **hard permanent-confirmation** (D3). This is what makes the add-by-name limitation disappear and CLOSES #278.

**How the shadow list reaches the client (B6).** The members subcollection is read-gated (`firestore.rules:815`), so a fresh joiner CANNOT list shadows client-side. Options:
- **(Recommended) `listUnclaimedShadows(inviteCode)` callable** — durable-account-gated (reject anon, D6), validates the invite code (reuse `normalizeInviteCode` from `joinGroupByInviteCode.ts:59`), returns `[{shadowMemberId, displayName}]` for every `isShadow:true && !claimed` member, WITHOUT requiring the caller to already be a member (it is the pre-join discovery call). This is the cleanest: the join screen calls it after a valid code is entered, BEFORE committing the join, and shows the claim picker.
- (Alternative) fold the list into the `joinGroupByInviteCode` result — rejected: the joiner is already a member by then and may have collided on a name. Discovery must happen BEFORE the join commit. Use the dedicated callable.

**Flow (spec the exact screens/state):**
1. User enters invite code on the join screen → `listUnclaimedShadows(code)`.
2. If the list is non-empty, show a "Is one of these you?" picker listing each shadow's display name. The user either:
   - taps a shadow → "Claim **<name>**'s spot?" sheet with a **hard, explicit permanent warning** (D3): "This permanently merges <name>'s expenses into your account. It can't be undone. The group creator must approve." → `requestClaimShadow(groupId, shadowMemberId)` → "Waiting for <creator> to approve." (the join itself may proceed as a fresh member OR be deferred — **DECIDE in the Gate**: recommend the requester joins as a fresh member immediately and the *approved* claim later re-keys their fresh slice into the shadow via D2 SUM — but that means the requester briefly holds a zero slice that SUMs cleanly; the simpler model is "request first, creator approves, THEN the claimer's identity is the shadow's" — pick one and pin it). 
   - taps "No, I'm new" → proceeds to the normal `joinGroupByInviteCode` with their own (non-colliding) name. If their typed name collides with a shadow they declined, the #279 guard still rejects — surface "that name is taken; claim it above or pick another."
3. The creator sees pending claim requests (a new affordance in group settings / a notification) → approve/decline via `decideClaimRequest`.

**The #279-guard inversion in the UI:** today a name collision on join is a dead-end ("name taken"). PR9 turns it into a path: the picker offers the claim, and "No, I'm new" forces a distinct name. The join callable's guard is unchanged (PR8); the client routes around it via the claim offer.
