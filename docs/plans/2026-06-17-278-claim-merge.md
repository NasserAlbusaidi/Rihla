# Shadow Members — Claim/Merge-on-Join (fast-follow slice of #278) Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
>
> **This spec is Gate-CATEGORY on all four axes** (new Cloud Function auth + money re-key + schema field-name re-key + a rules-adjacent member-doc rewrite). **It MUST clear `/run-the-gate` (a fresh-context Opus subagent, zero session history) BEFORE any PR6 code is written**, and PR7/PR8/PR9 each re-Gate before their own code. The money/parity tests below are non-negotiable.

**Goal:** When a real person joins a group that already holds a placeholder ("shadow") member with their name (the creator typed "Ali" via `addShadowMember`, PR1 of the add-by-name slice), let the joiner **claim** that shadow: the shadow's placeholder uuid identity is re-keyed to the joiner's real auth uid across every money doc, so the joiner inherits the shadow's balance instead of starting from zero. This is the **mirror image of `deleteAccount.ts`'s uid→tombstone re-key** — here it is uuid→uid. It is the last open slice of #278; **#278 CLOSES when PR9 ships.**

**Architecture:** A claim is a server-authoritative **uuid→uid re-key** performed by a NEW Admin-SDK callable `claimShadow`, modeled byte-for-byte on `deleteAccount.ts`'s two-phase cascade (Phase B = idempotent batched child-doc scrubs via `BatchWriter`, then Phase C = a transaction that retires the member identity with `group.memberIds` rewritten **LAST**). It cannot be a client rules carve-out: `memberIds` is fully server-authoritative (`validMemberIdsRefresh`, `firestore.rules:304`, requires `memberIds` unchanged — the clause is at `:308`), and #524 binds a client-written member doc's `id == userId == request.auth.uid` (`firestore.rules:783`) — a re-key that swaps a uuid for a uid in `memberIds` and touches other members' money docs can only be done by the Admin SDK. Because the balance oracle (`recomputeNet`, `groupNetBalance.ts`) is **identity-blind** (it keys on `userId`, never `isShadow`), the re-key is "just" a key rename across docs — but `splitDistribution` is a **map keyed by participant id**, and if the joiner already holds their own slice in the same group (D2), a naive overwrite-rename would **silently delete money**. So PR6 first **restores the SUM-on-collision map re-keyer `mergeUidMapKey`** (deleted in #441; see below), and PR7 asserts in-transaction that the post-re-key net per currency equals `priorShadowNet + priorClaimerNet` (B4 parity), aborting the whole claim if it doesn't. Authorization (PR8) is **creator-approval** (D1): the joiner *requests* a claim, the creator *approves*, and only an approved request lets `claimShadow` run. PR9 surfaces claimable shadows on the join screen (they arrive via a callable payload because the members list is read-gated `firestore.rules:815`) with a **hard, irreversible-by-design confirmation** (D3).

**Tech Stack:** Cloud Functions (Node 22 / TypeScript, `firebase-functions/v2`), Firestore Admin SDK, Jest + Firestore emulator (Java 21); Flutter / Riverpod / Dart client.

#### [P1] The dropped-slice parity hazard — when post-commit parity can break

**The hazard (verified this round):** the oracle folds a *live* member's `splitDistribution` slice into the balance ONLY if that member is in the event's `participantIds`. Specifically `groupNetBalance.ts:617-619` adds a split-recipient key to the event universe only when `allMemberIds.has(uid) && !liveMemberIds.has(uid)` — a **live** member whose key is in `splitDistribution` but NOT in `participantIds` is NOT added to the universe, and `:428` (`owedBucket.has(uid)`) then DROPS its owed. So a relabel that moves a split key from a non-participant id to a *participant* id (or vice-versa) can change whether that slice counts.

**Why the NORMAL claim is parity-safe by construction (D8):** because the claim request happens BEFORE the claimer joins (D8), the claimer is NOT a member at claim time and has NO independent slice. The CREATE rule (`firestore.rules:565-569`, `enforceParticipantKeys=true`) guarantees the shadow's split keys are all within `participantIds` already. The re-key moves `participantIds` item-1 (`replaceUid`) in lockstep with the `splitDistribution` key (`mergeUidMapKey`), so the claimer lands EXACTLY where the shadow was — both in `participantIds` and in the split map — and the slice that counted for the shadow counts identically for the claimer. **No drop.**

**The residual = the claimer-already-financially-present path.** The hazard is reachable only when the claimer *independently* has a position in the group's financial universe. Sub-cases: (i) **equal split** — the claimer is a co-participant of an equal-split event, so the re-key dedups `participantIds` (3→2) and moves the divisor (`mergeUidMapKey` can't help — `splitDistribution` is empty); (ii) **forged out-of-participant slice** — `shadow ∈ splitDistribution(eventX)` AND `shadow ∉ participantIds(eventX)` AND the claimer is independently in `universe(eventX)`; the shadow's slice was DROPPED pre-claim and after the re-key merges into the claimer's *counted* key; (iii) **departed-but-still-participant** — the claimer left (or was removed) so is `∉ memberIds`, but `leaveGroup`/`removeMember` never prune event `participantIds`, so they are still in the universe and sub-case (i) fires with a `memberIds`-only guard SILENT (the #557 round-2 refute). All require the claimer to be financially present, which **D8 forbids** — so these only arise via PR8 not yet existing, a forged/Admin doc, a returning member, or a TOCTOU race.

**The PR7 guard (#557 — enforce D8 in the engine):** reject up-front (`failed-precondition`) when the claimer is already in the **financial universe** — `claimerUid ∈ priorNet`'s key-set (which `finalizeNet` seeds from `seenUids` ⊇ every event participantIds universe ∪ group-settlement parties) — OR `∈ group.memberIds` (to also catch a footprint-less member). Phase A pre-check + Phase C tx `memberIds` re-check (TOCTOU). **The gate is the UNIVERSE, not `memberIds`** — keying on `memberIds` alone left sub-case (iii) open (round-2 refute: a departed participant still moves the equal-split divisor). This closes all three sub-cases before any irreversible write, superseding the original "detect-after, per D9" plan which (a) only caught sub-case (ii), missing the equal-split divisor, and (b) was POST-commit — the merge finalized, then threw `internal`, and the idempotent retry (shadow gone) blessed it un-verified. The **D9 post-commit parity assert is retained as the backstop** for the one residual the up-front guard can't reach: a forged out-of-participant slice paired with a NEW, non-member, non-universe claimer (test 19's old framing) and the exotic mid-claim-participant-add race — there the merge still finalizes-then-detects; tightening that to pre-commit is a tracked follow-up. (Re-keying universe membership consistently so the relabel can't trip the assert is still rejected — it would require the engine to reason about the oracle's drop semantics.)

## PR9 — Claim picker on join (CLIENT + payload, **GATE**)

**Goal:** Surface claimable shadows to a real joiner with a "is this you? claim / I'm new" choice and a **hard permanent-confirmation** (D3). This is what makes the add-by-name limitation disappear and CLOSES #278.

**How the shadow list reaches the client (B6).** The members subcollection is read-gated (`firestore.rules:815`), so a fresh joiner CANNOT list shadows client-side. Options:
- **(Recommended) `listUnclaimedShadows(inviteCode)` callable** — durable-account-gated (reject anon, D6), validates the invite code (reuse `normalizeInviteCode` from `joinGroupByInviteCode.ts:59`), returns `[{shadowMemberId, displayName}]` for every `isShadow:true && !claimed` member, WITHOUT requiring the caller to already be a member (it is the pre-join discovery call). This is the cleanest: the join screen calls it after a valid code is entered, BEFORE committing the join, and shows the claim picker.
- (Alternative) fold the list into the `joinGroupByInviteCode` result — rejected: the joiner is already a member by then and may have collided on a name. Discovery must happen BEFORE the join commit. Use the dedicated callable.

**Flow (spec the exact screens/state):**
1. User enters invite code on the join screen → `listUnclaimedShadows(code)`.
2. If the list is non-empty, show a "Is one of these you?" picker listing each shadow's display name. The user either:
   - taps a shadow → "Claim **<name>**'s spot?" sheet with a **hard, explicit permanent warning** (D3): "This permanently merges <name>'s expenses into your account. It can't be undone. The group creator must approve." → `requestClaimShadow(inviteCode, shadowMemberId)` → "Waiting for <creator> to approve." **Per D8 (locked): the requester does NOT join the group yet** — the request is pre-join, and the creator's approval (`decideClaimRequest`) performs the re-key that makes the claimer the member (no transient fresh slice, no D2-SUM-of-own-zero-slice). The requester polls their pending state via **`listMyClaimRequests(inviteCode)`** (claimRequests is `allow read: if false`, so no client doc-listen); when the creator approves, they are now a member with the shadow's balance. (This resolves the prior draft's join-vs-claim ordering open question.)
   - taps "No, I'm new" → proceeds to the normal `joinGroupByInviteCode` with their own (non-colliding) name. If their typed name collides with a shadow they declined, the #279 guard still rejects — surface "that name is taken; claim it above or pick another."
3. The creator sees pending claim requests via **`listGroupClaimRequests(groupId)`** (a new affordance in group settings / a notification — again a callable poll, since claimRequests has no client read) → approve/decline via `decideClaimRequest`.

**The #279-guard inversion in the UI:** today a name collision on join is a dead-end ("name taken"). PR9 turns it into a path: the picker offers the claim, and "No, I'm new" forces a distinct name. The join callable's guard is unchanged (PR8); the client routes around it via the claim offer.
