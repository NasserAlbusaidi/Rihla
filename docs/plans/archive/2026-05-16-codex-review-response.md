# Codex Review Response - v1.2.0+15 Scope

## Gap 1 - Join does not sync existing events

**Verdict:** Ship in +15, but simplify the server plan. The bug is a functional release blocker: the callable adds the UID to `groups/{gid}.memberIds` and creates `members/{uid}`, but it never updates existing event `participantIds` / `participantNames` (`functions/src/callables/joinGroupByInviteCode.ts:162`, `functions/src/callables/joinGroupByInviteCode.ts:201`). The client can then read events as a group member, but add-expense still fails because expense creation requires event participation (`security/firestore.rules:417`) and the route-scoped participant provider returns `null` unless the UID is in `event.participantIds` (`lib/features/trip/providers/trip_provider.dart:37`).

**What is wrong or missing:**

- Reading events outside the transaction is not necessary in the Admin SDK. The local Admin dependency exposes `Transaction.get(query)` and locks returned docs (`functions/node_modules/@google-cloud/firestore/build/src/transaction.d.ts:58`), but all transaction reads still need to happen before writes (`functions/node_modules/@google-cloud/firestore/types/firestore.d.ts:648`). Query events inside the transaction, then update group/member/event docs after all reads.
- The client-side self-join option is not viable without a real rules expansion. `validEventLightUpdate()` starts with `requesterIsParticipant()` (`security/firestore.rules:315`), and current `participantNames` rules only allow added keys, not changed values (`security/firestore.rules:328`). A non-participant cannot add themselves under today's rules.
- The 500-write concern is real in the abstract but over-scoped for this launch. Join would write one group doc, maybe one member doc, and one doc per event. Rihla groups realistically under 20 events do not need a batch fallback. Add a defensive max-events check if desired; do not design a second write path for +15.
- `updatedAt` churn is not the stated sort landmine. Group events are queried and sorted by `createdAt`, with null-date handling on the client (`lib/features/events/providers/event_provider.dart:36`). Active journeys sort by `startDate`/`createdAt`, not `updatedAt` (`lib/features/home/providers/active_journeys_provider.dart:170`). Existing `EventService.addParticipant()` already writes `updatedAt` when participants change (`lib/features/events/services/event_service.dart:155`).
- The re-join path matters. The current callable returns early when `memberIds.includes(uid)` (`functions/src/callables/joinGroupByInviteCode.ts:187`), so a fan-out limited to new members will not heal already-affected production users who retry the invite. The fan-out must run idempotently for already-members too, at least when the member doc exists or is healed.
- Do not deploy a broad ops callable for this. A versioned Admin script with dry-run, group filters, and idempotent writes is safer than a throwaway shell snippet, but it should not become a callable surface.

**Next step:** Implement one server-side path in `joinGroupByInviteCode`: resolve invite, read group/member/events in a single transaction before any writes, then `arrayUnion` the UID and set `participantNames.{uid}` on every non-deleted event where missing. Cover new join, already-member heal, soft-deleted-event skip, malformed event data, and no-event cases in Jest. Run a dry-run Admin backfill for affected groups before shipping +15.

## Gap 2 - Stale `participantNames`

**Verdict:** Deferring to +16 is acceptable for a hot +15, but the reason is narrower than "purely cosmetic" and the proposed 3-widget patch is incomplete. Balance math is UID-driven: group balances build participants from `GroupMember.userId` (`lib/features/groups/providers/group_balance_provider.dart:175`) and `BalanceCalculator` uses `payerParticipantId`, split recipient IDs, and settlement payer/recipient IDs for arithmetic (`lib/features/ledger/providers/expense_provider.dart:191`, `lib/features/ledger/providers/expense_provider.dart:283`). Stale names do not change money math or permissions, but they do mislabel money records and search results.

**What is wrong or missing:**

- `participantNames` is a display input in more places than the scoped 3 widgets. Examples: `ledger_screen.dart` enriches expense payer names from the event map but not settlement names (`lib/features/ledger/screens/ledger_screen.dart:87`), `LedgerDayCard` renders settlement snapshots directly (`lib/features/ledger/widgets/ledger_day_card.dart:149`), search indexes denormalized payer/recipient names (`lib/features/ledger/widgets/ledger_search_sheet.dart:439`), current-participant display names come from the event map (`lib/features/trip/providers/trip_provider.dart:37`), and active journey member names come from the event map (`lib/features/home/providers/active_journeys_provider.dart:153`).
- The named widgets are not the right patch boundary. `ExpenseCard` and `SettlementRow` look like older standalone components; the current ledger timeline goes through `LedgerDayCard` (`lib/features/ledger/screens/ledger_screen.dart:290`). Patch the data enrichment layer or current rendering path, not just unused/secondary widgets.
- Rules loosening can be safe only if it is exact: allow the signed-in participant to change only `participantNames[request.auth.uid]`, keep no removals, keep no changes to other keys, and keep `displayNameMapValuesAreValid()`. Existing validation rejects empty/control-character names (`security/firestore.rules:18`) and map values (`security/firestore.rules:36`). HTML injection is not a meaningful Flutter `Text` risk, but name impersonation remains possible and already exists via member display-name updates.
- "Backfill is automatic on first rename" is only true for users who rename again after deploy. Existing stale docs stay stale for users who do not touch their name. Also, `propagateDisplayName()` silently swallows failures (`lib/core/providers/settings_provider.dart:101`), so a too-large batch or rules mismatch would fail invisibly.

**Next step:** Defer from the minimum +15 unless the implementation is kept central. For +16, write rules tests first for self-only `participantNames` update, then update `propagateDisplayName()` to fan out to participated events with a guarded batch. Separately, enrich display data at the ledger/group-settle-up source so old settlement snapshots prefer current roster/event names without patching isolated widgets one by one.

## Gap 3 - Orphan anonymous Firebase Auth users

**Verdict:** The proposed partial +15 is not safe as written. UI dedup can be a temporary visual mitigation, but client-side "delete member docs, delete anon user, then recover" should not ship. A real fix needs a server-side cleanup/cascade path or an explicit decision that +15 remains closed-test-only with this known compliance gap.

**What is wrong or missing:**

- An orphan Firebase Auth user record alone does not render in member lists. The duplicate UI comes from Firestore membership state: `groupMembersProvider` streams every `members` subcollection doc (`lib/features/groups/providers/group_provider.dart:408`), and `GroupMembersSection` renders the provided list without checking `group.memberIds` (`lib/features/groups/widgets/group_members_section.dart:63`).
- Filtering only `GroupMembersSection` is too low. `groupBalancesProvider` also consumes the raw `groupMembersProvider` list to build balance participants (`lib/features/groups/providers/group_balance_provider.dart:121`). A dangling or duplicate member doc can affect balances and settle-up screens before the settings widget sees it.
- Filtering docs whose `userId` is not in `group.memberIds` only catches one orphan shape. It misses the "two of me" case where both anon UID and recovered UID are in `memberIds`; it also does not resolve duplicated names, stale creator roles, or balance participants.
- `createdBy` is not used in balance math, but it is functional. Group settings creator privileges depend on `currentUserId == group.createdBy` (`lib/features/groups/screens/group_settings_screen.dart:41`), event admin checks depend on event/group `createdBy` (`lib/features/events/utils/event_permissions.dart:15`), and group detail role labels use `group.createdBy` (`lib/features/groups/screens/group_detail_screen.dart:850`). Deferring all owner reassignment may strand the recovered human from creator/admin actions.
- The proposed "delete member docs while anon" claim is incomplete. Rules allow member deletion only when the group after-state no longer contains that UID (`security/firestore.rules:602`). The existing client leave flow pairs `arrayRemove(uid)` with member-doc delete in one batch (`lib/features/groups/providers/group_provider.dart:312`). Deleting only member docs should fail rules, and deleting memberships before proving recovery can lose data.
- The recovery sequence currently waits for pending writes, signs out, signs in with the email link, then clears pending state (`lib/features/auth/services/auth_recovery_service.dart:163`). Moving destructive cleanup before `signInWithEmailLink()` creates a bad failure mode: if auth delete or recovery fails, the user may lose the current anonymous membership before acquiring the target UID.
- There is a real deletion-policy mismatch. `DataDeletionService` currently deletes only the Firebase Auth user and explicitly defers Firestore cascade (`lib/features/auth/services/data_deletion_service.dart:13`). The in-app dialog says the account is permanently deleted but data becomes unreachable (`lib/features/auth/widgets/delete_account_dialog.dart:35`). The repo privacy/delete-data pages promise broader deletion/removal of identity data and group memberships (`hosting/privacy.html:99`, `hosting/delete-data.html:73`). I could not verify the live `https://rihla.app/privacy` page serving this policy in this run; the repo copy is still enough to treat cascade as a launch-risk item once deployed.

**Next step:** Do not implement client-side pre-recovery deletion. For +15 today, either leave this out and document it as a closed-test known issue, or do the smallest server-safe version: after successful recovery, call an Admin-backed cleanup with the old UID captured before sign-out, remove that UID from `memberIds`, delete matching member docs, and log failures without blocking the restored session. The fuller v1.2.1 path should add `auth.user.onDelete()` cascade and tests for member arrays, member docs, FCM tokens, and creator/admin edge cases.

## Gap 4 - RD-QA matrix RD-01..08

**Verdict:** Not just doc hygiene. It is not enforced by the two GitHub workflows, but it is enforced by the local release-readiness script and by the production-readiness docs. If the team uses only `release_android.yml` with repo vars already set to `yes`, empty matrix cells will not block upload; if the team follows `tool/check_release_readiness.sh`, they will block.

**What is wrong or missing:**

- `release_android.yml` gates upload only on the three repository variables (`.github/workflows/release_android.yml:36`). It does not invoke `tool/check_real_device_qa_gate.sh`.
- `readiness_check.yml` runs analyzer, theme purity, emulator tests, Flutter coverage, and coverage threshold, but no RD-QA gate (`.github/workflows/readiness_check.yml:57`).
- `tool/check_release_readiness.sh` does invoke the real-device QA gate (`tool/check_release_readiness.sh:151`), and that gate fails empty Android cells/evidence placeholders (`tool/check_real_device_qa_gate.sh:80`, `tool/check_real_device_qa_gate.sh:84`). The current matrix still has empty Android cells and placeholder evidence (`docs/REAL-DEVICE-QA.md:92`).
- `tool/release.sh` bumps/tags/pushes and lets CI take over; it does not run release readiness before tagging (`tool/release.sh:147`). This leaves a process gap between docs/script expectations and CI enforcement.

**Next step:** Decide which gate is authoritative for +15. If repo vars are the source of truth, update production-readiness docs to say RD-QA evidence is an external attestation and do not pretend the matrix blocks CI. If `tool/check_release_readiness.sh` is still the release gate, fill RD-01..08 Android cells with the actual closed-test evidence before tagging +15, or wire the gate into CI with the required device limitation acknowledged.

## MVP vs Right

**Minimum viable +15 today:** ship the three fixed +14 bugs plus Gap 1 server fan-out and a targeted Admin backfill for affected groups. Do not ship Gap 2 rules/UI churn. Do not ship the proposed Gap 3 client-side deletion sequence. Treat Gap 4 as a process decision: if the Play upload is already guarded by repo vars and debug build was physically verified, the matrix can be filled after the fact, but that means consciously bypassing the local readiness script.

**Right +15:** ship Gap 1 with tests and backfill, reconcile the RD-QA gate before tagging, and either fix account deletion/recovery cleanup server-side or explicitly hold it out of any public-launch claim. Gap 2 can remain +16 if the release goal is to unblock real expenses for joined users; it becomes +15 only if implemented centrally with rules tests and no broad widget sweep.
