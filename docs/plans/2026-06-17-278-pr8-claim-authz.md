## Goal

Implement **D1 (creator-approval)**: a real person *requests* to claim a placeholder ("shadow") member; the group **creator** *approves*; only an approved request invokes the PR7 re-key engine. After PR8 the engine is reachable **ONLY** via an approved `decideClaimRequest` — the raw `claimShadow` onCall is de-exported. This is the impersonation gate (a stranger must not be able to inherit a shadow's debt/credit unilaterally).

**D8 (request BEFORE join):** the requester is NOT yet a group member at request time. The creator's approval performs the re-key, which makes the claimer the member (inheriting the shadow's balance). No transient fresh slice.

## The `claimRequests` doc (server-authoritative, callable-mediated)

`groups/{gid}/claimRequests/{requestId}` — **clients NEVER read or write directly** (`allow read, write: if false`). Both the requester and the creator poll via callables.

- **`requestId` = deterministic `${requesterUid}__${shadowMemberId}`** — one request per (requester, shadow); makes idempotency a same-doc upsert (no query). Both components are uid/uuid (no `/`); `__` is a safe separator.
- **Fields:** `{ requesterUid, requesterDisplayName, shadowMemberId, shadowDisplayName, status, createdAt, decidedBy, decidedAt }`.
- **`status`:** `'pending' | 'declined' | 'claimed'`. There is **no intermediate `'approved'`** — the engine runs synchronously inside `decideClaimRequest(approve:true)` and the doc flips straight `pending → claimed` on engine success, or `pending → declined` on decline. (A persisted `'approved'` mid-state would be racy with the multi-batch engine; CAS the `pending` transition instead — see decideClaimRequest.)

## Callable specs

### `requestClaimShadow(inviteCode, shadowMemberId, displayName?)` → `{ requestId, status, groupId }`

Mirror `addShadowMember`'s `onCall({enforceAppCheck:true})` shape.
1. `request.auth` else `unauthenticated`.
2. anon → `permission-denied` (D6), BEFORE any read.
3. `inviteCode = normalizeInviteCode(...)` (invalid → `invalid-argument`); `shadowMemberId = validId(...)`; `displayName = normalizeDisplayName(request.data?.displayName)` (optional → 'Anonymous' fallback, for the creator's "who is asking" view only — NOT the adopted name, D7).
4. Resolve group: `db.doc('inviteCodes/{code}').get()` → not exists → `not-found`; `inviteData.groupId` string-guard → `failed-precondition` if malformed. (A bad/unknown code → `not-found`/`invalid-argument`, so only a holder of a VALID invite can open a request — a stranger can't fabricate requests for arbitrary groups.)
5. Load group; `isDeleted`/`deletingInProgress`/missing → `not-found`.
6. **Validate the shadow** (server-side; the requester can't read members): match `members` by `userId == shadowMemberId`; require exactly a claimable placeholder — `isShadow === true && isTombstone !== true` AND `shadowMemberId ∈ group.memberIds` — else `failed-precondition` ("That member can't be claimed."). (Same claimable predicate as the engine Phase A, so a non-shadow / already-claimed / tombstoned target is rejected at request time.)
7. **D8 self-protection:** the requester must NOT already be a member — `request.auth.uid ∈ group.memberIds` → `failed-precondition` ("You're already in this group."). (They'd hit the engine's pre-scan anyway; reject early with a clear message.)
8. **Upsert the request** (deterministic id): if a doc exists with `status:'claimed'` → `failed-precondition` (already claimed); otherwise `set` (merge-free overwrite) to `{requesterUid:auth.uid, requesterDisplayName:displayName, shadowMemberId, shadowDisplayName:<shadow's displayName>, status:'pending', createdAt: serverTimestamp(), decidedBy:null, decidedAt:null}`. Idempotent: a second identical request re-writes the same pending doc (one doc, still pending). A prior `'declined'` is re-opened to `'pending'`.
9. Return `{requestId, status:'pending', groupId}`.

> **NOT a member-mutation** — `requestClaimShadow` does NOT touch `memberIds` or any money doc. It only writes a `claimRequests` doc. No rate-limit (App Check is the per-actor control, #197) and no throttle-burn surface.

### `decideClaimRequest(groupId, requestId, approve)` → `{ requestId, status, alreadyClaimed }`

The impersonation gate. Mirror `removeMember`'s creator-gate shape.
1. `request.auth` else `unauthenticated`; anon → `permission-denied` (D6).
2. `groupId = validId(...)`; `requestId = validId(...)`; `approve` must be `boolean` → else `invalid-argument`.
3. Load group; missing/`isDeleted`/`deletingInProgress` → `not-found`.
4. **Creator gate:** `group.createdBy !== auth.uid → permission-denied` (the core D1 test).
5. **CAS the `pending` transition in a transaction on the request doc:** `tx.get(claimRequests/{requestId})`; not exists → `not-found`; `status !== 'pending'` → `failed-precondition` (already-decided, idempotent — test 7). **Read `requesterUid` + `shadowMemberId` from the DOC — treat `requestId` as an OPAQUE handle, NEVER parse it, and there is NO `claimerUid` in the input.** This is the impersonation seal: the creator chooses only approve/decline; the re-key target is fixed by whoever called `requestClaimShadow` (its `auth.uid`, persisted as `requesterUid`). A creator cannot redirect a claim onto an attacker-supplied uid because no uid crosses the `decideClaimRequest` boundary. (Gate R1 [P2].)
   - **`approve === false`:** in the SAME tx, set `status:'declined', decidedBy:auth.uid, decidedAt: serverTimestamp()`. Return `{requestId, status:'declined', alreadyClaimed:false}`. NO engine call; shadow untouched.
   - **`approve === true`:** the tx ONLY reads-and-asserts `pending` (it does NOT flip status — the engine is multi-batch and cannot run inside this tx). Commit the read-assert, then OUTSIDE the tx call `claimShadowEngine(db, groupRef, shadowMemberId, requesterUid)`:
     - **engine resolves** (incl. `alreadyClaimed:true`) → set `status:'claimed', decidedBy:auth.uid, decidedAt: serverTimestamp()`; return `{requestId, status:'claimed', alreadyClaimed:<engine result>}`.
     - **engine throws** (`not-found` / `failed-precondition` / `internal`) → **do NOT mark claimed**; the request stays `'pending'` (so a transient `internal`/TOCTOU is retryable by re-approving). **Propagate the engine's HttpsError unchanged** — its code+message already drive PR9's UX (the table above). A terminal `failed-precondition` (claimer-already-present) leaves the request pending; the creator can `approve:false` to decline it, or the requester joins as new.

> **Concurrency:** the only double-engine-invocation risk is two simultaneous `approve` calls. The CAS isn't enough alone (both could read `pending` before either sets `claimed`). Mitigate: the **engine is idempotent** — a second invocation sees the shadow gone (`alreadyClaimed:true`) and does NOT re-merge (PR7 test 16). So a double-approve at worst sets `claimed` twice (same terminal state, no money doubled). The serial `pending→claimed` set after a successful engine run is the natural barrier. This matches the engine's own idempotency contract; no extra lock needed.

> **[P2] TOCTOU residual (filed as a tracked issue, see below):** a concurrent admin editing an event's `participantIds` mid-claim can make the engine's post-commit parity assert throw `internal` AFTER the re-key committed; the idempotent retry then returns `alreadyClaimed` un-verified. Creator-approval + Phase-C tx-serialization narrow this to a near-impossible window. `decideClaimRequest` already treats `internal` as RETRYABLE (never marks claimed), and PR9 surfaces it as "couldn't complete, try again" — never as terminal success.

### `listMyClaimRequests(inviteCode)` → `{ requests: [{requestId, shadowMemberId, shadowDisplayName, status, createdAt}] }`

Requester polls their own request status (`claimRequests` is `allow read: if false`).
1. `request.auth` else `unauthenticated`; anon → `permission-denied` (D6).
2. `inviteCode = normalizeInviteCode(...)`; resolve group from the invite code (same chain as `requestClaimShadow`); missing → `not-found`.
3. **No membership gate** (D8 — the requester is pre-join). Query `claimRequests where requesterUid == auth.uid` (this group). Return ONLY the caller's own requests (never others').

### `listGroupClaimRequests(groupId)` → `{ requests: [{requestId, requesterUid, requesterDisplayName, shadowMemberId, shadowDisplayName, status, createdAt}] }`

Creator polls pending requests.
1. `request.auth` else `unauthenticated`; anon → `permission-denied` (D6).
2. `groupId = validId(...)`; load group; missing → `not-found`.
3. **Creator gate:** `group.createdBy !== auth.uid → permission-denied`.
4. Query `claimRequests where status == 'pending'` (the creator's actionable set). Return all pending requests for the group.

## [P2] TOCTOU residual — file it

`gh issue create` (P2, `#278` parent): "claimShadow post-commit parity can throw `internal` after a TOCTOU participantIds edit; idempotent retry returns alreadyClaimed un-verified." Body: the engine's `assertExactParity` (`claimShadow.ts:317-340`) runs AFTER the re-key commits; a concurrent admin `participantIds` edit between snapshot and commit makes `simNet != actualNet` → `internal` post-finalize, and a retry (shadow gone) returns `alreadyClaimed` without re-verifying. Near-impossible (creator-approval + Phase-C serialization). Mitigation already shipped: `decideClaimRequest` treats `internal` as retryable, never marks claimed; PR9 surfaces "try again", never terminal-success. Fix candidate: fold the universe re-check into Phase C or a pre-commit guard (rejected in PR7 as exceeding the tx read budget — re-evaluate).
