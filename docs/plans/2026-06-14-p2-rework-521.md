# Revised spec — #521: pre-settlement review sorts/truncates flagged expenses by raw cross-currency amount

> Round-2 rework output (investigate→spec→gate→refute, then revise→re-gate loop→re-refute). Rounds: 2. Gate: **clean** (P1s: 0). Refuter: **spec-needs-rework** (survives: true).

Spec: docs/plans/2026-06-14-p2-rework-521.md

## Summary
distinctReviewExpenses at pre_settlement_review.dart line 78 sorts deduped flagged expenses by bare cross-currency Decimal magnitude; the sheet at pre_settlement_review_sheet.dart line 17 and lines 96 to 98 applies a flat top-5 cap. In a mixed-currency event this interleaves currencies by raw magnitude and can fully hide a currency that is largest in itself but smaller in raw, the JPY 1000 versus OMR 5 case. Detection is per-currency-correct; only the sort plus truncate is wrong. P2 display-only: onTapExpense carries only e.id at settle_up_screen.dart lines 78 to 79, no money-flow or write. Fix is per-currency bucket capping so no currency is fully hidden and no cross-currency compareTo remains.

> **Cap decision (2026-06-14): `kReviewPerCurrencyCap = 5`, not 3.** Per-currency cap of 5 preserves today's single-currency row count (no regression to the common OMR-only path); a mixed-currency event shows up to 5 per currency so no currency is ever fully hidden. **Bucket ORDER is alphabetical (currency code ASC)** — deliberately NOT by bucket total, because comparing totals across currencies is the exact banned cross-currency magnitude comparison this fix removes. Within a bucket (same unit, comparable) order is amount DESC → createdAt DESC → id ASC. The "+N more" overflow stays a single cross-bucket aggregate count (display-only).

## Approach
Add a per-currency cap constant of five (`kReviewPerCurrencyCap = 5`), a result record `({List<Expense> shown, int overflow})`, and a helper `reviewItemList` in the pure service that dedupes flags by id, buckets by currency, sorts within each bucket by amount DESC then createdAt DESC then id ASC, caps each bucket at the per-currency cap, joins buckets in alphabetical currency-code order, and sums per-bucket overflow. Remove the old cross-currency `distinctReviewExpenses` sort entirely. The sheet calls `reviewItemList` and drops the old flat `_maxItems` cap constant.

## Re-gate findings (residual)
- **[P2]** (Adversarial pass / acceptance box must have a committed test)
  Acceptance box 7 ('createdAt descending then id ascending tiebreak deterministic for equal same-currency amounts') is MANDATORY, but the spec marks the only test that exercises it (RED-4) as 'Optional 4th'. An acceptance box with no committed test is unprovable. Worse, a createdAt-desc tiebreak test needs distinct timestamps, but the unit test _exp helper (test/unit/pre_settlement_review_test.dart:11-29) hardcodes createdAt: DateTime(2026, 6, 1) for every row and exposes NO createdAt param — the spec asserts only that _exp 'already has a currency param' and is silent on the missing createdAt param the tiebreak test requires. As written, the tiebreak is implemented in reviewItemList but never deterministically asserted.
  → **Fix:** Make the createdAt-desc-then-id-asc tiebreak test non-optional, and add a createdAt parameter to the unit _exp helper so two equal-amount same-currency rows can be given distinct timestamps; assert the resulting order is deterministic (newer first, then id ascending). This closes acceptance box 7 with real evidence rather than a claim.

- **[P3]** (Spell out exact data contracts / display semantics)
  The '+N more' overflow message (preSettleReviewMore(overflow), sheet:150) renders a single aggregated integer while shown items are displayed bucketed by currency. In a multi-currency event where more than one bucket overflows, the hidden count silently mixes currencies (e.g. shown shows 3 JPY + 1 OMR, '+3 more' are all JPY). The spec's overflow contract is arithmetically correct but does not state that the message is intentionally currency-agnostic, leaving a reader to assume per-bucket overflow.
  → **Fix:** Add one sentence to the dataContracts / risks noting the overflow integer is intentionally a single cross-bucket total (display-only, non-blocking sheet) so an implementer does not 'fix' it into per-bucket overflow lines without a deliberate design decision.

- **[P3]** (Verify concrete claims / surface unresolved UX regression)
  Acceptance box 10 ('User confirms cap 3 vs 5 for the single-currency case before merge') bakes a human gate into the acceptance list. The single-currency UX regression is real: today a single-currency event shows up to 5 review rows; the new per-currency cap of kReviewPerCurrencyCap=3 reduces that to 3 even when there is only one currency (RED-3 pins exactly this). This is correctly surfaced as an open question, but it means a behavior change to the common (single-currency, the 1.0 OMR-only default) path is unresolved at spec time and should be explicitly flagged as the dominant real-world impact, not just the mixed-currency headline. **RESOLVED 2026-06-14: cap set to 5, so a single-currency event still shows up to 5 rows — no regression.**
  → **Fix:** Resolve the 3-vs-5 question before implementation (or default kReviewPerCurrencyCap to 5 to preserve single-currency behavior and only let bucketing change mixed-currency events), so the most-common code path's visible-row count is a deliberate choice rather than a side effect of the mixed-currency fix.
