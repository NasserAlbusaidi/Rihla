# #1144 Residuals R1+R5 — Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Close the two rules-inexpressible residuals that keep #1144 open: **R1** (a departed *universe-only* actor — ex-payer/settlement-party/split-key never in an event's `participantIds` — can still have their net moved by roster-derived writes) and **R5** (a new expense can still name a deleteAccount tombstone ghost as payer/split-party, and a D9 roster removal of a ghost key still passes).

**Architecture:** Two PRs. **PR-A (R1, functions-only):** close R1 by making the *state unreachable* instead of fencing it — every genesis path for "departed universe-only actor" funnels through exactly one chokepoint, `leaveGroup`/`removeMember`, so a new pure detector over the balance snapshot those callables already load refuses a departure that would leave universe-only financial history behind. The detector covers ONLY payers + settlement parties — the fold's non-member-gated resurrection set; split keys are member-gated (`allMemberIds.has(uid)`, `groupNetBalance.ts:687-689`) and therefore *drop* (never resurrect) after a hard-delete departure (Gate R1 rubric P2). Zero rules changes, zero expression-budget cost. **PR-B (R5, rules+functions+client):** a group-doc `activeMemberIds` array (= `memberIds` minus tombstone ids; shadow uuids stay in) maintained self-healingly by every roster writer through one shared transactional helper; rules read it via an absent-falls-back-to-`memberIds` helper and switch the **expense CREATE** party gate, the D9 roster-removal guard, and the event roster ENTRY points (create / roster-add) to it. **Every expense UPDATE-path gate (pre-state, post-state, soft-delete arm) stays on `memberIds`** — ghost history must remain editable and soft-deletable (the deleteAccount cleanup lane; Gate R1 adversary P1). Settlement gates likewise stay on `memberIds` (ghost debt-cleanup is sanctioned, D5/D6). **The balance oracle is untouched by both PRs** — the R1 detector is a read-only consumer of `GroupBalanceSnapshot`, not a universe input, so the claimShadow lock-step contract (`groupNetBalance.ts:586-591`) is not triggered.

**Tech Stack:** Firestore security rules, Cloud Functions (TS, Node 22), Jest + rules-unit-testing under the emulator (`npm run test:emulator`), one Dart write-site change + `flutter test`.

## 1. Problem (verified)

**The fold gives a universe-only actor a balance the moment they stop being live.** Both oracles compute each event's universe as `participantIds ∪ (payers+settlement parties \ liveMemberIds) ∪ (member-gated split keys \ liveMemberIds)` (`groupNetBalance.ts:683-689`; client `expense_provider.dart:106-151`), and **equal/global/sub_group/custom-empty splits divide over that FULL universe, not `participantIds`** (`groupNetBalance.ts:423-433`, comment "NOT participantIds alone"; client `allocateExpenseOwed` receives `participants.map((p) => p.id)` = the universe, `expense_provider.dart:315`, recipients `expense_provider.dart:436-444`). Consequences, in order:

1. **While live**, a member whose roster key was removed from an event (D9 permits removing a *current* member, `firestore.rules:638-641`) is outside that event's universe entirely — their paid/owed rows are **dropped** by the drop-guard (`expense_provider.dart:321-327`; server `groupNetBalance.ts:369-371`).
2. **The leave/remove zero-gate** (`leaveGroup.ts:124-141`, `removeMember.ts:~160-177`) recomputes with the member still live — so those dropped rows contribute nothing, the gate sees zero, and departure commits.
3. **The instant the member-doc delete commits**, the fold flips — but only for the NON-member-gated universe inputs. Payers and settlement parties fold unconditionally when not live (`groupNetBalance.ts:684-686`), so a departed ex-payer's paid rows **resurrect** and they gain an equal-split *owed share* of every roster-derived expense in that event: the member departs "at exact zero" and immediately nets non-zero, no post-departure write required. **Split keys and `customSplitParticipants` entries do NOT resurrect**: their fold is member-gated (`allMemberIds.has(uid) && !liveMemberIds.has(uid)`, `:687-689`; client mirror `expense_provider.dart:145-148`), and leave/remove hard-delete every member doc — post-departure the uid is in no member doc, so split-key owed is *dropped*, the pre-existing #249/drop-guard posture. The R1 guard therefore covers payers + settlement parties ONLY; refusing a split-key-only leaver would block a genuinely square member on an axis that cannot resurrect (Gate R1 rubric P2).
4. **Steady-state (the filed R1):** once such a departed universe-only actor D exists on event E, rules cannot see D (`participants().hasOnly(...)` only inspects `participantIds`; rules can't read subcollections), so a new roster-derived expense (divides over universe ∋ D → D gains share) or an event soft-delete (removes D's rows) moves D's net through a fully rules-compliant write.

**R1 genesis paths — exhaustive enumeration (why one chokepoint suffices):** a "departed universe-only actor" requires (a) financial history in an event, (b) absence from that event's `participantIds`, (c) absence from live members. Every rules-compliant write that creates (a) requires the party in `participants()` at write time: expense payer `firestore.rules:837` (unconditional in `validExpenseBase`), split keys `hasOnly(participants())`, `customSplitParticipants.hasOnly(participants())` `:843`, event-settlement parties `:1032-1033` (a Gate R2 adversary claim that the payer gate was memberIds-only was refuted against `:837`; and because `:1032-1033` gates settlement PARTIES, settle-on-behalf #595 — which relaxes only the WRITER gate — cannot create universe-only parties). So via rules-compliant writes, (b) arises only *later*, through roster removal — D9 restricts removals to current members, so the key is still live at removal (dropped, not folded); a forged/Admin write can of course create (b) directly. Either way, (c) — the transition that makes the state balance-bearing — arises only via:
- `leaveGroup`/`removeMember` — **the chokepoint this PR guards.**
- `deleteAccount` — swaps uid→tombstoneId in `memberIds` (`deleteAccount.ts:735-763`) AND in every event's `participantIds` (`deleteAccount.ts:609-611`), so the ghost is never universe-only (it stays a participant); ghosts are the R5 lane.
- `claimShadowEngine` — swaps uuid→uid in `memberIds` (`claimShadow.ts:753-778`) and re-keys participantIds; identity continuity, never universe-only.
- Admin/forged writes — outside rules scope; Admin-SDK cleanup remains possible (documented posture).

**R5 (verified in-session):** tombstone ids sit in `memberIds` (`deleteAccount.ts:735-763` swap) and rules cannot subtract them (no list filter), so every `memberIds`-based gate passes ghosts: expense payer/split-key/customSplitParticipants (`expensePartiesAreCurrentMembers`, `firestore.rules:732-741`, callsites `:852`, `:970-971`, `:1003`), the D9 removal guard (`:638-641`), event create roster (`:567`), and light additive roster adds (post-state `hasOnly(groupMembers())` passes for a ghost; `:606-607` checks additivity only). A new expense naming a ghost, or a roster add of a ghost, creates fresh exposure for a "Deleted user". Pinned as ALLOWED today by publish-readiness test 16 (`firestore-rules-publish-readiness.test.ts:3776`) — this PR flips that pin for the CREATE surface.

**R5's boundary — CREATE-side only (Gate R1 adversary P1):** deleteAccount re-keys the deleted user's existing expenses to the tombstoneId (payer, split keys, customSplitParticipants — `deleteAccount.ts:338-394`), so ghost-referencing history is the ORDINARY deleteAccount aftermath, not an anomaly. The UPDATE-path gates (`:970` post-state, `:971` pre-state, `:1003` soft-delete arm) must therefore stay on `memberIds`: switching them would permanently freeze correcting or removing any expense a deleted-account user paid for — including retroactively on legacy groups the moment an unrelated roster write self-heals `activeMemberIds` — while delivering zero R1/R5 benefit (a leave/remove-departed party fails `memberIds` and `activeMemberIds` identically, so the swaps' only behavioral delta is the ghost freeze). It would also be asymmetric with the sanctioned settlement-cleanup lane (you could settle a ghost's debt but not delete the erroneous expense that created it). Cost of this boundary: an allocation *edit* can still name a ghost (post-state stays `memberIds`) — documented as residual R5-edit; client pickers filter ghosts (#1149).

## 3. Design decisions

**D-R1 — Refuse departure with universe-only history; no marker, no rules change.** In both callables, replace the `recomputeNet(db, groupRef)` call (`leaveGroup.ts:124`, `removeMember.ts:~160`) with `loadGroupBalanceSnapshot` + `computeNetFromSnapshot` (same oracle, decomposed — `groupNetBalance.ts:745-750` shows recomputeNet is exactly this composition) and run a new **pure, read-only** detector `universeOnlyEventIds(snapshot, uid)` over the same snapshot. Non-empty → refuse. The under-lock placement (#1147) makes the check race-free: any write landing before the lock is visible to the snapshot; any write after is fenced.
*Detector semantics — match the fold's RESURRECTION set exactly:* consider only events and money docs the fold considers live (same `isDeleted === false` filters as `computeNetFromSnapshot`); flag event E when uid ∉ `E.participantIds` AND uid appears as expense `payerParticipantId` or settlement `payerParticipantId`/`recipientParticipantId` — the non-member-gated universe inputs (`groupNetBalance.ts:684-686`). **Split keys and `customSplitParticipants` are deliberately NOT detected** (Gate R1 rubric P2): their fold is member-gated (`:687-689`), leave/remove hard-delete every member doc, so post-departure those keys *drop* (pre-existing #249/drop-guard posture) rather than resurrect — refusing on them would block a square member with a factually-false error. Soft-deleted docs are excluded: they contribute nothing to the fold, and their resurrection is already blocked client-side (#1150 gates undelete pre-state parties) — including them would over-block a leaver on history they cannot act on.
*Why refuse instead of stamp-and-fence (the issue's marker option):* the marker needs new rules clauses on the #723 near-ceiling event OR-chain plus new offline-replay-drop semantics, to police a state that only Admin/forged writes can create once this guard exists (genesis enumeration §1). Refusal is ~40 lines of pure TS, uses data already loaded, and closes past *and* future genesis at the source. Server-authoritative creates (the other issue option) were rejected outright: callable-based expense creates break offline-first entry.
*Why not zero-gate the simulated post-departure fold instead:* strictly more machinery (an oracle parameter to simulate non-liveness — an oracle touch with claimShadow lock-step implications) to permit a corner (universe-only history that happens to net zero) reachable only by forged writes. Refusal is over-strict exactly there, and that's acceptable; Admin cleanup remedies it.
*Error contract:* `failed-precondition`, message `'This member has unsettled event history and cannot leave the group.'` / remove variant. The client maps `failed-precondition` from these callables to the settle-up snackbar (`group_danger_section.dart:250-253`, `group_members_section.dart:255`) — for this refusal the CTA is imperfect (settle-up alone may not clear a universe-only position; the real remedy is Admin roster repair), but the state is forge-only reachable, the snackbar is honest that history is unsettled, and `aborted` stays reserved for lock races (#1147 contract). Copy refinement rides #1149/PR3. **Do NOT mint a new error code** — both handlers treat unknown codes as generic errors with raw-ish copy, which is worse.

**D-R5a — `activeMemberIds` = memberIds minus tombstones; shadows stay in.** Shadow uuids are legitimate expense parties (D4 precedent: "shadow expenses keep working"); tombstones are identities that departed *without* a zero-gate and must never gain fresh exposure. The field is server-authoritative after create (client writes it only at group create, mirrored by rules equality).

**D-R5b — one shared transactional helper, `nextActiveMemberIds`.** New `functions/src/callables/shared/activeMembers.ts`: `async nextActiveMemberIds(tx, groupRef, groupData, op)` where `op` is `{add: id} | {remove: id} | {replace: {from, to}}`. Present field → apply op to it (dedup on add). Absent → seed: `memberIds − (tx-queried members where isTombstone == true).userId`, then apply op. Returns a plain array the caller puts in its existing `tx.update`. Callers A-F (§2 matrix) each add one call inside their existing group-doc transaction — the tx-query for tombstones runs only on the absent-field (legacy) branch. deleteAccount maps its swap to `{remove: uid}` (never `{replace}` — the tombstone must not enter). **Ordering constraint (Firestore reads-before-writes):** the helper's absent-branch tombstone query is a tx READ, so every caller must invoke it before its first `tx.set`/`tx.update` — in deleteAccount specifically, before the tombstone member-doc `tx.set`, deriving from the PRE-swap `memberIds` (deleteAccount already reads members in-tx at `deleteAccount.ts:~717-718`, so this is satisfiable; put the helper call with the other reads at the top of the tx body).

**D-R5c — rules helper with fallback, arg-passed like #1150.**
```
function activeGroupMembers() {
  return groupData(groupId).get('activeMemberIds', groupData(groupId).memberIds);
}
```
(events match scope, next to `groupMembers()` — defined at `firestore.rules:424-426`, in the events match block). Integration = swap the ARG at the CREATE-side callsites only (the #1150 pass-members-as-arg shape means each fn body evaluates it once):
- `validExpenseBase` create arm `:852`: `expensePartiesAreCurrentMembers(data, activeGroupMembers())`.
- **`validExpenseUpdate` pre+post (`:970-971`) and the soft-delete arm (`:1003`) are NOT swapped — they stay `groupMembers()`** (Gate R1 adversary P1, §1 "R5's boundary"): ghost history must remain amount-editable and soft-deletable (deleteAccount cleanup lane). Side benefit: the expense-UPDATE path — the #723-sensitive one — gains zero new expressions; only the create arm pays the one extra `get()`.
- D9 removal guard `:638-641`: `hasOnly(activeGroupMembers())` — a ghost roster-key removal is now denied (closes R5's roster axis; removing a ghost's `participantIds` key can drop their equal-split owed from the universe when they hold no payer/split-key rows, a balance move).
- Event create standard branch `:567`: `participantIds.hasOnly(activeGroupMembers())` — new events cannot roster a ghost. Founding-batch branch unchanged (collapses to `[creator]`).
- Light-update roster-add clause (inside the existing `hasAny(['participantIds'])` gate at `:606-607`): `&& request.resource.data.participantIds.toSet().difference(resource.data.participantIds.toSet()).hasOnly(activeGroupMembers())` — added keys must be active (blocks ghost adds). Admin path gets the same added-keys clause inside D9's diff-gated block.
- **Event-settlement gates (`:1061-1062`) and group-settlement gates stay `groupMembers()`** — ghost debt-cleanup settlements are sanctioned (D5/D6); switching them would strand unreadable ghost debt. Same for `correctSettlement`/`correctLogicalSettleUp` (server mirrors, unchanged).
- `validEventBase` post-state `hasOnly(groupMembers())` (`:479`) **stays memberIds** — legacy events legitimately roster tombstone ids post-deleteAccount; switching would freeze even metadata renames on them.
*Consequence, stated plainly (D4-parallel):* an event whose roster contains a ghost permanently rejects new roster-derived expense CREATES (`participants().hasOnly(activeGroupMembers())` fails), exactly like departed-roster events since #1150 — exact/shares/percent splits among active members remain available, and EXISTING ghost history stays fully correctable (update path untouched). Frozen-entry posture, consistent across both departure kinds.
*#723 ceiling:* the create-arm swap is +1 `get` on a non-ceiling path; the expense-UPDATE path is untouched (see above). The two added-keys set-difference clauses are new cost on the near-ceiling event OR-chain. **Emulator is the verdict.** Named fallback: if any legitimate-path test reports `maximum of 1000 expressions`, drop the two roster-ADD clauses (ghost-adds are forge-only — no client roster-edit UI exists, `event_service.dart` `updateEvent` sends name/dates/description only; `eventFanIn` adds live uids) and keep the cheap create swap + D9 switch; document the narrowed residual in SECURITY-RULES.md.

**D-R5d — client group create writes both fields.** `group_provider.dart:208` gains `'activeMemberIds': [uid]`. Rules enforce equality at create. Old deployed clients would fail group-create after the rules deploy — acceptable and sanctioned (pre-launch, "server changes deploy freely", CLAUDE.md).

```ts
// #1144 R1: events where `uid` has LIVE financial history but is absent from
// participantIds — the "universe-only actor" states. Read-only consumer of the
// snapshot; NOT a universe input (the claimShadow lock-step contract above is
// not in play). Mirrors the fold's liveness filters exactly: soft-deleted
// events/docs are invisible here because they are invisible to the fold, and
// their resurrection for departed parties is rules-blocked (#1150).
export function universeOnlyEventIds(snapshot: GroupBalanceSnapshot, uid: string): string[] {
  const flagged: string[] = [];
  for (const event of snapshot.events) {
    if (event.data.isDeleted !== false) continue; // strict: absent isDeleted = NOT live (fold parity)
    const participantIds: unknown[] = Array.isArray(event.data.participantIds)
      ? event.data.participantIds : [];
    if (participantIds.includes(uid)) continue;
    // Payers + settlement parties ONLY — the fold's non-member-gated inputs
    // (:684-686). Split keys / customSplitParticipants are member-gated
    // (:687-689) and DROP after the hard-delete departure — never detected
    // here (a split-key-only leaver is square and must depart freely).
    // Liveness MIRRORS the fold's strict predicates (Gate R2 rubric P2):
    // isLiveDoc is `isDeleted === false` — an absent/null isDeleted is NOT
    // live and must not be detected. Reuse isLiveDoc / the event-scope
    // filter (`groupNetBalance.ts:297-302`, `:319-326`) verbatim rather
    // than hand-rolling `!== true` (which over-includes absent-field docs).
    const appears =
      event.expenses.some((e) => e.isDeleted === false && e.payerParticipantId === uid)
      || event.settlements.some((s) =>
        s.isDeleted === false
        && (s.payerParticipantId === uid || s.recipientParticipantId === uid));
    if (appears) flagged.push(event.id);
  }
  return flagged;
}
```
