
# Rihla Architecture

## 1. Overview

Rihla ("Journey") is an offline-first Flutter mobile app for group coordination and event planning. Users create persistent groups, spin up events inside those groups, and track shared finances across all of them.

```
┌─────────────────────────────────────────────────────────┐
│                     Flutter UI Layer                    │
│   Screens (ConsumerWidget / ConsumerStatefulWidget)     │
│   shared/widgets/ — reusable components                 │
└───────────────────────────┬─────────────────────────────┘
                            │ ref.watch / ref.read
┌───────────────────────────▼─────────────────────────────┐
│               Riverpod Provider Layer                   │
│   StreamProvider.family — Firestore real-time streams   │
│   Provider.family — derived/computed state              │
│   StateNotifierProvider — mutable state (settings)      │
└────────────┬──────────────────────────┬─────────────────┘
             │                          │
┌─────────────────────────▼───────────────────────────────┐
│                     Firebase Backend                    │
│  Firestore (primary; offline persistence is the ONLY    │
│    cache — serves offline reads + replays queued writes)│
│  Firebase Auth (anon + email-link recovery)             │
│  Cloud Functions (TS)                                   │
│  Firebase Messaging                                     │
│  Firebase App Check                                     │
└─────────────────────────────────────────────────────────┘
   (no Storage SDK — protected media via Cloud Functions if ever needed)
```

### Key Design Decisions

- **Firestore is the only cache** — Firestore with `persistenceEnabled: true` and `cacheSizeBytes: CACHE_SIZE_UNLIMITED` is the sole local cache. Its offline persistence serves offline reads from previously-fetched data and replays queued writes automatically when connectivity returns. There is no hand-rolled local cache and no manual sync queue. `BalanceCalculator` consumes the live Firestore streams directly.
- **No login screen** — Firebase anonymous auth is established silently on first launch via `FirebaseConfig.ensureAnonymousSession()`. `_AuthGate` (`main.dart`) retries on `internal-error` for corrupted restored sessions. All Firestore security rules work against the anonymous UID.
- **Durable-credential recovery (#441/#818)** — users start anonymous and may create/join groups before linking. Google/email linking is same-UID `linkWithCredential` and makes the current UID recoverable with zero migration. Restore on a new device is `signInWithCredential` (same UID, zero migration). Cross-UID restore/switch paths never migrate data and may discard only a provably-empty outgoing shell. The cross-UID merge engine (`cleanupAnonUidArtifacts` callable + `recoveryCleanupIntents` collection) was deleted in #441 PR5. The old `UidChangeListener` that wiped the SQLite cache on UID swap was removed with the SQLite cache (#50). Cross-UID isolation of the Firestore SDK on-disk cache is LIVE on main (#68): a cold-start `CacheUidBarrier` + `FirestoreCacheGate` (`lib/core/services/`) plus an in-session isolation overlay clear the prior anon UID's cache on a UID swap.
- **Shared Firestore base class** — Services extend `FirestoreRepository` (which provides `eventSubcollection(groupId, eventId, module)` and a `withFirestore` test-injection constructor). Do not add new global repositories — extend the base class or an existing feature service.
- **Feature-first code organisation** — Each feature is self-contained. No shared service layer.
- **Immutable models** — All domain models (`Group`, `Event`, `Expense`, etc.) are immutable value types with `copyWith`.

## 3. State Management

The app uses **Riverpod 2.x** with manually defined providers (no code generation).

### Provider Patterns

```dart
// 1. StreamProvider.family — Firestore real-time subscriptions
//    Family parameter is EventRef (a Dart record typedef)
final eventExpensesProvider =
    StreamProvider.family<List<Expense>, EventRef>((ref, eventRef) {
  return service.watchExpenses(eventRef.groupId, eventRef.eventId);
});

// 2. Provider.family — derived state computed from multiple streams
final eventBalancesProvider =
    Provider.family<AsyncValue<List<UserBalance>>, ({EventRef, Event})>(...);

// 3. StateNotifierProvider — mutable settings state
final settingsProvider =
    StateNotifierProvider<SettingsNotifier, AppSettings>(...);

// 4. StateProvider — simple boolean/string flags
final expenseLoadingProvider = StateProvider<bool>((ref) => false);
```

### Key Providers

| Provider | Type | Purpose |
|----------|------|---------|
| `routerProvider` | `Provider<GoRouter>` | GoRouter instance with redirect logic |
| `authStateProvider` | `StreamProvider<User?>` | Firebase auth state stream |
| `connectivityProvider` | `StateNotifierProvider<ConnectivityNotifier, ConnectivityStatus>` | Online/offline status |
| `settingsProvider` | `StateNotifierProvider<SettingsNotifier, AppSettings>` | User settings + device name |
| `groupEventsProvider` | `StreamProvider.family<List<Event>, String>` | All events in a group |
| `eventDetailProvider` | `StreamProvider.family<Event?, ({groupId, eventId})>` | Single event stream |
| `eventExpensesProvider` | `StreamProvider.family<List<Expense>, EventRef>` | Event expenses (Firestore stream) |
| `eventSettlementsProvider` | `StreamProvider.family<List<Settlement>, EventRef>` | Event settlements (Firestore stream) |
| `eventBalancesProvider` | `Provider.family` | Computed balances via `BalanceCalculator` |
| `sharedPreferencesProvider` | `Provider<SharedPreferences>` | Injected via `ProviderScope.overrides` in `main()` |
| `appBootstrapProvider` | `Provider<void>` | Push notification lifecycle sync |

### `EventRef` — Canonical Event Key

All Firestore-backed event providers use a Dart record typedef as the family parameter:

```dart
typedef EventRef = ({String groupId, String eventId});
```

This enables deep-link-safe data fetching: screens receive raw strings from GoRouter path parameters and construct an `EventRef` record inline.

## 4. Data Flow

### Firestore → UI (Happy Path)

```
Firestore snapshot
  │
  ▼ (GroupService / ExpenseService / etc.)
StreamProvider.family
  │
  ▼
Riverpod provider graph
  │ (ref.watch)
  ▼
Screen widget (ConsumerWidget)
  │ (provider.when / provider.valueOrNull)
  ▼
UI renders loaded / loading / error state
```

### Write Path

```
User action in UI
  │
  ▼ (ref.read(service).addExpense(...))
FirestoreRepository subclass (ExpenseService / GroupService / etc.)
  │ (WriteBatch or single doc.set)
  ▼
Firestore (persists locally immediately, uploads when online)
  │
  ▼ (Firestore snapshot fires on local write)
StreamProvider re-emits → UI re-renders
```

### Offline Write Behaviour

Firestore's offline persistence (`persistenceEnabled: true`, `cacheSizeBytes: CACHE_SIZE_UNLIMITED`) stores pending mutations locally. When connectivity is restored, the SDK replays them automatically — no manual sync queue is maintained in this codebase.

### Connectivity Check

`ConnectivityNotifier` pings Firestore every 60 seconds with `Source.server` against the current user's `fcm_tokens/{uid}` document. State transitions between `online`, `offline`, and `syncing`. The `OfflineBanner` widget subscribes to `connectivityProvider`.

Routing is handled entirely by **GoRouter 13.x** with declarative routes. No `Navigator.push` anywhere in production code.

### Route Tree

```
│   └── /pending           (RecoverPendingScreen — ?email=)
├── /create-group          (slide-up)
├── /join-group            (slide-up)
├── /join/:code            (deep-link entry into JoinGroupScreen)
└── /group/:gid            (fade + directional slide — GroupDetailScreen)
    ├── /settings          (GroupSettingsScreen)
    ├── /settle-up         (GroupSettleUpScreen, ?memberId query param)
    ├── /activity          (GroupActivityScreen)
    ├── /create-event      (CreateEventScreen — type chip-row)
    ├── /create-event/:type (CreateEventScreen — type pre-selected)
    └── /event/:eid        (EventCommandCenter — ACTIVE landing hub; user taps Ledger→ / +Add expense from here)
        ├── /ledger        (LedgerScreen)
        │   ├── /add       (AddExpenseScreen)
        │   ├── /edit/:expId (EditExpenseScreen)
        │   └── /settle-up (SettleUpScreen)
        ├── /activity      (ActivityFeedScreen, event-scoped)
        ├── /recap         (EventRecapScreen — #202 event closeout projection)

```

### Transition Patterns

| Route | Transition |
|-------|-----------|
| `/home`, `/profile`, `/activity` | `FadeTransition` |
| `/create-group`, `/join-group` | Slide-up (`Offset(0,1)` → zero) |
| All other module routes | Hand-rolled fade + directional slide via the `_sharedAxisTransition` builder (no `animations` package) |

### Splash Redirect

The splash route redirects unconditionally to `/home`; `appRouteRedirect` does not gate on `onboardingComplete`. `_AuthGate` ensures a Firebase anonymous session (with `internal-error` retry for corrupted restored sessions) before `SafarApp` renders.

### Direct-entry back guards

Any screen reachable as a direct route (deep links, recovery flows) checks `context.canPop()` and falls back to `/home` (or another root) when the stack is fresh. Tests under `test/features/.../*_navigation_test.dart` (e.g. `group_detail_navigation_test.dart`) enforce this; `Navigator.push`, `state.extra`, and named GoRouter calls (`goNamed`) are forbidden in production code (the readiness check greps for them).

### Type-Safe Route Names

All route path strings are defined as constants on `AppRoutes`:

```dart
class AppRoutes {
  static const String groupDetail = '/group/:gid';
  static const String eventHub = '/group/:gid/event/:eid';
  // ...
}
```

## 6. Offline Architecture

There is no hand-rolled local cache. Firestore's own offline persistence is the only cache — it serves offline reads from previously-fetched data and replays queued writes automatically. The former `LocalDatabase` (`safar_cache.db`) and its `lib/core/services/cache/` repositories were removed in issue #50; `BalanceCalculator` now reads the live Firestore streams directly.

> **Cross-UID cache isolation (live).** The old `UidChangeListener` wiped the SQLite cache on UID swap to keep one device's recovered account from reading the abandoned anon UID's cached data. It was removed with the SQLite cache (#50). Cross-UID isolation of the Firestore SDK on-disk cache is LIVE on main (#68): a cold-start `CacheUidBarrier` + `FirestoreCacheGate` (`lib/core/services/`) plus an in-session isolation overlay clear the prior anon UID's cache on a UID swap. The server-side `cleanupAnonUidArtifacts` callable was deleted in #441 PR5 — post-gate restores are same-UID (Google) or discard an empty shell (email), so there is nothing to scrub.

### `ConnectivityNotifier`

File: `lib/core/providers/connectivity_provider.dart`

Checks connectivity by firing a server-sourced Firestore read every 60 seconds. Exposes `ConnectivityStatus.online / offline / syncing` via `StateNotifierProvider`. The `OfflineBanner` widget watches this provider.

### Firestore Offline Persistence

Configured in `FirebaseConfig.initialize()`:

```dart
FirebaseFirestore.instance.settings = const Settings(
  persistenceEnabled: true,
  cacheSizeBytes: Settings.CACHE_SIZE_UNLIMITED,
);
```

This must be called before any Firestore read/write. All pending writes are replayed by the SDK on reconnection.

## 8. Financial Calculations

### Money Representation

All monetary values use the **`decimal` package** (`Decimal` type). Floating-point arithmetic is never used for money.

At the Firestore boundary, `MoneySerializer` converts between `Decimal` and integer subunits:

```
OMR 10.500  →  10500 (fils, scale 1000)
USD 9.99    →  999   (cents, scale 100)
JPY 100     →  100   (units, scale 1)
```

Supported currencies: OMR, USD, EUR, GBP, SAR, AED, JPY, KWD, BHD, QAR.

Default group currency is **OMR** (Omani Rial, 3 decimal places), but money
documents carry explicit currency codes and group/cross-group balances are
bucketed per currency with no FX conversion.

### `BalanceCalculator`

Defined in `lib/features/ledger/providers/expense_provider.dart`. Pure function — no side effects, no providers. The remainder from quantization goes to the **alphabetically-last recipient** so `sum(shares) == amount` exactly. Do not change this without updating `test/unit/balance_calculations_test.dart`.

**`calculateBalances()`** processes four expense scopes:

| Scope | Split logic |
|-------|-------------|
| `global` | Split evenly among all event participants |
| `subGroup` | Legacy scope (logistics removed in Phase 39) — back-compat fallback that splits evenly among all event participants, same as `global` |
| `personal` | No split — payer is solely responsible |
| `custom` | Split among a specified subset of `customSplitParticipants` |

> **Itemized bills (#203/#605) are NOT a fifth scope or `SplitMode`.** They are `SplitMode.exact` plus an opaque `SplitExplanation`/`SplitAdjustment` payload (`lib/features/ledger/models/split_explanation.dart`); items + service/tax/tip/discount adjustments fold into the exact `splitDistribution` client-side, and `splitExplanation` is display-only — never read by the server oracle.

Per-head cost is quantized to the expense currency's integer subunit precision
by round-tripping through `MoneySerializer` (`_toCurrencyPrecision`). This keeps
client math aligned with the server oracle and handles OMR/KWD/BHD at 3dp,
USD-style currencies at 2dp, and JPY at 0dp:

```dart
final perHead = _toCurrencyPrecision(
  (expense.amount / Decimal.fromInt(splitCount)).toDecimal(
    scaleOnInfinitePrecision: 10,
  ),
  expense.currency,
);
```

Settlement adjustments are applied after the split phase. The result is a `List<UserBalance>` with `totalPaid`, `totalOwed`, and `netBalance` per participant.

### Settlement Optimisation

**`calculateOptimalSettlements()`** uses a greedy heuristic (largest debtor ↔ largest creditor) — conservation-correct and near-optimal for typical small groups, but not provably the minimum (true minimization is NP-hard; no test asserts minimality):

1. Separate participants into debtors (`netBalance < 0`) and creditors (`netBalance > 0`)
2. Sort debtors ascending by balance; creditors descending
3. Pair the largest debtor with the largest creditor; settle the minimum of the two
4. Advance the pointer of whichever side reaches zero
5. Repeat until all balances are resolved

Result: minimal number of transfers to clear all debts.

### Group-Level Balances

`GroupBalanceProvider` (in `lib/features/groups/providers/group_balance_provider.dart`) tracks balances across all events in a group, computed from the Firestore-backed settlement streams. There is no SQLite balance table — the computation runs over the live streams.

### Payments

Payment processing is out of scope for the shippable v1 surface. Ledger settlement records track who owes whom; the app does not initiate real payment collection.
