#279 · The two Ahmeds problem

In the Gulf cohort, shared names are everywhere — a group easily holds two Ahmeds or two Mamas. Today JoinGroupScreen's Your name field free-types any name that passes length + control-char checks, with no collision check on the server (joinGroupByInviteCode.ts → normalizeDisplayName). Two identical names make the roster and settle-up ambiguous: who owes whom? These variants attack it at different points — prevention at entry vs. render-time disambiguation. ← gallery

bug(data-integrity): no display-name collision guard on join — duplicate names make the ledger ambiguous

P2 · bug · data-integrity · pairs with #289 disambiguator

Both variants want the same outcome — an unambiguous ledger — but choose where to fix it. V1 catches the clash while the joiner is still typing and nudges a one-tap distinct name (prevention at the source). V2 accepts the duplicate and disambiguates everywhere the name renders (roster, settle-up). V1 keeps stored names clean for free-text writes; V2 needs no server change but pushes the suffix logic into every name-rendering surface.

Recommendation: Variant 1 (inline disambiguation at entry) — fix it at the source so the stored name is already distinct; render-time suffixing (V2) is the fallback for names that slipped in before the guard existed.
