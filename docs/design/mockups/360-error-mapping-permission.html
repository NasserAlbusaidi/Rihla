#360 · Settle-up errors say the wrong thing

The settle-up catch block maps every failure to one string — settleUpRecordFailed = “Couldn’t record settlement. Check your connection and try again.” So a real permission-denied (you were removed from the group, ties to #358) reads as a flaky network. And a Firestore offline-queued write currently lands on the silent success branch — the money looks saved with no “will sync” reassurance. #360

fix(settle-up): error mapping mislabels permission-denied as “check your connection”

P3 · design · settle_up_screen.dart:340 · app_en.arb:816

Branch the catch at _recordSettlement on the FirebaseException.code: network codes keep the connection copy; permission-denied / unauthenticated get distinct, honest messages; and an offline-queued write (success-while-disconnected) earns a “saved, will sync” confirmation instead of the plain green toast. One new mapping function, three new ARB strings — no layout change.

Recommendation: After (mapped) — the current single-string mapping is a correctness bug: it tells a removed user to “check their connection,” which they’ll do forever. The mapping table below is the contract to ship.

Error mapping contract — firebase code → friendly copy
permission-denied
You no longer have access to this group. Removed / left (#358). Offer a dismiss → pop to groups, not a retry.
unauthenticated
Your session expired. Reopen Rihla to continue. Token lapsed mid-write — a network retry won’t fix it.
unavailable
Couldn’t reach Rihla. Check your connection and try again. The only code that keeps today’s string — a genuine network reach failure.
offline-queued
Saved — will sync when you’re back online. Firestore accepted the write locally; not an error. Sage toast, not green “recorded.”
