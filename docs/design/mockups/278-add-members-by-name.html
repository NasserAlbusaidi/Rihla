#278 · Add members by name at creation

A fresh group is a group of one: createGroup writes only the creator's member doc, and every friend must self-install + join by code before anything can be split. The GroupMember.isShadow field exists and the split UI already renders a "Shadow Profile" label — but no write path ever creates a shadow member. These variants are the creation surface for letting the creator seed placeholder people now, claimed on join later. ← gallery

#278

feat(groups): add members by name at creation (isShadow model is dormant)

P2 · enhancement · design · screen: CreateGroupScreen

All three live inside the existing create_group_screen.dart form (group name → your name → OMR currency). V1 and V2 add a people-seeding section that writes isShadow:true member docs; V3 is the honest counter-case — skip names entirely and lean on the invite link. Shadow people render with the dashed .avatar.shadow + a Shadow .pill-tag so it's clear they're unclaimed placeholders until a real person joins and claims the name.

Recommendation: Variant 1 (chips field) — one calm "Who's in?" line on the screen they already fill in, lowest friction to escape the group-of-one trap, and chips read as lightweight/erasable rather than a roster commitment.

No shadow members, no claim/merge step. Trade-off: until someone joins you're still a group of one — you can log spending but can't split it yet.

What: the deliberate counter-direction — no name fields at all, just push the invite code/link harder. Why distinct: it sidesteps the entire claim/merge problem and keeps the create screen untouched, surfacing the real cost of not doing #278 (the group-of-one wait). Implies: zero new write paths — but #278's persona pain (split tonight's dinner before anyone installs) stays unsolved, which is exactly why V1/V2 exist.

Scope note (Gate): this mockup is the creation surface only. The hard parts — claiming a shadow member on join, merging their accrued share into the real userId, and the name-collision guard (#279) — are money + schema changes that touch balances and Firestore rules, so they are Gate-mandatory and specced separately. V1 vs V2 differ only in how the creator types names; both produce the same isShadow:true member docs.
