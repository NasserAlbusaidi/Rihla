#698 · Trip Float — the shared pot

Core of headline epic #709. A crew throws OMR 50/head into a pot one person holds and spends from. Trip Float is a view + wizard over primitives that already exist: a chip-in is a settlement to the holder (#595), a pot spend is a holder-paid expense, remaining is derived — the oracle (calculateBalances/recomputeNet) is untouched. Worked example throughout: Musandam Trip, 4 people, target 50/head, Sara holds the pot. Omar has only chipped 30 so far. ← gallery

#698 · 1

Start a Trip Float — the wizard

entry: EventCommandCenter hub · one float per event · currency locked to group

Setup must take seconds for a non-accountant: who holds the cash and how much per head. Config lands as an opaque tripFloat map on the event doc (spendingSnapshot pattern) — no new collection. The float's currency is pinned to the group currency; chip-ins are recorded after creation, from the pot card, as cash actually changes hands.

Recommendation: A. One sheet, one decision surface. B's seed step front-loads data entry for money that usually arrives over the first day — record-as-it-happens beats declare-upfront.

The pot, live — hub card + float screen

derived view · Σ tagged chip-ins − Σ tagged pot spends · balance truth stays in settle-up

Everything here is a pure projection over tagged docs: IN = chip-ins (floatId-tagged settlements to Sara), SPENT = pot spends (floatId-tagged expenses Sara paid), REMAINING = IN − SPENT. Per person: paid-in vs their share of pot spends. Invariant the tests will pin: Σ per-person positions = remaining (10.625 + 10.625 + 10.625 − 9.375 = 22.500 ✓).

Recommendation: A. A hub card that opens a dedicated screen. B (a strip inside the ledger) can't carry the per-person panel or the closeout without crowding the expense list.

#698 · 3

Money in, money out — chip-in sheet + pot toggle

both ship · chip-in = tagged settlement to holder (#595) · draw = tagged holder-paid expense

The two write moments. Any member can record a chip-in for anyone (#595 already allows any-member-records-between-two-participants). A pot spend is the normal add-expense flow with one new switch: Paid from the pot — it pins the payer to the holder and tags the doc. No new write paths, no new validation surface beyond two allow-list keys.

No competition here — these are the shipping designs for both flows.

#698 · 4

Closeout — the pot folds into settle-up

no new mechanics · netBalance already carries every fils · feeds Trip Receipt (#704)

The epic's sharpest promise, provable with this worked example: because chip-ins and draws were real settlements and expenses all along, the ordinary settle-up already reconciles the pot — including Omar's 20.000 shortfall and the 22.500 cash still in Sara's pocket. Closeout is a status flip + an explanation, not a new money flow.

Single design. The one decision inside: closing the float does NOT write any settlement — the “Settle up” CTA hands off to the existing flow.

The proof-of-design phone. Note the fold: Sara's pot cash (22.500) minus what she hands Nasser and Ali (11.875) leaves exactly her own unspent 10.625 — and Omar's shortfall routes to Ali through the normal greedy min-transfer pass. Zero float-specific settlement writes; the suggested transfers line is the existing settle-up output, quoted. Closing stamps tripFloat.closedAt (view freezes, toggle disappears from add-expense) and the frozen summary feeds the Trip Receipt group pack (#704's open slice).

What this locks for Slice 1 data contract
Schema (all oracle-invisible)

event.tripFloat — opaque map: holderId · targetPerHeadSubunits? · currency · startedBy · startedAt · closedAt?. Partial-update only (spendingSnapshot pattern), diff-gated rules fn mirroring validEventCloseToggle — cheap gate first, 1000-expr ceiling respected.

settlement.floatId + expense.floatId — nullable string tags joining the two hasOnly allow-lists with absent-or-string guards. Exact precedent: groupSettleUpId (#752) / splitExplanation (#203). Never read by recomputeNet or any Function.

Gate probes queued

① Holder self-chip-in = tagged self-settlement (payer == recipient, nets to zero) — verify rules + BalanceCalculator accept it. ② Chip-in display special-case (“chipped in”, never “paid Sara”) at every settlement render surface. ③ Closed event (isClosed) freezes pot writes via existing eventAllowsClientWrites — float closeout should nudge before event close. ④ Multi-currency: pot is single-currency; tagged docs in another currency are a rules-reject, projection filters defensively.

Invariant for the tests

Σ per-person positions = remaining (here: 10.625 × 3 − 9.375 = 22.500 ✓) — table-driven across clean / short-chipper / negative-pot / custom-split cases.

The mockups shaped the contract: the target field exists because the progress chips need it; closedAt exists because the closeout freezes the view; the self-settlement exists because Sara's row above had to show in 50.000.
