#200 · Cross-event settle-up, made explicit

Group settle-up already aggregates every event and suggests optimised transfers — mathematically right, but a transfer like Ahmed → you can span people who never shared the original bill, and an event ledger can stay uneven after the group is settled. This issue makes the settlement explicit before recording, auditable afterwards from a persisted snapshot, adds a calm scope explainer so event and group ledgers are never confused, provides a first-class correction path (append-only offsetting record), and detects stale outstanding amounts before the write. All three directions sit on the existing group_settle_up_screen.dart path. ← gallery

#200

money/ux: make cross-event group settle-up explicit and auditable

P2 · money · design · cluster:settlement-ux

Each variant covers the same core jobs — a pre-record confirmation that itemises which events feed this transfer (AC1); a persisted per-event breakdown read back from the settlement snapshot, not recomputed (AC2); the "group settled, event ledger still uneven" scope explainer (AC4); a stale-balance revalidation state that surfaces when the outstanding amount changes while the sheet is open (AC6); and a correction path via an append-only offset record (AC5). Former-member settlement behaviour (AC7) is a product/rules decision deferred to a follow-up spec; the designs leave the recipient surface unchanged for that case. Variants differ in how the confirmation reads: itemised receipt sheet (V1, pick), plain-language sentence with expandable detail (V2), or inline provenance on the main screen (V3). The optimiser stays greedy_min_transfers; nothing about anyone's net position changes — we only make it legible.

Recommendation: Variant 1 (Receipt breakdown) — money decisions earn trust when the itemisation is visible at the moment of commitment, and the same receipt persists into history unchanged. V1 also most naturally hosts the stale-balance review state as a second sheet phase.

Receipt-first confirm sheet, with stale-balance guard. A showConfirmSettlementSheet stage between showRecordPaymentSheet and _recordSettlement itemises the per-event contributions from buildBreakdown (AC1), then persists them as settlementContext.eventBreakdown[] on the write so history reads back the same receipt, not a recompute (AC2). Immediately before writing, the service re-reads the outstanding pair amount; if it changed since the sheet opened, the confirm UI flips to the stale-balance review state rather than writing blindly (AC6). The scope banner distinguishes group vs event closeout (AC4). Correction (AC5) lives in the history tile's expand — a "Record correction" action opens a sheet pre-populated with a negative amount that creates an offsetting append-only record. Strongest match for the money label: the user commits to a decomposed number they can verify.

Sentence-first, detail on demand. Leads with a single readable claim ("…covering 2 events") and tucks the itemisation behind an expander — the math still persists to settlementContext on write (AC2), it's just collapsed at confirm time. Scope banner addresses AC4. Stale-balance revalidation (AC6) would interrupt with an inline warning above the CTA (same pattern as V1, not shown separately). Lighter to build than V1 (one summary string + reused breakdown rows) but the contributing amounts aren't on screen at the moment of commitment — weaker for a money flow where the breakdown is the trust signal.

Provenance built into the screen, not a sheet. The scope explainer is pinned at the top of settle_up_page_body.dart (AC4), the outstanding transfer shows its per-event breakdown inline (AC1), and every recorded row is tappable into the persisted settlementContext snapshot — including append-only correction offsets (AC2 / AC5). A "Record a correction" affordance makes the offset path explicit without mutating the original. Stale-balance revalidation (AC6) surfaces as a banner on the outstanding card before the Record button when amounts drift. Most surface-area (touches page body + history tile + provenance route + correction sheet) and the moment-of-commitment review is thinner than V1, making it the weakest pick for a first-time settle-up — but the strongest for repeat auditing.
